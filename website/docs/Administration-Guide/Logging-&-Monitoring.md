# Logging

The logs from the LLM containers is standardized across all of the different models.
This has been done in order to be able to parse all of the relevant information from the logs and create monitoring on top of them.

In order to make use of these logs, which are written to the standard out of each container, you must collect the logs.
If you do not have an established logging and monitoring process, you can use the simplified logging script provided below.
Otherwise, if you do have an established way of collecting logs, ensure that you can export them to a folder that can be accessed from SAS Studio as a `.log` file (as that it is the input for the parsing utilities).
The file has to hold the lines as the containers wrote them: the parser only reads a line that starts with `<timestamp> - <logger> - <level> - `, so a timestamp, a pod name or a JSON wrapper that your process adds to each line has to be removed again. If it is not, the parser reads no request and says so with a warning in the SAS log. The lines of each container also have to stay together in the file, as `kubectl logs` writes them: an export that orders the lines of all containers by their time is read with gaps, see [Requests that run at the same time](#requests-that-run-at-the-same-time).

For more information on how to parse the log and load it into SAS please take a look at `SAS-Viya-Integrations/Logging-Monitoring`.

Three programs of that folder work on the collected log, and they run in this order:

1. **Collect** the log - the script below, or your own process.
2. **Parse** it: `Log-Parser-Code.sas` or the *LLM - Log Parser* custom step write one row per request to the table `LLM_LOGS` - see [Running the Parser](#running-the-parser) and [The Columns of LLM_LOGS](#the-columns-of-llm_logs).
3. **Pull** what the Prompt Builder keeps in SAS Model Manager: `Get-All-Prompts.sas` or the *LLM - Get All Prompts* custom step write the experiments, the RAG setups and a catalog of models - see [The Experiments of Every Kind](#what-it-reads).
4. **Link** the two: `Link-Logs-To-Models.sas` fills, for every row of `LLM_LOGS`, the SAS Model Manager id of the model that answered and of the prompt, decision template or RAG setup that sent the request - see [Linking the Log to the Models](#the-rules-in-their-order).

:::note What the containers log
The shipped deployment templates set `SAS_SCR_LOG_LEVEL_SCR_IO=TRACE`, and the parser depends on it: the `Request: POST` / `Request Data:` lines carry the inputs and the options of every call, and the lines of the score code the token counts, the run time and the answer. For an LLM that is the system prompt, the user prompt and the full response; for a decision model the state, the questions and every answer with its confidence; for an embedding model the embedded text. That is what makes the usage report possible, and it also means prompt text and responses land in your log pipeline. Of an embedding call the table keeps the hash of the text in place of the text, and it also keeps the options of every call without their keys and the first error of a request that failed. Decide who may read the collected log file and the `LLM_LOGS` table accordingly, or lower the level and forgo the report.
:::

:::danger The containers also log secrets
At this level a container writes more than prompts. The options of a request are logged as they arrive, and for every model that is called with a provider key they hold it as `API_KEY:<the key>`. The request headers are logged too, and a call from the browser (the Prompt Builder) carries the user's `Cookie` header. Both must not reach a file that SAS Studio users can open: the collection script below replaces them with `REDACTED` before a line is written, and an established logging process needs the same step. The `redact_llm_log` function of the script expects the lines as the container wrote them, which is how `kubectl logs` prints them without `--timestamps` or `--prefix`: its three header expressions match a header at the start of a line, and only the `API_KEY` expression finds its text anywhere in a line. A process that puts a timestamp or a pod name in front of every line, or wraps the line (the log files of the container runtime, JSON), has to redact before that happens or adapt the three header expressions.

A log file collected **without** this redaction - with the script of release 2.2.0 or earlier, for example - may contain provider keys and session cookies. Delete those files, including copies and backups, and rotate every provider key that was in use while they were collected. The `LLM_LOGS` table never held either and does not need to be rebuilt for this: the parser never copied the key or a header into it. The parser of this release keeps the options of a request and replaces the keys in them itself, and of the headers it keeps the `X-Request-Id` and the kind of client.
:::

## Simplified Logging via a Script

Only use this script if you do not have a more robust process in place.

Create a script—for example `collect_llm_logs.sh`—and ensure that it is executable.
Use the code below and change both the namespace and the log path.
The namespace should be the namespace into which you have deployed the models, and the path needs to be reachable from inside of SAS Studio. The path below is an example and site specific - see [Getting the File to the SAS Compute Server](#getting-the-file-to-the-sas-compute-server) for what it assumes and for a way without it.
You can also change the logging interval; note that any changes you make here will have to be reflected in the entry for the `crontab`.
The default here also replaces the log file, as the assumption is that you pick up the new entries using the parsing script and append them to the table (a full replacement is also supported). The parser appends only where it is told to: set `%let _log_append_table = 1;` in front of it, see [Appending](#appending). With `%let _log_append_table = 0;` it replaces the table by the requests of the one file, and without the setting it stops at a table that holds rows.

```bash
# Set the script variables for your environment
llm_namespace="llm"
llm_log_path="/viya-share/pvs/sasdata/data/llm/llms.log"
llm_logging_interval="1h"
# Selects the model pods: the deployment templates label each of them app=<model name>
llm_pod_selector="app"

# Replaces the secrets in the container log with REDACTED: the provider key in the
# options of a request and the values of the Cookie, Authorization and X-CSRF-TOKEN
# request headers (in any spelling of upper and lower case, which needs GNU sed).
# sed runs in the C locale, where every byte is a character: in a UTF-8 locale a byte
# that is no UTF-8 ends a match, and what stands behind it would stay as it is
redact_llm_log() {
  LC_ALL=C sed -E \
    -e "s/(API_KEY:)[^,}'\"]*/\1REDACTED/g" \
    -e 's/^((.* Request Headers: )?Cookie:).*/\1 REDACTED/I' \
    -e 's/^((.* Request Headers: )?Authorization:).*/\1 REDACTED/I' \
    -e 's/^((.* Request Headers: )?X-CSRF-TOKEN:).*/\1 REDACTED/I'
}

# Keeps the lines of a container apart from the line this script writes in front of them: a
# line of a container that starts like that line - at its start or behind a carriage return,
# with or without backslashes in front - gets one more backslash in front, which the parser
# takes off again. The last line of a container is ended where it is not (needs GNU sed)
escape_llm_log() {
  sed -E \
    -e 's/(^|\r)(\\*#=# llm-log-collection )/\1\\\2/g' \
    -e '$a\'
}

# The time of this collection, in UTC: the same in the line in front of every container
llm_collected_at="$(date -u +%Y-%m-%dT%H:%M:%SZ)"

# Remove the next line to append to the log file instead
rm -f "$llm_log_path"
for pod in $(kubectl get pods -n "$llm_namespace" -l "$llm_pod_selector" -o name); do
  for container in $(kubectl get -n "$llm_namespace" "$pod" -o jsonpath='{.spec.containers[*].name}'); do
    # One line in front of the lines of each container: the parser ends a part of the file there
    {
      printf '#=# llm-log-collection pod=%s container=%s collected=%s #=#\n' "${pod#pod/}" "$container" "$llm_collected_at"
      kubectl logs -n "$llm_namespace" "$pod" -c "$container" --since="$llm_logging_interval" | escape_llm_log
    } | redact_llm_log >> "$llm_log_path"
  done
done
```

The script reads the model pods only. `-l app` selects every pod that carries a label named `app`, which the shipped deployment templates set to the name of the model. The pod of a `stage-weights` job does not carry it and stays out of the file, and so does every other workload that is labelled differently. If something else in your namespace is labelled `app` as well, give the model deployments a label of their own and set `llm_pod_selector` to it (for example `llm_pod_selector="accelerator=model"`).

The script reads every container of every model pod on its own, and writes one line in front of its lines: `#=# llm-log-collection pod=<pod> container=<container> collected=<time of the collection, UTC> #=#`. All lines of one run carry the same time. A container can write a line of that shape - a model writes what it is asked for, and its response is logged line by line -, so the script keeps the two apart: `escape_llm_log` puts a backslash in front of every line of a container that starts like the line of the script, at the start of a line and behind a carriage return, with or without backslashes in front, and it ends the last line of a container where `kubectl logs` did not. In a file this script wrote, a line of that shape is therefore a line of the script. The redaction leaves the line of the script as it is and makes no other line a line of that shape. The parser ends a part of the file at each such line and nowhere else, whatever time of collection the line carries, and takes the backslash off again, so a response holds the line as the model wrote it: a request that was running when its container was collected ends there without a response and without an error - `failed` is missing, and a NOTE counts it - and no line of one container is taken for a line of another. A file without such lines - collected with the script of release 2.2.0 or earlier, or by a process of your own - is read by the time of its lines, as before, and so is what stands in front of the first such line in a file that is appended to across the upgrade. In those lines nothing was put in front of a look-alike: a line of that shape in a response there is read as the line of the script. It ends the response, its request has no status and `failed` is missing - the NOTE counts it -, and the lines behind it are read as one part up to the next line of the shape. No code can tell it from the line of the script: a file with such a line in a response and a file in which the first collection of this release begins in the middle of that response are the same line for line, and a test of the repository holds the two. So start a new file with the script of this release instead of appending to a file of an earlier one. A process of your own can write the same line in front of the lines of each container it collects; it then has to put the backslash in front as the script does. The pod is no column of `LLM_LOGS`. On 2026-10-13 the script as it was that day - without `escape_llm_log` - collected the nine model pods of the test system and wrote nine such lines, all with one time of collection, and `Log-Parser-Code.sas` of that day read the file ([The Pass of 2026-10-13](#the-pass-of-2026-10-13)). The script with `escape_llm_log`, and version 2.7 of the parser, which takes the backslash off, ran in the tests of the repository only - the script with a `kubectl` of the test that answers from files and with GNU `sed` 4.9 of Git for Windows, which drops a carriage return in front of a line feed, so the lines that end with both were held by their rows and not by their bytes. They have not run in a live pass and are not run in SAS.

The redaction happens in the pipe, so an unredacted line is never written to disk, and the parser reads a redacted log exactly like an unredacted one. `redact_llm_log` runs `sed` in the C locale (`LC_ALL=C`), where every byte is a character. In a UTF-8 locale GNU sed matches a byte that is no UTF-8 with neither `.` nor a bracket expression, and the function as it was first written for this release - without the locale - redacted the value of a header or of `API_KEY` only up to such a byte. Measured on 2026-10-13 with GNU sed 4.9 of Git for Windows and the expressions of the script: in the locale `en_US.UTF-8` and in `C.UTF-8` the line `Cookie: abc<FF>secret-value` (`<FF>` being the byte 0xFF) became `Cookie: REDACTED<FF>secret-value`, and `x API_KEY:sk-abc<FF>secret, y` became `x API_KEY:REDACTED<FF>secret, y`; in the C locale they became `Cookie: REDACTED` and `x API_KEY:REDACTED, y`. A shell that a cron job starts often runs in the C locale already, an interactive one usually does not. The function with the locale is **not run on Linux or against a cluster**; the tests of the repository run it with GNU sed 4.9 of Git for Windows. The four `sed` expressions cover what the containers are known to log; if your requests carry a secret in another header, add a line for it.

An hour without a single request leaves a file without requests. The parser reports that with a note and leaves the `LLM_LOGS` table as it is.

Next add the following entry to your crontab (`crontab -e`), adjusting your path to the script:

```bash
0 * * * * /viya-share/pvs/sasdata/data/llm/collect_llm_logs.sh
```

This entry will run the log collection script at the top of every hour.

## Getting the File to the SAS Compute Server

The paths of this guide are examples, and both are site specific. The script writes to `/viya-share/pvs/sasdata/data/llm/llms.log` and the parser reads the path that `%let _log_path = sasserver:/export/pvs/sasdata/data/llm/llms.log;` names where `_log_path` is not set - the statement a site sets its own path with, in front of the program ([Settings that stay yours](#settings-that-stay-yours)). The two name the same file only on a system where the host that runs the script and the SAS compute server mount the same storage under these two paths. Set `llm_log_path` to the file as the collecting host sees it and `_log_path` to the same file as a compute session sees it, with `sasserver:` in front: the parser reads the file from the file system of the compute server, stops with an error for any other location and does not read from SAS Content.

Whether a compute session sees a directory can be asked in that session, `exists=1` means it does:

```SAS
data _null_;
    exists = fileexist('/export/pvs/sasdata/data/llm');
    put exists=;
run;
```

### Without a Shared Mount

On the test system (SAS Viya 2026.09, measured on 2026-10-11) there is no such mount: in a compute session neither `/export` nor `/viya-share` existed, and the workstation that collected the logs shares no directory with the compute server. The file went through SAS Content there:

1. The script of this guide wrote the redacted file to a local directory of the collecting host (`llm_log_path`).
2. The file was uploaded to a folder in SAS Content with the Files service: `POST /files/files` with the folder as `parentFolderUri`, the file as the body and its name in the `Content-Disposition` header.
3. The job that runs the parser first copied the file from SAS Content into the compute session, with a `FILESRVC` file reference and `fcopy`, and the parser then read the copy:

```SAS
/* Copy the collected file from SAS Content to the SAS compute server */
filename llmsrc filesrvc folderpath='/Users/<user>/My Folder/<folder>' filename='llms.log' recfm=n lrecl=32767;
filename llmdst '/tmp/llms.log' recfm=n lrecl=32767;
data _null_;
    length msg $300;
    rc = fcopy('llmsrc', 'llmdst');
    msg = sysmsg();
    put 'Copy of llms.log: ' rc= msg=;
run;
filename llmsrc clear;
filename llmdst clear;

/* Set the path in front of Log-Parser-Code.sas: the program takes _log_path where it is set */
%let _log_path = sasserver:/tmp/llms.log;
```

From release 2.3.0 on the last line stands in front of the program - in a program of your own that then includes the shipped file, see [Settings that stay yours](#settings-that-stay-yours): `Log-Parser-Code.sas` takes `_log_path` only where it is not set. That is how the program ran in [The Second Pass of 2026-10-13](#the-second-pass-of-2026-10-13), with its settings in front of the shipped file. Up to then the program set `_log_path` itself, in a `%let` line among its first lines, so a `%let` that only stood in front of it had no effect and the line of the program had to be changed. Both were measured on 2026-10-11, with the program of that day. With the block in front and the program's own line changed to `sasserver:/tmp/llms.log`, the parser wrote the 174 rows of the file. With the block in front of the unchanged program, the copy went through and the program then read its default path: `FileNotFoundError: [Errno 2] No such file or directory: '/export/pvs/sasdata/data/llm/llms.log'`, then `ERROR: The log could not be parsed, ...`, and the job ended as failed. The custom step has no such line: there the copy is the file the step is given as its log.

These are the statements that ran. On 2026-10-11 they ran as they are printed here, with only the folder filled in - one below the *My Folder* of the user who ran the job: the log said `Copy of llms.log: rc=0 msg=`, and the copy had the size and the MD5 digest of the uploaded file (558,176 bytes). In the first runs, earlier that day, each collection had a file name of its own; `fcopy` returned 0 there as well, and a file of 0 bytes arrived as a file of 0 bytes. `/tmp` is a directory that existed in the compute session of that system - the `fileexist` step above gave `exists=1` for it and `exists=0` for `/export/pvs/sasdata/data/llm`; take one your compute server can write to. The three steps were started one after the other, not from a crontab entry.

The file in SAS Content holds the prompts and the responses like the log itself, so whoever may read that folder reads them (see the note at the top of this page).

## Running the Parser

`Log-Parser-Code.sas` and the *LLM - Log Parser* custom step hold the same program. The README of `SAS-Viya-Integrations/Logging-Monitoring` describes the table it writes, what a row holds for each kind of model and what happens to a table that already exists. The two differ in what they bring along:

`Log-Parser-Code.sas` and the *LLM - Log Parser* custom step reach a site with the transfer package, in the folder `Logging and Monitoring` of the content folder ([Install or upgrade with the transfer package](./Setup-Additional-UIs.md#the-transfer-package)); from a checkout, `mdb content-deploy` brings both. A registered step is updated in place - `PUT /dataFlows/steps/{id}` with the file and its `id`, answered 200 with the id kept when it was measured on 2026-10-11 and on 2026-10-12 -, which is what `mdb content-deploy` does: a step that is deleted and uploaded again gets a new id, and saved flows that use it then have to be given the step again. The import and the deploy bring the step to its path of this release, `Logging and Monitoring/LLM - Log Parser.step`. A step your flows use from another folder - the starter package of earlier releases had it in `Custom Steps` - is not touched by either: update it in place from a checkout with `mdb content-deploy --only "Logging and Monitoring/LLM - Log Parser.step" --to "<path or id of your step>"`, see [One part, somewhere else](./Model-Definition-Builder.md#one-part-somewhere-else). Measured on 2026-10-13 in two test content roots: with the path of a registered step of that name the line said `equal` and named the step and its folder; with the id of a step of another name nothing was written and the line asked for `--force`, and with `--force` the step was updated with its id kept. A flow or a job that runs the step more than once in one SAS session needs the step of release 2.3.0. That step announces 36 columns to a flow; a flow that holds an older step announces twelve. A copy of the package `SAS Agentic AI Accelerator.json` of earlier releases must not be imported for the parser: that starter package holds the step and the code file of May 2025 - twelve columns, LLM calls only, and the session check that fails in a second run.

- **`Log-Parser-Code.sas`** starts a CAS session itself (`cas mysess;`) when the SAS session has none that is connected, assigns the librefs `public` and `casuser` and takes each of its settings where the macro variable is not set when it starts ([Settings that stay yours](#settings-that-stay-yours)). The session and the two librefs stay when the program ends. `_log_target_table_lib` names a libref: the program looks up the caslib behind it and, when no libref of that name is assigned, hands the value to CAS as the name of the caslib.
- **The custom step** is the same program without those first lines, so it takes the following from the SAS session it runs in.

### Settings that stay yours {#settings-that-stay-yours}

The five programs of the folder `Logging and Monitoring` - `Log-Parser-Code.sas`, `Get-All-Prompts.sas`, `Link-Logs-To-Models.sas`, `Load-Fact-Sheets.sas` and `Build-RAG-Cost-View.sas` - take a setting only where its macro variable is not set when the program starts. Up to release 2.2 the settings were `%let` lines at the top of each file, so a newer file, or an import of the content folder, replaced the values of a site with the defaults. Keep your values in a program of your own that sets them and includes the shipped file from the content folder; the shipped file can then be replaced without a value of yours in it:

```sas
%let _log_path = sasserver:/data/llm/llms.log;
filename shipped filesrvc folderPath='/SAS Agentic AI Accelerator/Logging and Monitoring' filename='Log-Parser-Code.sas';
%include shipped;
```

| --- | --- |
| `Log-Parser-Code.sas` | `_log_path` (`sasserver:/export/pvs/sasdata/data/llm/llms.log`), `_log_target_table_engine` (`CAS`), `_log_target_table_lib` (`Public`), `_log_target_table_name` (`LLM_LOGS`), `_log_append_table` (no default: `1` appends, `0` replaces, and without a value the program stops at a table that holds rows - see [Appending](#appending)), `_log_promote_table` (`1`), `_log_save_table` (`1`) |
| `Get-All-Prompts.sas` | The eleven settings under [Settings](#settings) of the pull |
| `Link-Logs-To-Models.sas` | The twelve settings under [Settings of the Link](#settings-of-the-link) |
| `Load-Fact-Sheets.sas` | `_lfs_path` (`/SAS Agentic AI Accelerator/Data`), `_lfs_caslib` (`Public`) |
| `Build-RAG-Cost-View.sas` | `_rcv_fact_caslib` (`Public`), `_rcv_runs_caslib` (`Public`), `_rcv_runs_tables` (`RAG_HR_RUNS`; several tables separated by commas, with or without blanks around them), `_rcv_out_caslib` (`Public`), `_rcv_out_table` (`RAG_RUN_COST`) |

- **Set means that the macro variable exists.** A variable that is set and empty stays empty. For `_gap_llm_project`, `_gap_embedding_project` and `_gap_decision_project` an empty value leaves the models of that kind out of the catalog.
- **Each program deletes its settings at its end**, with its other macro variables, as before. A program of yours therefore sets them every time, in front of the include. For the parser that includes `_log_append_table`: a second include in one SAS session without its `%let` line is a run without the setting, which stops at a table that holds rows. Measured on 2026-10-13: the first include, with `1`, appended; the second, with the log and the table set again and `_log_append_table` not, wrote its ERROR line and left the 4,654 rows and the saved file as they were.
- **A macro variable of that name that something else left in the SAS session counts as set** - a run of the program that was cancelled before its end, for one. Of the parser such a run leaves `_log_path` without its `sasserver:`, which the next run refuses. Start a new SAS session, or delete the variable with `%symdel`.
- **The two custom steps are not affected.** A step gets every setting from one of its controls, and the program inside a step has none of these lines.
- **Before the first run on a table of an earlier release** - a site that upgrades from 2.2.x and has an `LLM_LOGS` -, read [Appending](#appending): the parser of this release stops at that table until `_log_append_table` is set.

The defaults are the values the `%let` lines had, but for `_log_append_table`, whose line held `0` and which has no default any more: the other 36 settings of the five programs were compared with them in the code. Measured on the test system on 2026-10-12 with the parser, the pull and the link, each from a program like the one above - the settings, then the include of the shipped file from a test content root:

- **The parser** with `_log_path`, `_log_target_table_lib` and `_log_target_table_name` set wrote its table under that name into that CAS library: 1040 rows and 36 columns, promoted and saved, so the four settings that were not set had their defaults. Behind the include none of the seven `_log_` variables was left, and `Public.LLM_LOGS` had the rows and the modified time it had before.
- **The pull** with the CAS library and the five table names set wrote its five tables there - 318 rows and 61 columns, 27 and 32, 17 and 26, 107 and 40, 421 and 21 -, the tables of those names in `Public` were as before, and the eleven `_gap_` variables were gone. With `%let _gap_decision_project = ;` the catalog had 416 rows instead of 421; that the five rows are the decision models was not read.
- **The link** wrote `1040 of 1040 rows ... linked against 421 catalog rows`, and the twelve `_lnk_` variables were gone.
- **`Build-RAG-Cost-View.sas`** ran the same way with one run table, see [The Third Run](#the-third-run). **`Load-Fact-Sheets.sas`** took `_lfs_path` and `_lfs_caslib` from the job `Load-Accelerator-Tables`, which sets both in front of its include ([The tables of the reports](./Setup-Additional-UIs.md#load-accelerator-tables)).

Not run: a program with its defaults, which writes `Public`; and whether the control variables of a step stay behind it in a SAS Studio session, where a code file run next would take them for settings.

### What the Custom Step Takes from the Session

- **A CAS session.** The step asks the `SESSFOUND` function whether the session that the SAS option `SESSREF` names is connected - that is the session its CAS actions run in. When it is connected, the step starts no session, runs in that one and does not end it. When it is not, the step starts a session of its own (`cas llmLogMySess;`) and ends it as its last action. A table that is not promoted belongs to the session that created it, so of a run with a session of its own only what *Promote the table to global scope* or *Save the table* kept is left. The option goes on naming a session that was ended: on the test system `_CASNAME_`, `_SESSREF_` and the option `SESSREF` still named `LLMLOGMYSESS` after such a run, while `cas _all_ list;` listed no session, and SAS wrote `NOTE: The default CAS session LLMLOGMYSESS identified by SAS option SESSREF= was terminated. Use the OPTIONS statement to set the SESSREF= option to an active session.` That is why the step does not go by a name, and why statements of your own that follow the step in the same SAS session and need CAS have to start a session or set `SESSREF` to one.
- **The libref of the output table.** SAS Studio hands the step the output table as a libref and a table name. The step looks the libref up in `dictionary.libnames` and writes to the caslib it finds there. When the libref is not assigned in the session, nothing is found and the name of the libref is handed to CAS as the name of the caslib - which is the caslib you chose only where the two have the same name, as with `CASUSER` and `PUBLIC`. Without the libref the lines SAS Studio adds behind the step also report the output table as not existing: in the job that had a CAS session and no libref, the log held the line `_FLW_ACTION_TABLE_|CASUSER|<table>|0`, where the job with the libref had `|1`. The table was there - promoted, saved and read from a new CAS session with its 174 rows. What SAS Studio does with that line in a flow was not looked at; assign the libref in front of the flow to have it report the table.
- **The caslib `CASUSER`** of the user who runs the step. The parsed rows are uploaded there as `_TEMP_LLM_LOGS`, and the staging table is dropped at the end. In replace mode they are copied from there to `<table>_NEW` in the caslib of the output table; in append mode a DATA step reads them from there. Two more tables of the program can stand there for the time of a run: `_TEMP_LLM_LOGS_SEEN`, the transaction IDs of the table a run appends to, and `_TEMP_LLM_LOGS_SAVED`, the saved file of a table that is not in memory, loaded to count its rows by a run that replaces and by a run of `Log-Parser-Code.sas` without the setting.
- **Two librefs and a work table of its own, in append mode.** To append to a table that exists, the program assigns `_llmtgt` to the caslib of the output table and `_llmsrc` to `CASUSER`, asks CAS for the columns of the existing table (kept in `work._log_target_columns` while it is read, then deleted), writes the existing rows and the new ones to `_TEMP_LLM_LOGS_ALL` in the caslib of the output table with a DATA step, and clears both librefs. The DATA step reads the output table through `_llmtgt`, so the name of the table has to be one a libref can address (32 characters at most). `Log-Parser-Code.sas` does the same. The append ran on the test system on 2026-10-11, see [Appending](#appending).
- **PROC PYTHON with the pandas and swat packages, and what Python needs to reach CAS:** the SAS options `CASHOST` and `CASPORT`, the certificate file named in the environment variable `SSLCALISTLOC` and the token in `SAS_SERVICES_TOKEN`. The Python code connects to the CAS session of the step with them.

The code SAS Studio generates for a flow provides neither a CAS session nor the libref: the code generated on the test system for a flow of the step and its output table held no `cas` and no `libname` statement. The measurements ran that code unchanged as SAS Job Execution jobs, with the output table in `CASUSER`, in three kinds of session. The first had these two lines in front (the name of the session is free):

```SAS
cas mysess;
libname casuser cas caslib='casuser';
```

The second had the `cas` statement alone in front, and the third neither of the two, so that the step started its own session. [What Was Measured](#what-was-measured) has what each of them did. These runs were made with the step as it was earlier on 2026-10-11, which started its own session where the macro variable `_CASNAME_` did not exist. The step now reaches the same two branches through `SESSFOUND`, and with that check it was run again later that day: see [The Session Check with SESSFOUND](#the-session-check-with-sessfound).

## The Columns of LLM_LOGS

One row per scoring request, whatever kind of model answered it. The first twelve columns are the ones the table had before release 2.3.0 - names, order, types and meanings unchanged, the *LLM Usage Report* reads them - and 24 follow behind them.

| Column | What it holds |
|---|---|
| `timestamp`, `model` | When the request arrived, and the model it was sent to: the name of its container |
| `system_prompt`, `user_prompt`, `response` | For an LLM the two prompts and the response; for a decision model the questions as the JSON that was sent, the state and the answers as JSON; missing for an embedding model |
| `temperature`, `top_p`, `top_k`, `max_tokens` | From the options of the request. `max_tokens` is read from `max_tokens`, then `max_completion_tokens`, then `max_length` |
| `prompt_length`, `output_length`, `runtime` | What the score code logged: input tokens, output tokens, seconds. For an embedding model `prompt_length` holds its tokens |
| `kind` | `llm`, `embedding` or `decision`, by the names of the inputs of the request (`document`; `questions` / `state`; `systemPrompt` / `userPrompt`). Missing when the `Request Data:` line can not be read |
| `status_code` | The status of the `Response:` line. Missing when the log holds no such line for the request |
| `failed` | 1 when the log holds an ERROR line for the request, no `Response:` line although its container went on with another request, or a status of 400 and above; otherwise 0. Missing where the log does not decide it: for a request that was still running where the lines of its container end - at the end of the file or of a part of it -, and for a request that ran at the same time as another one where no line of the log says which of them a response belongs to. See [Requests that run at the same time](#requests-that-run-at-the-same-time) |
| `error_text` | The first ERROR line of the request, cut after 500 characters; for the line the container writes for an exception, with the last line of the traceback added. What has the shape of a key is replaced by `REDACTED` |
| `transaction_id` | The id the container gave the request (the `transaction_<id>` logger, the `transaction_id` of `Response Data:`) |
| `request_id` | The `X-Request-Id` header |
| `user_agent` | The kind of client by the `User-Agent` header: `python-requests` (the score code of another model, a job, a script), `browser`, `SAS` or `other`. No version, no address and no Referer is kept, and no other header is read |
| `embedding_mode` | The `Embedding_Mode` option of a call to an embedding model, as sent. Missing when the call sent none; the model then used its default, which the log does not say |
| `project` | The `project` input of a call to an embedding model (the RAG runtime sends `rag`) |
| `input_hash` | The SHA-256 of the text an embedding model was given. The text itself is not kept |
| `answer`, `answer_confidence` | The headline of a decision: the answer to the first question and its confidence. `response` holds all answers |
| `options` | The options as they were sent, with the value of `API_KEY` and of every other option that is a secret by its name (key, secret, password, passwd, pwd, credential, authorization, bearer, cookie, a token that is no number) or by its shape (`sk-...`, `Bearer ...`, a JWT, 20 and more letters and digits in a row that hold both) replaced by `REDACTED`. A name also says so with `pass` or `pw` as one of its words (`my_pass`, `userPass`, `pw` - not `bypass`) and with `passphrase`. Inside a value the user and the password of an address (`scheme://user:password@host`), a header that carries a secret with everything behind its name, and what follows `bearer` or `basic` are replaced as well. The parser does this itself, whether or not the collection redacted the log |
| `rag_collection`, `rag_query_hash` | For an LLM whose user prompt holds the results of a retrieval: the collection and the SHA-256 of the question. The results are the JSON object the RAG runtime writes, with all six of its keys (`query`, `hits`, `graph_context`, `retrieval_mode`, `collection`, `ingestion_run_id`); of several such objects in one prompt the last one counts. The search tries 500 opening braces of a prompt and decodes 2,000,000 characters at most, so a prompt with more braces than that in front of its retrieval gets no collection |
| `model_id`, `caller_model_id`, `caller_project_id`, `caller_kind`, `caller_name`, `experiment_run_id`, `rag_model_id`, `match_method`, `match_candidates` | Written empty by the parser. No line of a log names the model in SAS Model Manager or the prompt, decision template or RAG setup that sent a request; [`Link-Logs-To-Models.sas`](#the-rules-in-their-order) fills them |

A hash is the SHA-256, in lower-case hex, of the UTF-8 bytes of the text with every run of white space made one blank. The three programs hash a text the same way. That is how the question of a retrieval is found again: its `rag_query_hash` is the `input_hash` of the call that embedded it in query mode. `timestamp` is a SAS datetime; `temperature`, `top_p`, `top_k`, `max_tokens`, `prompt_length`, `output_length`, `runtime`, `status_code`, `failed`, `answer_confidence` and `match_candidates` are numbers; every other column is text (VARCHAR).

### A request that failed

A request whose score code raises writes no `Response:` line: the container logs the traceback and `Error occurred in the model scoring function`. Such a request ends at that line and is a row with `failed` = 1, no `status_code` and its error in `error_text`. Before this release it was a row without numbers and response that nothing told apart from a request still running.

### Appending

The rows of the existing table and the rows of the log are written to one new table, which takes the place of the existing one as in replace mode; a table that was promoted is promoted again, whatever the option of the run says. The 36 columns stand in front in their order. A column the existing table lacks - a table of release 2.2 has the first twelve - is added and is missing in its rows; a column the parser does not know stays behind the others, with its type and length, and is missing in the new rows; what the link wrote into existing rows stays. A text column that the existing table holds with a fixed length (CHAR) is read under another name and its values are handed to the VARCHAR column without their trailing blanks, so nothing of the new rows is cut to the old length. A column that is a number in the table and text in the parser, or the other way round, stops the DATA step: the table is left as it is and the log has `The new table could not be created, the table <caslib>.<table> was left as it is.` The saved copy is replaced by the wider table when saving is on, and left as it was when it is off. Appending rewrites the whole table on every run, and other sessions do not see it between the drop and the promote. The parser goes back over a row of the table in one case only - a row that holds neither a response nor an error, see below -, and the new columns of rows an earlier release wrote can not be filled by parsing their log files again: those rows have no `transaction_id`, so with `_log_append_table = 1` their requests are appended a second time (the last entry of the list of 2026-10-13 below), and with `0` the table is replaced by the requests of the one file.

**A request is written once**, in every state of the setting. A request is known by three columns together: its `transaction_id`, its `model` and its `timestamp`, the time of its request line. The container writes the transaction ID into the lines of the request, so the three are the same in every file and every run that holds the request; the `X-Request-Id` header is set outside the container and is not used for it. The ID alone is not taken for the request: the container gives a request its ID unless the client sends one, and a client can send the same ID with every request. Of a request the log itself holds more than once - the lines of a container that were collected twice into one file - one row is written, with `1`, with `0` and without the setting: the first that is complete, and the first of all where none is. A row is **incomplete** when its `failed` is missing: the lines it was read from hold neither a response nor an error for the request, as for a request that was still running where a collection ended. A run with `1` leaves out a request of the log that the table holds already, with one exception: a complete row of the log takes the place of the rows of the table of its request when each of them is incomplete - a request that was cut off where an earlier collection ended and that a later one holds whole. A complete row of the table is never replaced, and no row is replaced in a table without a numeric column `failed`. The row that takes the place is the row of the log: what the link wrote into the row it replaces goes with that row, and the link fills the new one at its next run. A table that lacks one of the three columns is compared with nothing. A request without a `transaction_id` is never taken for another one: it is appended every time it is parsed, and no rule of the program can decide that case - in a file without the lines of the collection script, such a request and another request with the same lines are the same file line for line, and onto a table that holds the row the first has to add nothing and the second a row. In a file of the collection script the line of the script names the pod and the container, but the table keeps neither of a row: the row of such a request of one container and the row of the same request of another container are the same row, so the same file onto the same table has to add nothing in the one case and a row in the other. A column of `LLM_LOGS` for the pod and the container would tell them apart; the table has none. And a request read again and another request of the same container, written in the same second with the same lines, are the same file line for line with the line of the script as well: no column of the table can tell those two apart. The run says its numbers in one line: `NOTE: <r> request(s) were read from the log. <a> were appended to the table <caslib>.<table> and <p> took the place of <x> row(s) of it whose failed was missing: the table held <o> row(s) and holds <n> now. <s> were left out, as another row holds their request: <t> a row of the table, <l> a row of the log.` A run that appends nothing writes nothing: where every request of the log is in the table already and none takes the place of a row, no table is built and the saved file is not written - `NOTE: <r> request(s) were read from the log and none of them was written: the table <caslib>.<table> keeps its rows, and neither the table nor its saved file was written. All were left out, as another row holds their request: <t> a row of the table, <l> a row of the log.` A table that is only its saved file is still loaded for such a run, and promoted where the run promotes. Version 2.9 ran on 2026-10-14 (the last list below); the ERROR line for a table whose rows can not be counted and the drop of a table an append loaded for itself were added after that pass and have not run in SAS: they are followed in the tests of the repository against a CAS library that is made up (`log_parser_table_harness.py`).

The new table only takes the place of the existing one when the DATA steps that wrote it ended with a return code of at most 4, when its rows and the rows that were taken out of it are as many as the existing table held and the log added, and when the two DATA steps that leave out the requests the table holds already ended with 0 or 4. Otherwise the program writes one ERROR line with the return codes and the row counts, drops what the DATA step left and leaves the existing table as it is. The new table gets the label of the existing table, and `Extracted LLM Log Data` - the label of a table the parser writes fresh - where that one had none. Both were added after the runs of 2026-10-11 and ran on 2026-10-12, see the second list below.

### Requests that run at the same time

Only the lines of a transaction (the `transaction_<id>` logger) and the `Response Data:` line name the request they belong to. Every other line is given to a request where the lines around it leave one request it can be the line of, and to none otherwise:

- **The first lines of a request** - the headers, the request data, the two `Randomly generated` lines - are the lines of the request whose request line stands in front of them, as long as no other request line stands in between. A first line that no request is waiting for shows that requests wrote their first lines at the same time: every request since the one whose first lines broke off keeps its request line only.
- **The first line of a transaction** belongs to the one request of its model that has all its first lines and no transaction yet. Where two such requests are waiting, the transaction is given to neither: both rows keep their prompts, `options`, `request_id`, `kind` and `user_agent` and have no `transaction_id`, `status_code`, token counts, run time, response or `error_text`.
- **The lines of the score code** (`prompt_length:`, `output_length:`, `run_time:`, `response:`, `answer:`, `answers:`, its ERROR line) **and the `Response:` line** are the lines of the one transaction that is running. A request is taken as still running when a later line of the log names its transaction. While a second one is running, such a line is given to neither.
- **`failed` is missing** for a request whose response could not be given to it, and for a request that was running where the lines of its container end. It is not 1 for either reason, within the limits at the end of this section.
- **A request that waits.** A request whose first lines are complete and that never gets a transaction stays waiting until its container's part of the file ends. The requests of that model that follow it in the part are then left open, and the NOTE counts them.
- **First lines that broke off where the lines end.** Where the first lines of a request broke off at the request line of another one and no request since has a status or an error when the lines of the container end, what stands behind the break - first lines, a transaction, lines of the score code - can be of the request that broke off as well as of a request since: the requests since keep their request line only, and all are counted in the NOTE. A transaction that starts while no request of its model has all its first lines, behind such a break, shows that the request went on, as a first line does that no request is waiting for. Where a request since has ended, nothing is taken back and the request that broke off is read as failed; a file in which it went on while each request since waited for the next one is the same line for line.
- **One line of each kind.** The score code writes each of its lines once for a request. A second line of a kind for the one request that is taken as running was written by another request: the request keeps none of the values of the score code and is counted. A `Response:` line without its `Response Data:` line behind it is the line of the one running transaction only behind the line of that transaction that follows the score code, or with a status of 400 and above.

The SAS log then has `NOTE: <n> request(s) were running at the same time as another request - of their container, or of another container whose lines are mixed with theirs in the file. ...`, with the number of requests that can have missing values and of those whose `failed` is missing.

**Where a part of the file ends.** The collected file holds the lines of one container after the other, appended pod after pod and collection after collection, and a part can begin and end in the middle of a request. **In a file the collection script of this release wrote**, a part ends at the line the script writes in front of the lines of each container and nowhere else: a request that is running or waiting there ends without a response and without an error, nothing that was read goes on in the next part, and a part that begins with a later line of a transaction follows that transaction to its end and gives it to no request. The time of the lines decides nothing in such a file: a line that is older is a line of its container that was written late, and a transaction that has not ended runs until it ends or its part does, so a line of the score code is given to no request while another transaction runs beside it. The time of collection of such a line decides nothing: every line of that shape ends a part, and in a file the script wrote every line of that shape is a line of the script - it puts a backslash in front of a line of a container that starts like its own, which the parser takes off again behind the first line of the script. What stands in front of that first line - lines an earlier release collected, in a file that is appended to - is read as a file without such lines, and ends at it. **In a file without such lines** - collected before this release, or by a process of your own - the time of the lines goes back where one part ends and the next begins, and that is the one sign of it: a line that is more than one second older than a request that is running or waiting starts the next part. Either way a request that is running where its part or the file ends has neither a response nor an error in the log: the leftover lines of the next part are not added to it, its `failed` is missing, and a NOTE of its own counts such requests - `NOTE: <n> request(s) were running where the lines of their container end - at the end of the file, or at the end of a part of it: where the collection script wrote its line in front of the lines of the next container, or, in a file without such lines, where the time of the lines goes back. The log holds neither a response nor an error for them, and failed is missing for them.` Every request whose `failed` is missing is counted once: in this NOTE where the lines of its container end on it, also where another request ran beside it, and in the NOTE of the requests that ran at the same time where a response could not be given to it. A request whose first lines broke off at the request line of such a request is counted with it. So is, in a file that holds no line of a transaction, a request that had all its first lines and ended at that request line. A request without a `Response:` line whose container went on with another request is `failed` = 1. In a file without the lines of the script a part boundary at which the time does not go back by more than one second is not seen; the end of this section has the further limits of such a file. The line of the script is read since version 2.6 of the step, whose code file read a file with nine such lines on 2026-10-13 ([The Pass of 2026-10-13](#the-pass-of-2026-10-13)). Of what version 2.7 changed here, the backslash and the lines in front of the first line of the script ran in SAS in [The Second Pass of 2026-10-13](#the-second-pass-of-2026-10-13), on staged lines and on a copy of the collected file; the time of collection that decides nothing and which NOTE counts a request are not run in SAS.

**A line that is one second older.** Inside a part a line can be one second older than the line in front of it - it is stamped when it is made and written a moment later - and ends no request. It is the line of its transaction when it names one of this part; a line of the score code or a `Response:` line that is older by a second is given to no request, and the requests that are running then are counted in the NOTE of the requests that ran at the same time. A transaction is over at a request line only when every later line that names it is more than a second older than that request line. That a container writes a line at most one second late is read from the line format and not from a case: a line that is stamped two or more seconds before a request line in front of it is taken for the start of the next part, and the rows around it lose values and are counted in a NOTE. Behind the first line of the collection script none of this depends on how much older a line is: a line that is older is a late line of its container, whatever its time.

**The lines of each container have to stay together in the file**, as `kubectl logs` writes them and the collection script appends them. In a file that mixes the lines of several containers - a time-ordered export of a log store - the score lines of a request that ran while a request of another container was running are given to neither, so its token counts, its run time and its response are missing, and the NOTE counts it. A request line for another model does not end a request that is running.

**A response that holds lines of a log.** While a request is the only one that is running, the lines of its response up to the next line of its transaction are kept as text, also where they start like log lines; a line there that names another transaction of the part - the `Response Data:` line of a request whose `Response:` line came earlier - ends the response. A request line there, with a `Request Headers:` line directly behind it or with no further line that starts like a log line behind it up to the next line of the transaction, is read as a request first and decided at the end of the file. It is a request where it gets a transaction, an error, a status or a response of its own, or where a transaction of its model starts behind it that is given to no request. A request line that gets none of them while a request that came later in its part got its transaction - which a container gives a request at once - is read as a line of the response: the file is read once more with it as text, no row is written for it, the response is whole, and the request keeps its status whatever time the quoted lines carry. A request whose container wrote nothing but its first lines there - no transaction, no error, no status - is the same file line for line, so a NOTE counts the request lines that were read that way: `NOTE: <n> line(s) that read as a request line stand in the response of another request, in front of the next line of its transaction, and got no line of their own - no transaction, no error, no status and no response - while a request that came later in their part got its transaction. They were read as lines of that response, and no row was written for them. A request whose container wrote nothing but its first lines there reads the same.` Where nothing came later in its part, the line can also be a request that came in while the response was written and that the end of the file, or of its part, cut off before its transaction began - two such files are the same line for line, and a test of the repository holds two that are. It is read as a line of the response, no row is written for it, the response is missing, and a NOTE counts such requests: `NOTE: <n> request(s) have no response: a line that reads as a request line stands in their response, in front of the next line of their transaction, and nothing behind it in its part says whether it is a line of the response or a request that came in while the response was written and that the end of the part cut off. It was read as a line of the response.` A request line that scores nothing (`GET`) gets no transaction either way and is read the same way. With one more line that starts like a log line behind the quoted request line, and that is no `Request Headers:` line, the request line is text of the response. A prompt is logged on one line and is always kept as text. This is version 2.6 of the step, and the NOTE that counts the lines read that way version 2.7; neither has run in SAS on a file that is known to hold such a line. Up to version 2.5 one more row was written for a quoted request line, the response ended in front of it, and the runs below were made with that reading.

# The Experiments of Every Kind

`SAS-Viya-Integrations/Logging-Monitoring/Get-All-Prompts.sas` reads what the Prompt Builder keeps in SAS Model Manager and writes it into five CAS tables. Every row of every table carries `modelID` and `projectID`, the SAS Model Manager ids of the model and of its project - the model being the prompt template, the decision template or the RAG setup itself, where its trackers and its manifested score code are stored. The *LLM - Get All Prompts* custom step runs the same program.

The program ran on the test system on 2026-10-11 as it was that day - version 2.0 of the step - and on 2026-10-12 with what that run had led to - version 2.1 of the step: the refusal of a table name that no libref can address, the runs taken from a ledger, the further columns and roles of the catalog, the setup without a collection and the session check of the code file. See [The Pull on SAS Viya](#the-pull-on-sas-viya). What was changed after the second run - version 2.2 of the step: the condition code of a run that wrote an ERROR line, the function its messages go through, the counter of an `optimizationId` that a tracker holds twice - ran there later that day ([the third run](#the-third-run)). Version 2.3 of the step - the counter that passes over the id of another entry - and the settings the code file takes only where they are not set are not run in SAS. The Python of the program runs in the test suite of the repository against a made-up SAS Model Manager, and the SAS code around it is held by the tests as text.

## What It Reads

- The projects with the tag `Prompt-Engineering` - projects of decision templates carry that tag as well. Of every model: `Prompt-Experiment-Tracker.json`, `Prompt-Optimization-Tracker.json` and the manifested score code (the `.py` file with the role `score`).
- The projects with the tag `RAG-Engineering`. A setup saved by the Prompt Builder is read from its `rag-setup.json`. A model registered by the step *RAG - Register Setup* (named `RAG Retrieval - <setup>`) has no such file: it is read from the `pipeline.yaml` the step stores with it, from its properties `collection`, `pipelineVersion`, `configuration` and `ingestionRunId`, and from its training table, which the step sets to `<CAS server>/<caslib>/<prefix>_LEDGER`. Any other model of such a project is left out with a NOTE.
- The projects that hold the definitions of the models that answer a request. The Prompt Builder finds them by id (its options `llmProjectID` and `embeddingProjectID`) and the decision models by the project name `Decision Model Project`; the program finds all three by name - `LLM Model Project`, `Embedding Model Project`, `Decision Model Project`, the names `mdb setup` gives them - so that it needs no id.

Nothing is written to SAS Model Manager, and every listing is read to its last page.

## The Prompts as They Were Sent

The Prompt Builder stores the templates and the variables of a run and sends the prompts with the values filled in. The program fills them in the same way: the variables one after the other in the order they are stored, `{{name}}` with blanks or line ends inside the braces, the value as it is - not trimmed, whatever the type of the variable - and a `{{name}}` of no variable left as typed. A decision run sends its questions as they are stored and gets the variables filled into its state only. The hash is the one of the log table, taken of the whole text before it is cut to the length of its column.

The templates of a manifested model are read from its score code, which is parsed and never run. A manifested model strips every value before it puts it into the prompt, the Prompt Builder does not.

Measured outside of SAS on files saved from the test system: the templates were read from nine manifested score codes, one of them a decision template manifested with 2.2.0 whose score code does not compile and is read statement by statement; the questions and the state template read from the score code of one decision template fit 41 of the 105 requests to its decision model in the collected log of 1040 requests, and the questions of its tracker equalled the questions of those requests character by character. Not compared: a prompt as an experiment run sent it with a logged request.

## Messages and Limits of the Pull

- A model whose file can not be read (not JSON, a failed request), and a project or model that can not be listed, is a WARNING with its name; the model keeps its row without runs and the pull goes on.
- When the projects themselves can not be listed, the program ends with an ERROR and leaves the output tables as they are.
- A definition project that is not found is a WARNING; an empty setting asks for nothing.
- The run ends with one NOTE per output table: `<caslib>.<table> was written with <n> rows and <m> columns.`
- A run table whose name is no SAS name of at most 32 characters, or whose caslib holds a quote, `&`, `%` or `;`, is left out with a WARNING.
- An output table name of more than 32 characters, or one that is no SAS name: `ERROR: The table name <name> of the output <output> has <n> characters. A SAS libref addresses a CAS table by a name of 32 characters at most, nothing was read or written.`, or `... is no SAS name: letters, digits and underscores, and no digit in front. Nothing was read or written.` Nothing is read and no table is touched.
- A RAG setup without a collection: `WARNING: The properties of the model <name> (<id>) could not be read: <reason>. The setup has no collection without them and is left out of the model catalog, where no request could be linked to it. Its row of the RAG setups stays.`, or `WARNING: The RAG setup <name> (<id>) names no collection and is left out of the model catalog, ...`
- A setup whose runs are taken from its ledger: `NOTE: The run table <caslib>.<prefix>_RUNS is not in memory. <n> run(s) were taken from the ledger <caslib>.<prefix>_LEDGER - the runs its rows still name, each from the start its id holds to the latest of its rows.`
- An `optimizationId` that a tracker holds on more than one entry: `WARNING: The file Prompt-Optimization-Tracker.json of the model <name> (<id>) holds the optimizationId <ids> on more than one entry. In the model catalog the rows of a later such entry carry the id with a counter, as in 1#2 - for an entry without an id the counter alone -, so that no two rows of the catalog have the same key. The table of the optimizations holds the entries as the tracker has them.` Where entries without an `optimizationId` repeat, the message says `... holds <n> entries without an optimizationId.` in that place, or both joined by `and`. The WARNING of version 2.2 of the step was seen on 2026-10-12 in [the third run](#the-third-run); its wording as it is here, of version 2.3, is not run in SAS.
- In the step, an output table that is no CAS table: `ERROR: The selected output library does not point to a CASlib, nothing was read or written.` - one line, where the step ended with an ABORT statement up to version 2.1. Not run in SAS.
- A run that wrote an ERROR line and left an output table unwritten sets the condition code of the SAS session (`SYSCC`) to 1012 as its last statement in front of the macro variables it deletes: a table name that is refused, projects that could not be listed or another reason for which SAS Model Manager could not be read, a table that was not written, and in the step an output library that is no CAS library. A WARNING - a model that could not be read, a setup that is left out - leaves the condition code as it was. Measured on 2026-10-12 in [the third run](#the-third-run): the refusal of a table name of 34 characters ended with `SYSCC` 1012 and a failed job. And the step in the code SAS Studio generates for a flow, with its output table in WORK: `ERROR: The selected output library does not point to a CASlib, nothing was read or written.`, no ABORT line, no request to SAS Model Manager, `SYSCC` 1012 and a failed job. The first DATA step behind the step is the flow's own `%_flw_action_end`; it wrote `NOTE: Due to ERROR(s) above, SAS set option OBS=0, enabling syntax check mode.` and did not run, so the log held `_FLW_ACTION_START_` and neither `_FLW_ACTION_TABLE_` nor `_FLW_ACTION_END_` for the node, and `obs` was 0 behind the flow code. A refusal behaves like any SAS error: later DATA steps of the session do not run until `SYSCC` is reset. What SAS Studio shows for such a node was not looked at. A table name that is refused still gives two ERROR lines: its own, and the line that says that the experiments could not be read, which is the line that ends such a run.
- Every message the Python writes is made one text before it is handed to SAS, by the function the parser and the link program carry: in a name from SAS Model Manager a quote shows as a backtick, `%` as `pct`, `&` as `+`, a semicolon as a comma, a comment mark is split by a blank, a tab or a line break is a blank, and parentheses that do not pair up show as brackets - then the ones around the id of the model as well. Up to version 2.1 of the step the function let comment marks, tabs and a parenthesis without its partner through. Measured on 2026-10-12 in [the third run](#the-third-run) with models named `/* open (x) setup`, `/* open setup` and a name with quotes, a semicolon, a percent sign and `%put`: the WARNINGs arrived whole - `/ * open (x) setup (<id>)`, with the parentheses that pair up left as they are, and `` `q` `d` , 50pct pct put x, setup (<id>) `` -, the closing NOTEs followed, `SYSCC` was 0 and `RAG_SETUPS` held the names unchanged. SAS Model Manager refused a model name with a parenthesis without its partner (HTTP 400), so that such a parenthesis shows as a bracket was not measured.
- The requests are made one after the other: one per project and one or more per model.

# Linking the Log to the Models

`SAS-Viya-Integrations/Logging-Monitoring/Link-Logs-To-Models.sas` fills the nine link columns of the log table. It reads the log table, `MODEL_CATALOG` and, when it is there, `RAG_RUNS`, links the rows without a `match_method` and, where it linked a row, puts the table back, promoted and saved. A run that links no row leaves the table as it is.

The program ran on the test system on 2026-10-11 and on 2026-10-12, each time as it was that day, see [The Chain on SAS Viya](#the-chain-on-sas-viya). The first run linked the 1040 rows of the collected log, and its summary broke the SAS log. The program was changed - its messages, the rule for an experiment run, the window of a retrieval query, the calls of optimizations and judges, what it does to a table it links no row of -, and the second run measured the rules as this section has them. What was changed after the second run - the condition code of a run that wrote an ERROR line and no table, and what the program does with a log table that it loaded from its saved file and linked no row of - ran in [the third run](#the-third-run) later that day. The link program has no custom step. The parser and the link program must not run on one table at the same time. Since the third run the program takes its settings only where they are not set ([Settings that stay yours](#settings-that-stay-yours)), which is not run in SAS.

## Settings of the Link

| Macro variable | Default | Meaning |
| --- | --- | --- |
| `_lnk_log_caslib`, `_lnk_log_table` | `Public`, `LLM_LOGS` | The log table. Its link columns are filled in place |
| `_lnk_catalog_caslib`, `_lnk_catalog_table` | `Public`, `MODEL_CATALOG` | The catalog of Get-All-Prompts.sas |
| `_lnk_runs_caslib`, `_lnk_runs_table` | `Public`, `RAG_RUNS` | The ingestion runs. Without the table no embedding row is linked to an ingestion run; the program says so in a NOTE |
| `_lnk_redo_all` | `0` | `0` links the rows without a `match_method` and leaves every other row as it is. `1` links all rows again |
| `_lnk_min_literal` | `20` | The characters of fixed text (whitespace not counted) a template needs to take part, an experiment run in its prompts, and a call of an optimization or of a judge in the texts the catalog holds of it |
| `_lnk_utc_offset` | `0` | The hours the clock of the containers is ahead of UTC. The ingestion runs and the windows of the optimizations are recorded in UTC |
| `_lnk_query_window` | `300` | The seconds within which the prompt that carries a retrieval follows the embedding of its query. A query embedding without such a prompt is not linked |
| `_lnk_promote_table`, `_lnk_save_table` | `1`, `1` | They decide for a table that is not promoted and for one that has no saved file. A table that is promoted is promoted again and a table that has a saved file is saved again, whatever the two say - as the parser does it when it appends |

A table that was saved but is not in memory (after a restart of the CAS server) is loaded from its `.sashdat` file first; this holds for all three tables. A log table that was loaded and of which the run then links no row is promoted as `_lnk_promote_table` says, and its saved file is left as it is (see [What the Program Does to the Table](#what-the-program-does-to-the-table)); the catalog and the runs table that were loaded stay tables of the session of the program. The program needs PROC PYTHON with the pandas and swat packages and the caslib `CASUSER`, as the parser does. A setting that has to be a number and is none gives a WARNING, and its default is taken. The program starts a CAS session (`cas lnkMySess;`) only when the SAS session has none that is connected, and ends only that one.

## The Rules, in Their Order

No request, header or log line names the caller. Every link is therefore made by content, and `match_method` says which rule decided.

1. **The model that answered** (`model_id`): the catalog row with the role `llm`, `embedding` or `decision_model` whose name is the name of the container (`model`). When two models of that role have the name, `model_id` stays empty and a NOTE names the two.
2. **`experiment run`** (LLM and decision rows): the system and the user prompt of the row are the prompts of an experiment run as the Builder sent them (for a decision: the questions and the state), the run was sent to the model of the row, the request was not sent by the score code or a SAS session (`user_agent` is not `python-requests` or `SAS`) - the Builder page sends its runs from a browser -, and the `runtime` of the row is the `run_time` the catalog holds for that run and model, compared with three decimals. The prompts are compared by the hashes the catalog holds of them, so a prompt that is longer than a column of the catalog is still found. A run is given to one row: the earliest request gets it, and a run that a row of an earlier link holds is taken. A request with the prompts of a run whose run time is the one of no run is another request with the same prompts: the rules below say who sent it, and it gets no `experiment_run_id`. Where the catalog holds no `run_time` for the runs with these prompts - a catalog written before the column existed -, the row gets the newest of them, `match_candidates` is their number, and a NOTE counts such rows.
3. **`questions and state`**, **`questions`** (decision rows): the questions of the row are the questions of a decision template. Questions are compared as JSON, so the order of the keys and the whitespace do not matter; a text that is no JSON is compared as text. When the state of the row fits a state template that has fixed text, the method is `questions and state`, otherwise `questions`.
4. **`template`** (LLM rows): the system prompt and the user prompt of the row fit the templates of a prompt. Every `{{variable}}` stands for any text, also for none and for several lines; the fixed text has to be there in its order, from the first character to the last, whitespace squeezed. The templates of earlier experiment runs of a prompt count as its templates.
5. **`optimization`**, then **`judge`** (LLM rows): the request is a call the Prompt Builder made *for* a prompt and not with it - a call of a prompt optimization, or the call a judge gets to rank the answers of a run. A catalog row of that role links a request when three things hold: the request holds every text of the row (`resolved_system_prompt`, `resolved_user_prompt`) in its system or in its user prompt, at least one of them as a part of the prompt and not as the whole of it; it went to the model in `target_model`; and, where the row has `window_start` and `window_end`, it was sent inside that window (whole seconds, `_lnk_utc_offset` applies). The texts need `_lnk_min_literal` characters together. `caller_model_id` is the prompt the call was made for and `caller_kind` what the catalog says that caller is. A judge call gets the `experiment_run_id` of the run that was judged when exactly one run remains; two judged runs with the same prompts leave it empty. An optimization is asked first: a call of a judge that was made while an optimization of the same prompt was running, to a model that optimization called and with the system prompt it started from, is an `optimization` row.
6. **The RAG setup of a prompt** (LLM rows, column `rag_model_id`, does not change `match_method`): the prompt carries the results of a retrieval, and the setup is the one the catalog has for its collection. So a call of a prompt that is fed by a retrieval is linked to its prompt and to the setup. Of several retrievals in one prompt the last one counts, as for the parser.
7. **`retrieval query`** (embedding rows in query mode): the hash of the embedded text is the hash of the query of a retrieval that an LLM row of the table carries, and that LLM row follows the embedding within `_lnk_query_window` seconds. The nearest such row decides: the embedding row gets the setup of the collection it names. The same question is embedded many times and for more than one collection, so a prompt that came before the embedding, or long after it, says nothing about this request. Two prompts of two collections in the same second are `ambiguous`. A setup of which the catalog names another embedding model than the model of the row is not taken.
8. **`ingestion run`** (embedding rows in document mode whose `project` input is `rag`, as the RAG runtime sends it, or empty): the request lies between `started_at` and `finished_at` of exactly one run of `RAG_RUNS` whose `embed_model` is the model of the row. A run without a start or an end, or whose end lies before its start, takes no part, and a NOTE counts such runs.

Between several callers that fit, the one with the most fixed text wins and `match_candidates` is their number. A caller of which the catalog only names other target models is taken when no other caller fits. Two callers with the same amount of fixed text, two collections for one query or two overlapping ingestion runs give `match_method = ambiguous` and empty caller columns. A row that fits nothing gets `none` and `match_candidates = 0`; its `model_id` is filled all the same.

Where two models hold one collection - a setup that was saved in the Prompt Builder and registered with the step *RAG - Register Setup* - the model the Builder saved is taken, for `rag_model_id`, for a retrieval query and for an ingestion run, when the other model is its registration: the catalog marks it `step`, the two name no different embedding models, and it is named `RAG Retrieval - <name of the setup>` or holds an ingestion run of `RAG_RUNS` that the setup holds as well. Another model with the same collection name, two setups of the Builder with one collection, or two models of the step stay open: `rag_model_id` is empty and the embedding rows are `ambiguous`, unless the retrieval names an ingestion run that `RAG_RUNS` holds for one of them only.

A row whose content can not be compared - questions that are nested deeper than Python reads JSON - gets `none`, a catalog row that can not be read takes no part, and a WARNING names both. The rows around them are linked. Measured on 2026-10-12: a decision row whose questions were 30000 opening brackets gave `WARNING: 1 row(s) could not be compared with the catalog - RecursionError - and got match_method none.`, and every other row was linked as before. With 2000 opening brackets the Python of that system (3.12.12) raised no such error: the row got `none` without the WARNING, as questions that fit no template do.

**The limits of the rules `optimization` and `judge`.** Both link by containment: the texts of the catalog row have to stand in the prompts of the request, with `_lnk_min_literal` characters together as the only limit of size, without a word boundary, and for a `judge` row without a window of time. A request that is no call of the Prompt Builder is therefore linked when it holds those texts and no rule above fits it. Outside of SAS, on made-up rows: a request to the target model inside the window of an optimization that asks about the prompt (`Is this a good system prompt? <the system prompt> Tell me.`) is an `optimization` row, and so is a variant of the prompt - the system prompt and one more sentence - that is sent inside the window; a request to the judge model that quotes both prompts of a judged run is a `judge` row of that run, months later as well; and `Claim: hail` is found inside `Claim: hailstorm`. On the collected log the 49 `optimization` and 13 `judge` rows of 2026-10-12 were the calls of the Prompt Builder and none more: checked outside of SAS, the whole text of the catalog row stood in the system prompt of all 49, inside the window, and both prompts of the judged run in the user prompt of all 13, and no other caller and no other run held them. Such a row carries a `rag_model_id` when the prompt it quotes held the results of a retrieval, although the call made no retrieval itself: on that log 62 of the 193 LLM rows with the setup of one collection are such calls, and the summary line and the second statement of the example under [How the Tables Join](#how-the-tables-join) count them among the prompts of the setup.

**The window of a retrieval query on the collected log.** Of the 290 query embeddings of the log of 1040 requests, 124 were followed by the prompt with their question within one second, 13 more within 33 seconds and one after 178 seconds. 83 were followed only after 6.8 to 23.8 minutes, 18 only had such prompts before them, and 51 had none. The 83 and the one of 178 seconds are 84 query embeddings of one collection that were sent before the first prompt of that collection - retrievals that were tested before a prompt used them. The default of 300 seconds links the 138, the one of 178 seconds among them; with `_lnk_query_window = 1800` it is 221. Both numbers are what the program linked on the test system on 2026-10-12.

## What Cannot Be Linked, and Why

- **No caller id is logged.** A request carries its inputs and nothing about who built them. A direct call of a model (a script, a health check, the test of a deployment) has no caller in SAS Model Manager at all.
- **Two templates with the same text.** A copy of a prompt, or two decision templates with the same questions and no state that tells them apart, fit the same requests: `ambiguous`.
- **A template that is one variable.** `{{input}}` fits everything, so it says nothing. A template with less than 20 characters of fixed text takes no part; the program counts such callers in a NOTE.
- **The Builder's test calls against a template that was changed afterwards.** The catalog holds the saved template and the templates of the runs that were kept. A test call that was not kept as a run and was made with a text that is no longer the template fits nothing.
- **The health check of an optimization, and a call whose instructions the optimizer rewrote.** The calls of a prompt optimization and of a judge are linked through a text of the prompt they hold. The health check an optimization sends first (`You are a health check.`) holds none, and neither does a call of an optimizer that has replaced the instructions by a proposal of its own.
- **A further request with the prompts of an experiment run** - the run sent again from the Builder page without being kept - is linked to the prompt by its template or its questions, and to no run.
- **A retrieval that never reached an LLM prompt** (the test of a retrieval, a flow that only retrieves), or whose prompt does not follow within `_lnk_query_window` seconds: its query embedding has no LLM row to be linked through.
- **Embedding calls outside of an ingestion run**, a run without `finished_at`, a setup with neither a run table nor a ledger in memory when `RAG_RUNS` was written, and the earlier ingestions of a setup whose run table is not in memory - a setup of the Prompt Builder whose job definition holds the program from before release 2.3.0, or whose run history is switched off: its ledger names the newest run only.
- **The LLM calls of an enrichment** during an ingestion: their prompt is in no catalog.
- **A published model that sends the prompts of an experiment run again** is linked to the prompt, not to the run.
- **A template longer than 32,767 bytes** is cut in the catalog and fits no request.
- **Rows of an earlier parser** have no kind, no hashes and no collection. The kind is taken from the role of the model that answered, where the catalog holds a model of that name; a row whose model the catalog does not hold is counted in a NOTE of its own, `<n> rows of no known kind`. Measured on 2026-10-13 on a copy of a table of release 2.2 after the append of a collected log: of its 3,630 earlier rows none got a caller, 3,434 got no `model_id` - their model names are not in the catalog - and all 3,630 carried the `match_method` `none` afterwards, so a later link leaves them out unless `_lnk_redo_all` is 1.

| From | To | Meaning |
| --- | --- | --- |
| `LLM_LOGS.model_id` | `MODEL_CATALOG.modelID` (roles `llm`, `embedding`, `decision_model`) | The model that answered |
| `LLM_LOGS.caller_model_id` | `PROMPT_EXPERIMENTS.modelID` | The prompt or decision template (`caller_kind` = `prompt` or `decision`) |
| `LLM_LOGS.caller_model_id`, `experiment_run_id`, `model` | `PROMPT_EXPERIMENTS.modelID`, `runID`, `model` | The row of the experiment run (`match_method` = `experiment run`). `experiment_run_id` is text and `runID` a number, and a run id counts inside one model only. A judge call (`match_method` = `judge`) carries the id of the run it judged, and its `model` is the judge |
| `LLM_LOGS.caller_model_id` | `PROMPT_OPTIMIZATIONS.modelID` | The optimizations of that prompt. A call of an optimization (`match_method` = `optimization`) carries no id of the optimization: it is the one with `startedAt <= timestamp <= finishedAt` |
| `LLM_LOGS.caller_model_id` | `RAG_SETUPS.modelID` | The setup of an embedding row (`caller_kind` = `rag`) |
| `LLM_LOGS.rag_model_id` | `RAG_SETUPS.modelID` | The setup whose retrieval an LLM prompt carried |
| `RAG_SETUPS.modelID` | `RAG_RUNS.modelID` | The ingestion runs of a setup |
| `LLM_LOGS.model_id`, `caller_model_id`, `rag_model_id` | `MODEL_CATALOG.modelID` | The name and the project of any of the three |

`MODEL_CATALOG` has one row per model and pattern, so a model is there several times: join to it through a distinct list of `modelID`. `MODEL_CATALOG.target_model`, `PROMPT_EXPERIMENTS.model` and `RAG_SETUPS.embedding_model` are names of containers and equal `LLM_LOGS.model`.

`experiment_run_id` is the place of the run in the tracker of the prompt, not a lasting id: when a run is deleted in the Prompt Builder, the runs behind it are numbered again, so after a new pull a row that was linked earlier can name another run. The link program counts such rows in a WARNING - rows whose run id the catalog no longer has, and rows whose run has another run time than the request - and `%let _lnk_redo_all = 1;` links all rows again.

An example - what each prompt, decision template and RAG setup asked of the models, and the calls of the Builder's experiment runs beside their rows of `PROMPT_EXPERIMENTS`. The three statements ran on the test system on 2026-10-11 and on 2026-10-12 on the tables of the chain, with only the table names changed, without an ERROR or a WARNING and in 0.3 seconds; `input(l.experiment_run_id, best32.)` read the VARCHAR column:

```SAS
libname public cas caslib='Public';

proc sql;
    /* Requests, failures, tokens and seconds per caller and answering model */
    create table work.usage_by_caller as
    select l.caller_kind, l.caller_name, l.caller_model_id, l.model,
           count(*) as requests,
           sum(l.failed) as failed_requests,
           sum(l.prompt_length) as input_tokens,
           sum(l.output_length) as output_tokens,
           sum(l.runtime) as seconds
    from public.llm_logs as l
    where l.caller_model_id is not missing
    group by l.caller_kind, l.caller_name, l.caller_model_id, l.model;

    /* The prompts that were fed by a retrieval, per RAG setup */
    create table work.prompts_by_rag_setup as
    select s.name as rag_setup, s.collection, l.caller_name as prompt, count(*) as requests
    from public.llm_logs as l
         inner join public.rag_setups as s on s.modelID = l.rag_model_id
    group by s.name, s.collection, l.caller_name;

    /* The logged request of an experiment run beside what the tracker kept of it */
    create table work.experiment_run_requests as
    select e.name, e.runID, e.model, e.best_prompt, e.run_time as tracked_seconds,
           l.timestamp, l.runtime as logged_seconds, l.status_code
    from public.llm_logs as l
         inner join public.prompt_experiments as e
            on  e.modelID = l.caller_model_id
            and e.runID   = input(l.experiment_run_id, best32.)
            and e.model   = l.model
    where l.match_method = 'experiment run';
quit;
```

## What the Program Does to the Table

The log table has no key, and its prompts and every column a site added must not be rewritten. The program therefore numbers the rows in a copy in the caslib `CASUSER`, reads what it compares into Python (the prompts only of the rows it links), uploads the nine link columns with the row number, merges them back by that number into `<table>_NEW` beside the log table, checks that this table has as many rows as the log table, restores the order of the columns, gives the new table the label of the log table, and replaces the log table the way the parser does: dropped, renamed, promoted, saved. While it runs it needs room for two more copies of the table. A table that grew while it was linked - the parser appended to it - is left as it is, with an ERROR line; run the two one after the other.

A run that links no row - every row has a `match_method` - builds no new table: the log table, its promotion and its saved file stay as they are, and the SAS log has `NOTE: 0 of <n> rows of <caslib>.<table> were linked, as every row has a match_method. The table was left as it is. With _lnk_redo_all = 1 all rows are linked again.`

A log table that was not in memory, and that the program loaded from its saved file, is put in place by such a run as it was loaded: it is promoted where `_lnk_promote_table` is 1, the saved file is not written again, and one line says so - `NOTE: The table <caslib>.<table> was not in memory. It was loaded from its saved file and promoted as it was loaded, the saved file was left as it is.` With `_lnk_promote_table = 0` the line is `NOTE: ... It was loaded from its saved file and not promoted, as _lnk_promote_table is not 1, so it is a table of this CAS session and gone when the session ends. The saved file was left as it is.`, and where the promotion does not take, `WARNING: ... could not be promoted, so it is a table of this CAS session and gone when the session ends. ...` Before, the loaded table was a table of the session of the program and ended with it. Measured on 2026-10-12 in [the third run](#the-third-run), with the table dropped from memory and its saved file left: with `_lnk_promote_table` 1 the first NOTE, and the next job found the table in memory, promoted, with its 1040 rows and 36 columns and the saved file as it was; with 0 the second NOTE, and the next job found no table and the file as it was. The WARNING was not provoked.

Every message of the program is made one text before it is handed to SAS, where a line for the log is a statement on its way: in a message a quote shows as a backtick, `%` as `pct`, `&` as `+` and a semicolon as a comma, a comment mark is split by a blank, a line break or a tab is a blank, parentheses that do not pair up show as brackets, and a message of more than 900 characters ends in three dots. Measured on 2026-10-12 with a catalog in which two models carried one name with a quote, a semicolon and `%put ERROR: x;`: the NOTE about the two models showed the quote as a backtick and the `%` as `pct`, and no ERROR followed. The parser and the pull carry the same function since version 2.4 and 2.2 of their steps; with it their messages arrived as text in [the third run](#the-third-run).

A log table without the link columns was written by an earlier parser and is refused with one ERROR line that names the parser. Without the catalog there is one ERROR line that names Get-All-Prompts.sas. In both cases the table is left as it is. Where CAS refuses to list the saved files of a CAS library the program reads - for a table of the link that is not in memory, or for the saved file of the log table where `_lnk_save_table` is not `1` - the run links nothing and writes nothing: `ERROR: CAS refused to list the saved files of a CAS library the program reads, so it is not known whether a table that is not in memory is there as a saved file or whether the log table has one. Nothing was linked and the tables were left as they are.` Up to this release such a listing was taken for a library without the file. A run that wrote an ERROR line and no table - a log table or a catalog that was not found, a listing of saved files that CAS refused, a table the program refused, rows that could not be linked, a new table that could not be put in place - sets the condition code of the SAS session (`SYSCC`) to 1012 as its last statement; a WARNING, a NOTE and a run with nothing to link leave the condition code as it was. In the second run, before the statement existed, the refusal of a table of twelve columns ended with `SYSCC` 0 and a completed job. In [the third run](#the-third-run) the same refusal and the run without a catalog ended with `SYSCC` 1012 and a failed job, and a second run with nothing to link and a run with a `_lnk_query_window` that is no number - a WARNING - as completed with `SYSCC` 0. As for the parser, the first DATA step behind a refused run does not run until `SYSCC` is reset ([Reading the Job Log](#reading-the-job-log)).

The SAS log ends with one NOTE per kind of row, for the whole table, and with a fourth one where the table holds rows whose kind is not known - rows of an earlier parser whose model is not in the catalog: `NOTE: 3434 rows of no known kind: 0 linked to a model, caller by ambiguous 0, none 3434.` (2026-10-13). The three lines of a table without such rows:

## The Chain on SAS Viya

The three programs ran one after the other on the test system three times, each time as they were then: on 2026-10-11, on 2026-10-12 with the changes the first run had led to, and later that day with the changes the second run had led to. This section has the first run, then for each defect of the first run what the changed program did in the second, then [the second run](#the-second-run) as a whole with what was changed after it, and then [the third run](#the-third-run), which measured those changes. What was changed after the third run is the part that is not run in SAS.

On 2026-10-11 the chain was 23 SAS Job Execution jobs of the *SAS Studio compute context*, all of them on tables of their own in `CASUSER`, on a redacted collection of 1040 requests. The CAS server of that system runs without workers, and its PROC PYTHON is Python 3.12 with pandas 2.3.3, swat 1.18.1 and requests 2.34.2. The job logs hold the build stamp of the system (`V.04.00M0P09082026`), not the name of its release. What the parse did is under [The parser of this release on SAS Viya](#the-parser-of-this-release-on-sas-viya) and [Appending](#appending), what the pull did under [The Pull on SAS Viya](#the-pull-on-sas-viya). The link and the joins:

**What held**

The table kept its 36 columns in their order with their types and labels - only the lengths of the eight text link columns changed -, its rows in their order and the other 27 columns unchanged in every row. ## Making the Links Exact

The links are made by content because nothing else is logged. What would make them exact is a caller id that the manifested models send themselves: a key in `options` - the SAS Model Manager id of the prompt or decision template - that the generated score code of the answering model ignores and the container logs with the request, and, for a retrieval, the id of the setup or its collection in the `project` input of the embedding call, which the RAG runtime sends as the constant `rag` today. The parser would read both from the `Request Data:` line and no rule above would be needed for such a request. It is not built: it needs a change of the Prompt Builder and of the RAG runtime, and a new manifest of every model - a prompt, a decision template or a retrieval model that was manifested before sends no id.

# The LLM Usage Report

The LLM Usage Report is a ready-made SAS Visual Analytics report. It is part of
the transfer package of the content folder and sits in **SAS Content > SAS
Agentic AI Accelerator > Logging and Monitoring** - see
[Install or upgrade with the transfer package](./Setup-Additional-UIs.md#the-transfer-package).
It is the **recommended template** for monitoring LLM
usage and prompt experimentation in your environment — import it and use it as-is,
or as the starting point for your own dashboards. Up to release 2.2 the report
was a package of its own, `LLM Usage Report.json`; that package carried a share
and an authorization rule that named two users, and the one package carries
neither.

## Prerequisites — the tables it reads

The report builds on four CAS tables, **all expected in the `Public` caslib by
default**. Load them (promoted and saved) before or after importing so the report
has data to bind to:

| Table | Produced by |
|---|---|
| `LLM_LOGS` | Parsing the collected container logs — `Log-Parser-Code.sas` or the *LLM - Log Parser* SAS Studio custom step |
| `LLM_FACT_SHEET` / `EMBEDDING_FACT_SHEET` | `mdb load-facts` (or `Load-Fact-Sheets.sas`) — see [Model Definition Builder](./Model-Definition-Builder.md) |
| `PROMPT_EXPERIMENTS` | `Get-All-Prompts.sas` or the *LLM - Get All Prompts* SAS Studio custom step - see [The Experiments of Every Kind](#what-it-reads) |

The report reads the twelve columns `LLM_LOGS` had before release 2.3.0 and the columns `PROMPT_EXPERIMENTS` had before it. `LLM_LOGS` keeps those twelve with their names, order and types. `PROMPT_EXPERIMENTS` keeps its columns with their names and types, and in the order they had among themselves, but not at their places: the pull writes new columns in between. Measured on 2026-10-13 against the table the test system had, 212 rows and 38 columns: the table as pulled had 312 rows and 61 columns, and the 38 stood in their order, from the fifteenth on at other positions. The columns this release adds, and the four further tables of the pull, are for reports of your own.

Measured on the test system on 2026-10-13, on a copy of the `LLM_LOGS` of release 2.2 that a collected log of 1,024 requests was appended to, with the report's own join - `LLM_LOGS.model` to `LLM_FACT_SHEET.model_id`, an inner join - run as a query; the report itself was not opened on the copy:

- **The totals of the earlier rows were the same** before and after the append: the join and its 15 totals for the 3,630 rows.
- **The rows of embedding and decision models do not reach the report.** Their models are not in `LLM_FACT_SHEET`, so the join drops them: of the 1,024 new rows the 242 of LLMs were left. All 242 count as calls, also the 83 that failed and carry no token count and no run time.
- **`model_id` is a column of both tables of the join** once `LLM_LOGS` has its 36 columns: `LLM_LOGS.model_id`, which the link fills, and `LLM_FACT_SHEET.model_id`.
- **The detail table lists a request only where its `prompt_length` lies between 1 and 8946.** That range is a fixed filter of the report - of the one on the test system and of the report in the package of this repository -, so a request with more input tokens, or without a token count, is not listed there: 83 of the 242 were not.
- **With its defaults the pull replaces `Public.PROMPT_EXPERIMENTS`** and creates `PROMPT_OPTIMIZATIONS`, `RAG_SETUPS`, `RAG_RUNS` and `MODEL_CATALOG` beside it; on that day the run wrote to tables in `CASUSER`.
- **A job that gets no compute session writes nothing.** One of 18 jobs of that day ended as failed with `The SAS Compute server was unable to create a session for the submitted request.` Its log was empty and the tables were as before; it was submitted again and ran.

## Import the report

`mdb builders-import` imports the content folder, and the report with it:

```bash
mdb builders-import                              # the tables of the report stay bound to Public
mdb builders-import --report-caslib MyLib        # ... or are pointed at the tables of the same name in MyLib
```

See [First install and upgrade](./Setup-Additional-UIs.md#first-install-and-upgrade)
for what the command does, and
[Importing without `mdb`](./Setup-Additional-UIs.md#importing-without-mdb) for
SAS Environment Manager and the `sas-viya` CLI. After the import the report is
under **SAS Content > SAS Agentic AI Accelerator > Logging and Monitoring > LLM
Usage Report**. The two fact sheets are loaded by `mdb load-facts`, or by the
job `Data/Load-Accelerator-Tables` of the content folder
([The tables of the reports](./Setup-Additional-UIs.md#load-accelerator-tables)).

## Change the CAS library (default: `Public`)

The report binds each of its four tables to
`server=cas-shared-default;library=Public`. If your tables live in a **different
CAS library**, repoint them one of two ways:

- **`mdb builders-import --report-caslib <library>`** points `LLM_LOGS`,
  `LLM_FACT_SHEET`, `EMBEDDING_FACT_SHEET` and `PROMPT_EXPERIMENTS` at the tables
  of the same name in that library, through the import mapping of the transfer
  service. The file is not edited. The release table of the Prompt Builder
  report follows `--caslib` / `SAS_CAS_LIBRARY`. The option has not run against
  SAS Viya.

- **SAS Environment Manager / SAS Visual Analytics** — import the package as-is,
  then open **LLM Usage Report** in SAS Visual Analytics and, in the **Data** pane,
  use **Edit → Change data source** on each of the four tables to point to the same
  table in your library.
