## Configurations for SCR deployment

For the creation of the SAS Container Runtime publishing destination it is recommended to use the [SAS Viya CLI](https://go.documentation.sas.com/doc/en/sasadmincdc/default/calcli/titlepage.htm). The command detailed below is used to create a publishing destination that is using a Azure Container Registry.

### Kubernetes Deployment

`mdb deploy <model_id> --registry <registry> --host <ingress-host>` renders a ready-to-apply manifest from the templates in the *SCR-LLM-Deployment-YAML* folder (see [Model Definition Builder](./Model-Definition-Builder.md#deployment-yaml-and-ci-pipelines)): `deploy-modelName-template.yaml` for hosted-API models, `deploy-modelName-env-template.yaml` for Azure definitions that read their resource, key and deployment from the container environment, and `deploy-modelName-PV-template.yaml` plus `llm-weights-pvc-template.yaml` / `stage-weights-job-template.yaml` for self-hosted models with staged weights ([Serving Open-Weight Models](./Serving-Open-Weight-Models.md)). The templates were written for Azure Kubernetes Service (spot-node affinity and tolerations) and are easily adapted. The following assumptions are made:

-   Namespace called *llm* in which the SCR containers will be deployed - every object of a template names it; `mdb deploy --namespace <name>` renders the Deployment, Service and Ingress into another one. `llm-weights-pvc-template.yaml` and `stage-weights-job-template.yaml` are not rendered by `mdb deploy` and keep *llm*: for another namespace change their `namespace:` lines before you apply them (the command reminds you when it renders the PV variant).
-   The Ingress serves its host with the TLS secret *llm-tls-certs*; `mdb deploy --tls-secret <name>` names another one. The Secret has to exist in the namespace of the Ingress - an Ingress reads no Secret of another namespace -, so the certificate Secret of your SAS Viya ingress, which lives in the namespace of SAS Viya, is copied there first ([how](./Model-Definition-Builder.md#deployment-yaml-and-ci-pipelines)).
-   A definition that takes its provider key from the container's environment ([`--auth env`](./Model-Definition-Builder.md#auth-env)) gets that variable from a Kubernetes Secret: `mdb deploy` adds a `secretKeyRef` to the Deployment (Secret *llm-api-keys*, or `--key-secret <name>`, one entry per variable name) and prints the `kubectl create secret generic` command for it, with the variable names only. Create the Secret in the namespace before the pod starts; a missing Secret or entry keeps the pod in `CreateContainerConfigError`. To add a key to a Secret that exists, use the `kubectl patch` line the command prints - `kubectl apply` of a Secret that lists only this run's variables removes the others. Any other hosted definition takes its key per call, from the caller.
-   The Ingress has no authentication. A container that holds its provider key (`--auth env`, and `azure-foundry-env`) answers anyone who can reach *host/llm/model_name* with the organisation's key, without a credential-domain check: restrict who can reach the path - an allowlist of source addresses on the Ingress (`nginx.ingress.kubernetes.io/whitelist-source-range` with ingress-nginx), a NetworkPolicy, or no Ingress where only callers inside the cluster use the model - and set a spending limit for the key at the provider.
-   Each model container requests 1000m CPU and 4000Mi of memory and has no limit, and the pods go to nodes labelled and tainted `app=llm` (spot nodes preferred) - that is why we recommend having a separate node pool for this workload; in non production environments it is recommended to use a spot-instance with a lot of available CPU and RAM, e.g. Standard_D64s_v5. `mdb deploy --requests CPU,MEMORY`, `--limit-memory` and `--pull-policy` change the model container, `--node <name>` pins the pods to one node, and `--node-class <class>` tolerates the SAS node taint `workload.sas.com/class=<class>:NoSchedule` in place of the `app=llm` affinity, so the models can share a node pool of SAS Viya ([placing the pods](./Model-Definition-Builder.md#ingress-contour)). `--requests` and `--limit-memory` apply to every model of one render: small values suit models that call a provider's API, not those that run their own weights (the Hugging Face transformers LLMs, the sentence-transformers embedding models, `von_1_2`) - render those in a second run with larger values and keep the router of the `--all` run.
-   The URL endpoint schema looks like this *host/llm/model_name* here the container will be reached, that means the full address for a container is *host/llm/model_name/model_name*.
-   The Ingress of each model is one for the NGINX Ingress controller: it rewrites *host/llm/model_name/model_name* to */model_name*, the only path the Python SCR runtime answers. On a cluster whose ingress controller is Contour, as on current SAS Viya deployments, such an Ingress reaches no model. Render with `mdb deploy --all --ingress contour`: the models get no Ingress, and `llm-router.yaml` adds one NGINX router (`nginx-unprivileged`, resolving each model's Service through the cluster DNS) behind one Contour Ingress for */llm*, with the same URLs - see [A cluster with Contour](./Model-Definition-Builder.md#ingress-contour).
-   The templates set `SAS_SCR_LOG_LEVEL_SCR_IO` to `TRACE`, which is what the [log parser](./Logging-&-Monitoring.md) reads - at that level every request and response, prompts included, is written to the container's standard output. Lower it if your logs must not carry prompt text, and accept that the usage report then has no token counts.
-   A republished image with the same `:latest` tag is only picked up when the pod is recreated. On a node pool without spare CPU a `kubectl rollout restart` can deadlock (the new pod cannot schedule while the old one holds the resources); scaling the deployment to 0 and back to 1 always works.

### Azure Container Apps/Instances

If you want to deploy the LLM containers as Azure Container Apps or Azure Container Instances than please make sure that when you follow the [Deploying the Builder UIs](./Setup-Additional-UIs.md) you set the object's *deploymentType* to *aca* (the value recorded in your `llm-prompt-builder.json`).

Please also note that the attribute *SCREndpoint* contains the value *randomString.region.azurecontainerapps.io* from the https://model.randomString.region.azurecontainerapps.io/model URL of your Azure Container App.
