Deploying the Builder UIs

The Prompt Builder is not required, but it is the no-code tool that puts an otherwise code-only workflow in front of the people who own the work. It is one application that builds up to three kinds of things, chosen on its Setup card:

  • a prompt template for LLMs lets prompt engineers test new prompts across LLMs, compare the results, version their experiments, and turn the best prompt into a model for further consumption in the platform (for example in SAS Intelligent Decisioning);
  • a decision template for decision models does the same for the typed questions a decision model answers — see Decision Definitions;
  • a RAG setup lets a data or decision engineer configure a document pipeline — sources, chunking, embedding model, vector store — save it as a governed RAG setup, and generate the ingestion job and SAS Studio flow that run it. This part is the RAG Builder.

One single-file build, one Job Execution definition and one Data-Driven Content object serve all three. Which of them a deployment offers is decided by three switches among the object's options (see Configuration): decision templates are on by default, prompt optimization and RAG are off until an administrator switches them on. RAG additionally needs its runtime in SAS Content — see RAG Ingestion and Retrieval.

Standalone build

The Prompt Builder is shipped as a standalone application in the LLM-Prompt-Builder directory of this repository. It has no dependency on the SAS Portal Framework for SAS Viya — it is a single self-contained HTML file that you embed directly in a SAS Visual Analytics report through SAS Job Execution. Up to release 2.2 the RAG Builder was a second application with a build, a job definition and a report of its own; all three are retired, and a site that still has them follows the upgrade steps of the 2.3.0 changelog.

Install or upgrade with the transfer package​

The content folder /SAS Agentic AI Accelerator ships as one transfer package, SAS-Agentic-AI-Accelerator.json in the folder SAS-Viya-Integrations of the repository. It holds the Prompt Builder ready to run — the Visual Analytics report that hosts the object, the SAS Job Execution definition that serves the single-file app and the optimization job — and with it the RAG runtime, the logging programs with their two custom steps and the usage report, the files the tables of the reports are loaded from, and a first page with an installation check. Importing it takes the place of building the app and wiring it up by hand (steps 1–2 below).

The commands of this section ran on the test system in eleven passes, twice on 2026-10-12, three times on 2026-10-13, three times on 2026-10-14, twice on 2026-10-15 and once on 2026-10-16, in test content roots and as they were then: what the first found changed the import, the second measured the import in place, the third what was built after the second, the fourth what was built after the third, the fifth what was changed after the fourth, the sixth what was changed after the fifth, the seventh what was changed after the sixth, and each pass after it what was changed after the pass before. What was measured, and what has not run has all eleven.

First install and upgrade​

With mdb installed and your .env filled in (Setup SAS Model Manager):

# first install
mdb setup               # the repository, the projects, the release table, the authorization commands of the repository
mdb builders-import     # the content folder

# upgrade
mdb builders-import

A site that created the Call LLM node of SAS Intelligent Decisioning with Create-Custom-SAS-Intelligent-Decisioning-Node.sas of an earlier release has it under an id of its own, and the package brings it under f9efcbb7-f57b-4a62-b56d-1a89595e2039. There mdb builders-import asks the site before it uploads anything of the decisions: it leaves the decision Decisions/Call LLM Node and the node type out, imports everything else, and ends with exit code 1 and the command to run once, before the import:

mdb decision-node-migrate           # dry run: the node type and every decision version that uses it
mdb decision-node-migrate --apply   # give the node the id of the package and move those decisions
mdb builders-import

The Call LLM node and its id says what the migration does and why the old node is never deleted while a decision uses it; --no-decisions imports without the decision instead.

Then open Start Here, in a compute context that runs as you:

https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Start Here&_contextName=<a compute context that runs as you>

Go through the lines of its installation check, run the commands of Access to the content folder, and — on a first install — continue at step 3 (the credential domain), step 4 (the Content Security Policy) and the optional object options of step 5.

mdb builders-import does in one run what an import otherwise leaves to hand work afterwards:

  1. It reads the options of the Prompt Builder report at its place, <content root>/Prompt Builder/Prompt Builder — and of the retired report <content root>/RAG/RAG Builder, while that still exists — and keeps them in a file builder-options-captured-<time>.json in the current directory. A report of that name elsewhere is not read and not written. Importing a report replaces the options an administrator set on the object, see Preserving builder options across a report import; this is what makes an upgrade one command. A report that is there and cannot be read, or that holds no option at all, stops the command here, before anything is loaded or imported.
  2. It loads the release table the Prompt Builder report binds to (--no-releases skips that): from Data/ACCELERATOR_RELEASES.csv of the package where the package holds it, so that the table says what was imported, and otherwise from the changelog of the checkout.
  3. The reports go through the SAS Viya transfer service: the two reports, the files that are children of a report (the pictures of the usage report) and the folders they sit in, cut out of the package. The command rewrites the import mapping before the job starts, so that nothing is edited after the fact: the data source of the Prompt Builder report is retargeted from the shipped Public.ACCELERATOR_RELEASES to SAS_CAS_LIBRARY.SAS_RELEASES_TABLE on your CAS server, and the placeholder host https://your-sas-viya-host in the Data-Driven Content URL becomes SAS_VIYA_URL. With --report-caslib <library> the other tables the reports read — LLM_LOGS, LLM_FACT_SHEET, EMBEDDING_FACT_SHEET, PROMPT_EXPERIMENTS — are pointed at the tables of the same name in that library; without it they stay bound to Public. It waits for the job and reads every task of it: a task that did not end completed is printed and ends the run with exit code 1.
  4. The decision Decisions/Call LLM Node and the Call LLM node type it carries go through the transfer service too, in an import job of their own (--no-decisions leaves them out). The command asks the site first: a node type with the id of the package is overwritten in place - local edits of its code and its terms are replaced, and the line says so -, a missing one is created under that id, and a Call LLM node under another id stops this part before anything of it is uploaded, with exit code 1 and the line mdb decision-node-migrate, because the transfer service would skip the decision without a failed task. A decision or a node type without a completed task of the job ends the run with exit code 1. A decision that is not imported gets no folder in place either. See The decision that carries the Call LLM node.
  5. Every file, custom step and job definition is written in place, by the requests mdb content-deploy sends, with the package as the source: an object that is at its path on your site is updated under the id it has there, and a missing one is created. One line per object says equal, updated, created or FAILED — see What an upgrade does to what a site has. Every file, custom step and job definition below the root folder of the package is brought, and every empty folder — the manifest of your checkout does not limit what is brought. The never-ship rule and the rule for a path do: an object whose name, or the name of a folder above it, is empty, . or .., holds a slash or a blank at either end is not taken, and gets a not imported: line with its reason. release.json is written last, and only when every object in front of it was written.
  6. It writes the options back: the ones it read; or, with --options <file>, a file saved with mdb options-save — the way to change a value before the import; or, on a site that has no Prompt Builder report yet, the values mdb setup discovers — the repository, the LLM and the embedding project ids, the SCR endpoint and the deployment type. On such a first install the three switches keep the defaults of the package, so RAG and prompt optimization are off until you enable them in step 5. Either way every placeholder host that is left in the report becomes SAS_VIYA_URL. A repository or project id the report holds no value for is discovered from the deployment, for that kind only; a value the report holds is kept. A run that writes every option back removes its builder-options-captured-<time>.json.
  7. It writes sas-viya-cli-content-commands.txt, see Access to the content folder.

mdb builders-import --dry-run says what a run would do and writes nothing: every request it sends, the sign-in aside, is a GET, nothing is uploaded, and its mapping: lines are what the package itself says about its tables and its host. A run that did not do everything ends with exit code 1 and prints the command to run next, on a line of its own; that command names the kept options file, so that the second run does not read the options again from a report the import may have replaced already. A kept file stays in the directory the command ran in until a run writes every option it holds back. It holds option values and no key. The release table needs no clone, the rest of the command does: the clone of the repository gives the manifest — the default package file and content root, and the site settings of the job definitions it lists —, configures a site without the Prompt Builder report by discovery from the model definitions, and gives the release table of a package that holds none.

Where a run stops:

  • A report that is there and cannot be read: <report>: it is on this site and its content cannot be read (...), Nothing was imported. A report that is read and holds no option at all stops the same way: <report>: it is in <folder> and holds no option at all - .... Run the command again when the report can be read, name the options with --options <file>, or pass --no-options-capture — then the imported report is configured from the deployment, and what an administrator set is gone.
  • A task of the import job that did not end completed: the import job ended completed, and n of its tasks did not: with a line per task. The options are not written into a report the command cannot be sure was replaced; the command to repeat names the kept options file.
  • A write of the in-place part that is refused or gets no answer: that object is FAILED, every object behind it is listed as not attempted, and Stopped at the first write that failed: ... says what was written before it. A folder that cannot be created stops the run the same way. Nothing is removed, and a second run leaves what is equal by then as it is. release.json is written last, and only when every entry in front of it was written: after a run that stopped, the folder's release.json is the one an earlier run wrote — Start Here shows that release and its commit, and checks the entries that file lists —, and after a first install that stopped there is none, and Start Here shows release.json as missing.

What an upgrade does to what a site has​

A custom step that a flow uses is referenced by its id, and so is a job definition behind a link or a schedule. The in-place part of the import therefore never replaces an object by a new one:

updated      step          RAG/steps/RAG - Embed Chunks.step  (templates; id <the id on your site> kept)
updated      file          RAG/rag_core/tokens.py  (content replaced in place; id <the id on your site> kept)
updated      jobDefinition Start Here  (code; id <the id on your site> kept)
equal        step          RAG/steps/RAG - List Documents.step  (id <the id on your site>)
created      file          Logging and Monitoring/Link-Logs-To-Models.sas  (id <a new id>)
  • An object at its path is updated under its own id, whatever id the package carries for it — a site that got its content from an earlier package, from mdb content-deploy or from the earlier deploy script has other ids than the system the package was exported from. A file keeps its id too: its content is replaced, the file is not deleted. Nothing of the exporting system — an id, a link, a user — reaches your site with the in-place part.
  • A second import changes nothing: every line says equal, and nothing is written.
  • Two objects of one name in one folder are both named with their ids, and neither is written; the same holds for an object and a reference of its name to an object of its kind elsewhere, and such a reference alone fails its entry. A reference of that name to an object of another kind fails nothing: the run lists it at the end as <path> (reference to a <kind> - not the <kind of the entry> that is listed under this name). The kinds are spelled as the other lines spell them: file, folder, report, registered step, job definition; an object of no kind of the manifest is called by the content type the Folders service gives it, or by its address. The rest is brought and the run ends with exit code 1. Remove the one that is not used, or the reference, and run the command again.
  • What is not at its path is not touched. A step you registered in a folder of your own — the starter package of earlier releases put LLM - Log Parser into the folder Custom Steps, and a step may live in the folder of a user — stays as it is, and the import creates the step of this release at its path beside it. Update yours in place from a checkout with mdb content-deploy --only "<its path in the manifest>" --to "<path or id of your step>", see One part, somewhere else.
  • The settings of a site in a job definition stay. A compute context a site set in the parameter _contextName of a job definition — Start Here, Load-Accelerator-Tables, SAS-LLM-Prompt-Builder-UI — stays: an import and a deploy leave an existing value alone. The option RAG: ingestion compute context (ragComputeContext) of the options the import writes back is given to a job definition the import creates and to one on the site that has no _contextName; a _contextName a job definition on the site holds is kept. It has to be a context that runs as the requesting user; where the options name none, the default of the package (SAS Studio compute context) takes its place, and computeContext, the context of the optimization job, is not taken. --compute-context <name> writes that context into every job definition that has the parameter. contentRoot is always written with the content root the content goes to. The other values a site points Start Here and the loader at — the CAS library and server, the credential domain, the names of the repository and the projects, the compute contexts the page looks for, the release table — are settings of the site as well; the address of the guides is the release's. Measured in the second pass of 2026-10-12: the import kept the _contextName a test root had set on Start Here and wrote that root into its contentRoot. Measured on 2026-10-13, with options that name an ingestion compute context: Start Here kept the _contextName the root had set, the job definition Load-Accelerator-Tables, which the import created, got the context of the options, and --compute-context wrote its context into Start Here. A job definition on the site without the parameter was not part of that pass.

Another content folder. --content-root <folder> brings everything but the reports into that folder and writes it into the parameter contentRoot of the two job definitions that have one; a folder that is not there is created only with --create. The reports and the decision Decisions/Call LLM Node are imported only into the folder the package was exported from, /SAS Agentic AI Accelerator, and only because that folder is at the root of SAS Content: the transfer service takes no target folder, and no mapping to another folder is known to work. With another content root the command says Reports (...): NOT imported and Decisions (...): NOT imported with the reason and ends with exit code 1; --no-reports --no-decisions says that this is meant, and the transfer service is then not called at all. The command it names to run again adds both.

After an upgrade, reload the Prompt Builder report. On a site that had the report RAG Builder, the switch Enable RAG setups in the Options pane of the object is ticked and the RAG: options below it hold the values of the old report; the Setup card offers RAG setup for a document collection as a third kind, and an existing setup opens. If the RAG card is shown and cannot be chosen, the credential domain is none — see The retired RAG Builder report. Enable prompt optimization (DSPy) shows what the report stored: ticked where optimization was enabled before.

What an import does not bring, and what it replaces:

  • No tables, no projects, no credentials, no option values. A transfer package cannot carry CAS tables, SAS Model Manager projects, credentials or the option values of a site. mdb setup creates the repository and the projects, the command above writes the options, Managing Credentials has the credential domain, and the tables are loaded as The tables of the reports says.
  • A job definition holds a copy of its program and of its form. An import replaces both, and the parameters with them, except the two that are settings of a site: a compute context an administrator set in the parameter _contextName of SAS-LLM-Prompt-Builder-UI stays. The job definition of a RAG setup that a site generated is not part of the package and keeps the ingestion program of the day it was manifested — see After an upgrade: manifest every setup once.
  • The logging programs are replaced as files. Settings that were written into Log-Parser-Code.sas or Get-All-Prompts.sas are gone with the old file; from release 2.3.0 on a site sets them in a program of its own — see Settings that stay yours.
  • An import removes nothing. What a site has in the folder beside the content of the package stays, the retired report RAG Builder among it.
  • The Call LLM node comes under one id, f9efcbb7-f57b-4a62-b56d-1a89595e2039, with the decision that carries it. A site that has a node named Call LLM under another id — created with Create-Custom-SAS-Intelligent-Decisioning-Node.sas of an earlier release — runs the migration mdb decision-node-migrate before the import. mdb builders-import refuses the decisions there before it uploads them and ends with exit code 1 and the migration command. A transfer import of the package in SAS Environment Manager is not asked: it fails the task of the node, and skips the decision without a task, while the import job ends completed. See The Call LLM node and its id.
  • The reports go into one folder. The files, custom steps and job definitions follow --content-root; the two reports and the decision are imported into /SAS Agentic AI Accelerator or not at all, see What an upgrade does to what a site has.
  • The uploaded package is deleted. The command uploads the reduced package for the reports and deletes it once the import job has ended; a delete that is refused is a line with the id of the package and how to delete it. That delete has not run against SAS Viya.

Access to the content folder​

The package carries no authorization rule and no share: who may read the folder is decided on the site. The rules mdb setup writes cover the model repository, not this folder.

mdb builders-import writes a file sas-viya-cli-content-commands.txt into the current directory (--out <dir> names another one, --no-files leaves it out): two sas-viya authorization create-rule commands that give the LLM Consumers group — the group the commands of mdb setup create — Read on the content folder and on what is in it, with the id of the folder filled in. The command runs neither. Review the file, replace the group if you use another, and run the two commands with the SAS Viya CLI.

On a site that upgrades, this is also what gives the people who used the RAG Builder access to the folder Prompt Builder: the report and the job definition SAS-LLM-Prompt-Builder-UI that serve the RAG Builder now live there.

The one file imports like any transfer package. SAS Environment Manager. Import the JSON from SAS Environment Manager → Content → Import. Then correct the host in step 5: open the report and update the Data-Driven Content object's base URL to your SAS Viya server.

SAS Viya CLI. Use the transfer plugin of the sas-viya command-line interface. This assumes you have installed the CLI, created a connection profile, logged in and installed the plugin as described in Introduction — SAS Viya CLI Setup. In the commands below substitute https://viya.example.com with your own SAS Viya URL.

    # bash / Linux / macOS
    sed -i 's#https://your-sas-viya-host#https://viya.example.com#' SAS-Agentic-AI-Accelerator.json
    # PowerShell / Windows
    (Get-Content SAS-Agentic-AI-Accelerator.json) `
      -replace 'https://your-sas-viya-host','https://viya.example.com' |
      Set-Content SAS-Agentic-AI-Accelerator.json

  2. Upload the package — the command prints the new package's id:

    sas-viya transfer packages upload --file SAS-Agentic-AI-Accelerator.json

  3. Import it by that id:

    sas-viya transfer packages import --id <package-id>

    Or do both in one go, capturing the id (requires jq):

    pkg=$(sas-viya --output json transfer packages upload \
      --file SAS-Agentic-AI-Accelerator.json | jq -r '.id')
    sas-viya --output text transfer packages import --id "$pkg"

    (On older transfer plugin versions the same commands are sas-viya transfer upload / sas-viya transfer import — they still work, marked deprecated.)

The host is a transfer substitution

The placeholder lives in the package's substitutions block, which is what SAS's import machinery is designed to remap. Editing the string before upload (step 1 above) is the simplest fix. Alternatively, remap it at import time with a mapping file: pass --mapping mapping.json to the upload and the CLI writes a JSON file whose substitutions block holds the entry with the placeholder URL — edit that value to your host, then pass the same file to the import:

sas-viya transfer packages upload --file SAS-Agentic-AI-Accelerator.json --mapping mapping.json

Preserving builder options across a report import​

Importing a report overwrites your configuration

Every option you set on the Prompt Builder object — repository and project IDs, the SCR endpoint, the credential domain, the three switches, and for RAG the content root, the ingestion compute context and which vector stores the deployment offers — is stored inside the Visual Analytics report, not alongside it. A transfer package carries those values too, so importing a newer version of the report replaces your settings with whatever the package was built against.

This does not fail loudly. The report still opens and the app still runs; it simply shows the package's defaults — RAG switched off, no project IDs. mdb builders-import reads the options before it imports and writes them back; for an import made any other way, save your options first.

mdb builders-import without --options does both steps below by itself and keeps what it read in builder-options-captured-<time>.json. The two commands are for a file to keep with your deployment records, to edit before an import, to carry to another deployment, or for a package that is imported without mdb (see Model Definition Builder for installing the CLI and its [viya] extra):

# BEFORE importing a new report package
mdb options-save --file builder-options.json

# AFTER the import
mdb options-restore --file builder-options.json --dry-run   # check what would change
mdb options-restore --file builder-options.json             # write it back

options-save discovers the Model Manager repository and the LLM and embedding projects exactly as mdb setup does, then overlays whatever your live Prompt Builder report already holds — so a deployment that has been tuned is captured as tuned, not as freshly bootstrapped. Keep the resulting file with your deployment records; it supersedes the llm-prompt-builder.json seed as the record of how this environment is configured.

options-restore writes back only the options named in the file. The newly imported report keeps its new layout, data items and objects, and regains your configuration. It also replaces the shipped placeholder host your-sas-viya-host - in the object's Data-Driven Content URL and in the viyaHost / SCREndpoint defaults - with SAS_VIYA_URL, so a report imported by hand needs no URL edit afterwards (mdb builders-import does both in one run).

  • The report is matched by name (Prompt Builder). If you have renamed the report in your deployment, rename it in the file to match, or the restore skips it.

A package is exported with the option ticked: on a report that would ship it switched off, mdb package-export ends with exit code 1 and writes nothing.

Why the build base64-encodes its scripts

SAS Job Execution serves HTML through a Go template engine that treats {{ … }} as directives. The build base64-encodes every inline <script> and decodes it at runtime so the minified bundle — which inevitably contains {{/}} — is not corrupted. This is automatic and requires no action.

3. Provide the API keys via the credential domain​

The Prompt Builder resolves provider API keys from a SAS Viya credential domain (default agentic-ai-keys) under the identity of the signed-in user — a user credential overrides a group credential, and models the user holds no key entry for are shown disabled with a note. RAG setups take the vector-store credentials, and where each store lives, from the same domain. Set the domain up once with the CLI-based scripts as described in Managing Credentials; no data source, table, or report assignment is involved.

Keys stay governed

Keys live encrypted in the Credentials service — never in the report definition, the URL, or a data table. Who holds a credential in the domain (directly or via group membership) is who can run paid model calls.

note

That sandbox does not include allow-popups, which is why the links that leave the page — "Open in SAS Model Manager", the link to a saved prompt-test, the links to a decision in the delete dialogs — copy their URL instead of forcing a new tab on a normal click (use the browser's right-click → Open link in new tab). Add allow-popups to the IFrame Sandbox Attribute Value to let these links open a tab directly. A link is copied only where no tab opened: with allow-popups a click opens the tab and leaves the clipboard alone.

The page carries the referrer policy same-origin, a meta element in its head: what it asks of another origin than its own carries no Referer, what it asks of its own origin keeps it. A link to another site — the user guide link of the Optimize step — therefore does not tell that site the address of your SAS Viya host. A tab the page opens on SAS Viya itself, such as SAS Model Manager, is told where the click came from, as before, and the calls to SAS Viya keep their Referer; that holds where the page is served from the SAS Viya origin, as in the setup described on this page, and not where the viyaHost parameter names another origin. A call to a model container on another host carries no Referer either, but that host still learns where the page runs: a browser names the origin of the page in the Origin header of every cross-origin call, whatever the referrer policy.

5. Add the object to a Visual Analytics report​

If you imported the transfer package then open up the SAS Visual Analytics report under SAS Content > SAS Agentic AI Accelerator > Prompt Builder > Prompt Builder and then continue.

  1. In a Visual Analytics report, add a Data-Driven Content object and in the Options pane under Web Content enter the URL from the previous step or if you imported it update the base URL to your SAS Viya server.
  2. Assign the release table to the object: in the Data pane pick Public.ACCELERATOR_RELEASES (loaded by mdb setup or mdb load-releases; the library and name follow SAS_CAS_LIBRARY / SAS_RELEASES_TABLE) and add any of its columns to the object's role. A Data-Driven Content object does not render until it has a data assignment; the Prompt Builder itself reads nothing from it, and provider keys still come from the credential domain (step 3). The table carries the accelerator's changelog - one row per release and per change, with a component column - so the same report can show what changed for the Prompt Builder next to the object. A change to the Prompt Builder is one row for each part of it that it concerns, named in the column builder_part (Prompt, Decision, RAG): a page that lists the changes keeps its filter on component and gets a button bar on builder_part, with which a reader picks the part - see The release table for the rows and for what a page built before the column shows.
  3. Open the object's Properties panel and set the configuration values (see below).

Configuration (Properties panel)​

The object publishes one list of options, in the order of the tables below: first the options every kind shares, then the three switches, each directly followed by the options that only matter while it is on. Visual Analytics writes every value into the object's URL under the URL parameter name and reloads the app, which is how a changed switch makes its options appear or disappear.

The five environment-specific values are exactly those captured in your llm-prompt-builder.json — the file produced in the Setup SAS Model Manager chapter (regenerate it by re-running mdb setup if you have lost it), where each stands under the name of its URL parameter: modelRepositoryID, llmProjectID, embeddingProjectID, SCREndpoint and deploymentType. mdb builders-import writes the same five into the report by itself, so copying them by hand is only needed for a report you built yourself.

Verify TLS certificates in manifested models​

Three kinds of manifested model make an HTTPS call themselves when they are scored: a prompt template manifested with Include the LLM call in the manifested model, a decision template, and the retrieval model of a RAG setup. Each verifies the certificate of what it calls against the CA bundle of the SAS Viya deployment. sslVerify decides what is written into the score code of such a model when it is manifested:

  • It is a default written at manifest time. Changing the option changes the models manifested from then on. A model that is already manifested keeps what it was manifested with, in SAS Model Manager and on every destination it is published to, until it is manifested again.
  • It changes nothing else. The calls the Prompt Builder page makes in the browser, the ingestion job of a RAG setup, and a prompt manifested for the Call LLM node (where the node makes the call) are as before.
  • The SAS Studio custom step has a checkbox of its own. A retrieval model registered with RAG - Register Setup is not manifested on this page, and the step does not read sslVerify. Its checkbox Verify TLS certificates in the registered retrieval model (Runtime section, ticked by default) writes the same line into the same score code and sets and removes the same tag — see RAG Ingestion and Retrieval.
  • A destination can overrule it in both directions with an environment variable: LLMCONTAINERSSLVERIFY for prompt and decision templates, RAGEMBED_SSLVERIFY and RAGSTORE_SSLVERIFY for the retrieval model. true switches verification on for a model manifested with it off, false the reverse — see Deployment of Decisions.
  • Off is visible. A model manifested while the option is not ticked carries the tag TLS-Verification-Off, on all three kinds, and manifesting it again with the option ticked removes the tag. The step shows a warning before the click that names this option and the variable that turns verification back on: Finalize for a decision template, Finalize for a prompt only while Include the LLM call in the manifested model is ticked, and Manifest setup for a RAG setup. Finding the models that do not verify lists such models and names the line to look for in a score code.
  • A report saved before the option existed shows the checkbox ticked, and so verifies. The state of the checkbox is stored with the report: it is there again after the report is saved and reopened.

Leave it ticked unless a destination cannot verify. The case it exists for is SAS Micro Analytic Service running Python in a container that does not have the CA bundle; Publishing to SAS Micro Analytic Service: the certificate bundle describes it, the fix that keeps verification on, and when switching it off is acceptable — a test system on a closed cluster network, not production.

In the URL the option reads like a switch: Visual Analytics writes sslVerify=true or sslVerify=false; in a URL written by hand 0, no and off also switch verification off, in any case. A blank, missing or any other value keeps it on.

info

Until the object is configured it shows a "Configuration required" message and does not call SAS Viya, so it never fails against placeholder IDs. The message names what is missing for each side, and completing either is enough for the page to load: prompt and decision templates need the repository ID, the LLM project ID and the SCR endpoint; RAG setups need the repository ID, Enable RAG setups ticked and a credential domain other than none. A site with no LLM project therefore gets the RAG Builder alone.

Every field can also be appended to the object's URL by hand using its URL parameter name above (for example &judgeModel=...&modelCardReportURI=/reports/reports/<uuid>), which is a reliable fallback if your Visual Analytics version does not render the options panel. For a switch, Visual Analytics writes true for a ticked checkbox and false for one that is not; in a URL written by hand a switch also reads 1, yes or on as on and 0, no or off as off. Anything else, and a blank or missing value, is its default.
