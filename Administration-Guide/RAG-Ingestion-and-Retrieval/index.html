RAG Ingestion and Retrieval

The accelerator ingests a document corpus into a vector store and serves it back to a decision. This page is the operations view: what to deploy, what the environment must provide, which knobs matter, and what the product does with your data. For building a pipeline, see the RAG user guide.

What gets deployed​

Everything lives in one governed SAS Content folder, by default /SAS Agentic AI Accelerator/RAG:

FolderContents
rag_core/The Python runtime every step and job imports at run time
steps/The nine custom steps, registered as dataFlows resources
jobs/Ingest-Documents.sas, the standalone schedulable job, and Test-Retrieval.sas, the probe behind the Builder's Test retrieval
models/The retrieval model template, manifested per setup
generated/Default destination for per-setup artifacts — the ingestion job and the Studio flow the Builder generates, and what RAG - Register Setup writes. The Builder lets an author choose a different folder per setup

This is the RAG runtime. It holds no user interface: the RAG Builder that writes setups against it is part of the Prompt Builder — see Serving the RAG Builder below.

Two ways put the runtime there:

  1. The transfer package. mdb builders-import imports the content folder, and the runtime is the folder RAG of it — see Install or upgrade with the transfer package. The package is compared with the repository before it ships, file by file and step by step, so a site that imports the package of a release has the runtime the documentation and the changelog of that release describe, and needs no script.
  2. From a checkout. The shipped script publishes the runtime of your checkout — for a fix between two packages, or for a site that does not import the package:
./SAS-Viya-Integrations/Other/deploy-rag-content.ps1
./SAS-Viya-Integrations/Other/deploy-rag-content.sh

The script calls mdb content-deploy --only RAG --to <the RAG content root> (see One part, somewhere else). It needs the Model Definition Builder installed and a sign-in it can use — a token, a password grant or the login of the SAS Viya CLI. The folder it deploys into is /SAS Agentic AI Accelerator/RAG; -ContentRoot (PowerShell) or -r (bash) names another one: the RAG content root itself, a folder of any name, which is what the option RAG: content root of the Prompt Builder holds. A site with such a content root deploys the runtime there after an import, because the import brings it into the folder RAG of the content folder. -DryRun / -n lists what would change and writes nothing. A folder that is not there is created only with -Create / -c (with every folder above it), so a mistyped path does not become a new folder. A warning mdb writes to the error stream - InsecureRequestWarning where TLS verification is off - does not stop the PowerShell script, also with its streams redirected, and both scripts end with the exit code of mdb. The command they call, mdb content-deploy --only RAG --to <folder>, created the 41 entries of the runtime directly in a test folder on SAS Viya 2026.09 on 2026-10-12. On 2026-10-13 the PowerShell script ran as a dry run for a test folder, with every stream redirected into a file and its command line saved beside it: the file held the warning and 41 entries: 41 equal., and the request log GET requests only; the exit code of the script was not saved. Not run against SAS Viya: the bash script, a run without -DryRun / -n, and -Create / -c.

Nothing is ever fetched from the internet at run time, so both ways work in an air-gapped deployment: the SAS Content folder is the distribution channel, not GitHub.

If a deploy ends with a line that says FAILED, read the line Stopped at the first write that failed: ... under it and run the deploy again: it stops at the first write that is refused or gets no answer, lists what it did not attempt, and removes nothing, so the folder holds the file it had or the new one. Up to release 2.2 a file was replaced by deleting it and uploading the new copy. Measured on 2026-10-11 on SAS Viya 2026.09 with deploy-rag-content.ps1 as it was then — a script that uploaded the files itself —, against a content folder that held the runtime of release 2.0: the first run stopped after four files with (409) Conflict on the upload of a file (POST /files/files) whose old copy it had just deleted, and left that file missing. The same upload was answered 201 a minute later, and a second run of the script completed with Deployed 35 files. All nine steps had kept their ids, and every file equalled the checkout afterwards. A third run later the same day went through at the first attempt. mdb content-deploy deletes no file: it replaces the content of a file that differs in place, under the id the file has. That update has not run against SAS Viya.

Why a deploy and not a manual upload

A .step file uploaded as a plain Content file renders as an empty step editor — steps are dataFlows service resources. The deploy also updates an already-registered step in place rather than replacing it. Re-registering a step mints a new id, and every saved flow referencing the old id breaks.

After an upgrade: manifest every setup once​

A new runtime in the folder does not reach what a site made from the earlier one. After the package of a new release was imported, or its runtime deployed from a checkout:

  • Open every RAG setup in the Prompt Builder and click Manifest setup. A retrieval model holds the score code it was manifested with, and the job definition of a setup holds a copy of Ingest-Documents.sas from the day it was manifested; the manifest writes the template and the program of the release into them. For release 2.3.0 that is what brings the endpoint a setup embeds at (Where a setup embeds), the TLS setting of the report, the lengths of the variables (The lengths of the variables), the saved ledger that is loaded back (A saved ledger is loaded back), the run lock that follows the column types of the ledger, and a failed run that ends as a failed job.
  • Run the ingestion of each setup once. From release 2.3.0 on the job publishes <prefix>_RUNS and <prefix>_DOC_EVENTS beside the ledger, and that one run publishes every run the vector store holds for the collection (Run history). A job definition that was not manifested again holds the program of the day it was made and publishes neither table.
  • Publish the decisions that use the retrieval model again, so that the destinations run the new score code. No published decision has to be repaired for the lengths of the variables.
  • A setup that was registered from a flow gets the new score code when the step RAG - Register Setup runs again (the checkbox of the step). A job that the step generated from a flow is not written by Manifest setup: run the step again with the flow named under Studio Flow to generate the scheduled job from. A job that SAS Studio itself deploys from the flow does not have the statements that report a failed run as failed.
  • A schedule, a monitor or a script that reads the state of the ingestion job has to expect a new state from release 2.3.0 on: a run that failed ends as failed. Up to 2.2.x, and with a job definition that was not manifested again, it ends as completed with ERROR: RAG ingestion failed: … as the last message of the program in its log.

Serving the RAG Builder​

The RAG Builder is not an application of its own. It is the RAG setup kind of the Prompt Builder: the same single-file app, the same job definition (/SAS Agentic AI Accelerator/Prompt Builder/SAS-LLM-Prompt-Builder-UI) and the same Data-Driven Content object in the Prompt Builder report. There is nothing to build and no job definition to create for it — deploy the Prompt Builder as described in Deploying the Builder UIs, then switch RAG on:

  1. Import the package or deploy the runtime (above), so the content root holds rag_core, the steps, the jobs and the model template.
  2. Open the Prompt Builder report, select the object and open its Options pane. The release table Public.ACCELERATOR_RELEASES has to be assigned to the object, as for every use of it — see step 5.
  3. Tick Enable RAG setups. The options that start with RAG: appear below the checkbox.
  4. Fill them in: the embedding model project, the content root, the CAS server, the ingestion compute context, a checkbox per vector database the deployment offers, and the operational policy (TLS, deleted-document handling, history retention, run-history recording, embedding replicas, table persistence). The Model Manager repository, the SCR endpoint, the deployment type and the credential domain are the ones the Prompt Builder already has; they are set once and used by every kind. The whole list, with defaults, is in Configuration.

The Setup card of the Prompt Builder then offers RAG setup for a document collection beside the template kinds, and choosing it shows the Builder's own four steps. While the switch is not ticked — the default — the kind is not offered, nothing of the Builder is loaded and nothing RAG is requested from SAS Viya. With it enabled, the first request for RAG is made when a user chooses the kind.

The folder picker and its compute session​

The document folder of a setup is chosen with Browse, never typed, so a setup names a folder its author could see. For SAS Content the picker lists folders through the Folders service. For the compute server it needs a compute session: no other service lists that file system, and only a session shows what the ingestion will see - the same file system, as the same user.

  • The session is started in the ingestion compute context as soon as the RAG kind is shown, because a new session takes about half a minute to be ready (13 s to create and 21 s to be idle, measured on SAS Viya 2026.09). Listing a folder afterwards takes a fraction of a second.
  • It is named Prompt Builder - RAG folder picker and is kept alive with a request every minute while the RAG kind is shown. It is deleted when the user switches to a prompt or decision template or leaves the page.
  • It is created with an idle timeout of five minutes (the session attribute sessionInactiveTimeout), so a session whose page stopped asking - a closed laptop, a lost network - ends by itself.
  • Start folders. The options RAG: start folder on the compute server and RAG: start folder in SAS Content set where the picker opens; blank, the default, opens it at the top. With a start folder set and its allow folders above option not ticked, the picker cannot go above it and a setup can only be saved with a folder below it. This guides the users of the page; it is no permission. What the file system or SAS Content lets a user read decides what the picker shows, and the ingestion job reads the folder its definition names.

The policy values are recorded onto each setup as it is created, so a setup keeps what it was built with.

Three settings worth checking when RAG does not behave as expected
  • The credential domain must not be none. Prompt and decision templates read none as "look no key up". RAG has no such mode — the ingestion and the retrieval take the store's user, password, host and database from the domain — so the RAG card is shown disabled and says why.
  • The Model Manager repository ID must be set. Every kind needs it; without it the kind is not offered.
  • The ingestion compute context is not the optimization compute context. The option is ragComputeContext (RAG: ingestion compute context); the option computeContext belongs to the prompt optimization job and is never read for an ingestion. A blank ragComputeContext does not hide the kind: it blocks Launch ingestion and Test retrieval with a message that names the setting.
These options live inside the report

Importing a newer Prompt Builder report from a transfer package replaces every value above with whatever the package was built against — silently, since the report still opens and the app still runs, with RAG switched off. Save them with mdb options-save before importing and restore them after: see Preserving builder options across a report import. That section also covers a site that still has the retired report named RAG Builder from release 2.2 or earlier.

Served standalone rather than embedded, the same settings are query parameters of the Prompt Builder job — the switch included, because it is off by default:

.../SASJobExecution/?_program=/SAS Agentic AI Accelerator/Prompt Builder/SAS-LLM-Prompt-Builder-UI&_action=form&enableRag=true&modelRepositoryID=<uuid>&embeddingProjectID=<uuid>&ragComputeContext=<context name>

(The browser encodes the blanks.) Without an LLM project in the URL the page shows the RAG Builder alone; add llmProjectID and SCREndpoint to get the template kinds beside it. A URL written for the job definition RAG-Builder-UI of release 2.2 or earlier has to be rewritten this way: that definition is retired, its context parameter was called computeContext, and it needed no enableRag. id is no longer read from the URL. For your own builds: npm run build:rag is gone, and npm run build produces the one dist/index.html that holds all three kinds.

If you replace the app by hand: the HTML is the FORM, and the form is a property

mdb builders-import and the manual steps in Deploying the Builder UIs put the built dist/index.html into the job definition for you. Updating the definition through the REST API instead has two ways to go wrong, both of which look like something else:

  • &_action=form serves the job's form. HTML in code produces "Parameter Error — HTML form file was not found", which reads like a missing file rather than the wrong field.
  • The form is an entry inside the definition's properties list, named form — not a top-level form key. A PUT carrying a top-level key returns 200 and silently drops it, so the deploy looks successful while the old app keeps serving. Verify by reading the property back, not by trusting the status code.
What the Builder never asks a user

Three things a person building a corpus should not have to know are resolved rather than typed:

Comes from
Vector store host, port, databaseThe credential domain — see below
Embedding modelListed from the embedding model project
Embedding dimensionsThe chosen model's fact sheet
Maximum chunk sizeCapped at the chosen model's published token window

A typed model name has nothing behind it until a container is published, and the failure surfaces as an HTTP 404 at the first embed call — after the crawl and the chunking have already run. A vector column is created at the model's width and cannot be widened afterwards. And text beyond a model's token window is dropped by the model silently rather than rejected, so an oversized chunk is embedded from its opening only — retrieval then matches on text the answer never sees, with nothing in the run reporting a problem. The Builder asks for the model first for that reason: the ceiling has to be known before anyone picks a chunk size under it.

What the Builder's buttons create — and what they clean up​

ButtonWhat it leaves in your environment

Browse ledgerNothing — reads the promoted ledger table

Test retrieval asks the live collection a question and shows the chunks that come back, with what the probe cost. It is deliberately built to leave no trace: the job definition it runs is created without a parent folder, so it never appears anywhere in SAS Content, and it is deleted when the run ends — including when the run fails or is abandoned. The hits travel back in the job log rather than in a CAS table, because an output table would itself be an artifact of a test meant to have none. The finished job's own record and log remain in SAS Job Execution, as for any job run.

It exercises the collection, not the registered score code: it queries through rag_core exactly as the ingestion does, so a broken retrieve_context.py would still pass. Verifying that needs the published model.

One ledger for the job and the flow​

Manifest setup generates two things that ingest the same setup: the ingestion job, which is the one program Ingest-Documents.sas, and the SAS Studio flow, which is made of the RAG custom steps. Both keep the same ledger, <prefix>_LEDGER, and both take the same run lock on it: a row that the start of a run appends to the table. They do not store the ledger alike:

The ledger was last written byIts text columns are
the ingestion jobCHAR, with fixed lengths
the flow (RAG - Load Vector Store), or RAG - Purge DocumentsVARCHAR

CAS does not append a row whose column is VARCHAR where the table has CHAR, or the other way round. Up to release 2.2 each of the two declared its lock row the one way it stores the ledger itself. Seen on 2026-10-11 on SAS Viya 2026.09: a setup ingested with Launch ingestion, then its generated flow run in SAS Studio, stopped in the first step with

ERROR: The variable doc_id has been specified with incompatible data types.
ERROR: The action stopped due to errors.
ERROR: RAG - List Documents failed: the run lock could not be written to <caslib>.<prefix>_LEDGER - refusing to ingest unguarded

and left the ledger as it was. The append the other way round — a CHAR row to a VARCHAR table, which is the job on a ledger a flow wrote — was refused with the same text in a scratch caslib. The job itself was not run on a ledger a flow had written before the change; by its code it did not look whether its lock had been written, so it would have gone on without one.

From release 2.3.0 the job, RAG - List Documents and RAG - Purge Documents ask the table for its column types (table.columnInfo) before they take the lock, and declare the lock row the way the table holds its text. The log of the run says which it found: NOTE: the ledger … holds its text columns as char - the run lock is written the same way, or as varchar. The steps that read the ledger compare its values without the blanks a CHAR column is padded with. Nothing has to be migrated: a ledger of either type is used as it is, and it still changes its type with the writer that last completed a run. The two were not made to store the ledger alike; that would have changed how the last step of a flow, or the job, writes the table, and neither change could be measured.

The new lock is in the steps and in the job, which reach a site with the transfer package, or from a checkout with deploy-rag-content. The job definition of a setup holds a copy of Ingest-Documents.sas as it was when the setup was manifested, so manifest the setup again afterwards; whether a flow generated earlier runs the redeployed steps without that was not checked.

Measured on 2026-10-11 on SAS Viya 2026.09, with the ingestion job and the generated flow of one setup, in both directions:

  • The job on the ledger it had written (CHAR). The log said NOTE: the ledger Public.…_LEDGER holds its text columns as char - the run lock is written the same way, the append added one row, and the run completed with 3 documents unchanged.
  • The generated flow on that CHAR ledger — the case that had failed with incompatible data types. All five steps ended green. Afterwards the ledger was VARCHAR, with 3 rows of status unchanged and no lock row.
  • The job on the VARCHAR ledger the flow had left. The log said … holds its text columns as varchar - the run lock is written the same way, the append added one row, and the run completed with 3 unchanged.

Measured again on 2026-10-11 on the same system, with pgvector and with SingleStore 9.0.40. The job and the flows ran as SAS Job Execution jobs in the SAS Studio compute context, the flows as the code SAS Studio generates for them and not clicked in SAS Studio, on ledgers in CASUSER:

  • A project without a ledger, then the job twice. The first run found 3 documents new, and the ledger it wrote was CHAR. The second run logged as char, appended the lock and completed with 3 unchanged. The same on SingleStore.
  • The step RAG - Purge Documents in the mode purge, on a CHAR and on a VARCHAR ledger (pgvector), and on a CHAR ledger (SingleStore). The step logged the type it found and appended its lock, its log said removed 1 chunk rows for 1 documents, and the ledger held 2 documents afterwards and no lock row. The ingestion that followed — the flow in two of the three cases, the job in one — found the purged document as new and brought it back. On pgvector the removed chunk row is the step's own log line; on SingleStore the collection was read and held 2 chunks.
  • A first step that fails and hands the lock back, on both types (pgvector). RAG - List Documents with a documents folder that does not exist appended its lock, failed, and wrote NOTE: RAG - List Documents: the run lock was released so the run can be retried. The ledger kept its 3 rows and its type and held no lock row, and the next run, less than three minutes later, was not refused.
  • The job reads its lock back (see below). Every job run on a ledger that existed showed two PROC JSON steps before the Python program and completed.

Not measured in those runs: a lock that CAS refuses, which is what the read-back of the job is there for; a first run of the flow without a ledger with these steps (a flow on a ledger of its own ran green earlier the same day, before the change); the fallback for a table whose column types cannot be read; two runs at the same time, and with them a run that the lock of another run refuses; and a lock older than 30 minutes. What the job does with its lock when its run fails was not measured either. By the code of that day it left its lock row in the ledger; it now takes its own row out again. All of these but the first and the third were measured later the same day, with the job and the steps as release 2.3.0 ships them — see Measured with the runtime of release 2.3.0 at the end of this section.

The job reads its lock back. RAG - List Documents reads the lock it appended and refuses to go on without one. The job did not: by its code a lock that CAS had refused went unnoticed there, and the job went on without one. It now exports the ledger a second time, after the append, and looks for a lock row the first export did not hold. Without one it ends with RAG ingestion failed: RuntimeError: the run lock could not be written to the ledger … - refusing to ingest unguarded, and the ledger stays as it was. The check sees only that the row is not there, so the message names where to look and not one cause: the SAS log above it, for an ERROR of the append or of the export after it. The passing case was measured, as said above; the refusal was not provoked. To see it on a site: run the job of a setup whose ledger exists (Launch ingestion after deploy-rag-content and Manifest setup) — the run has to complete as before, and its log then shows two PROC JSON steps before the Python program where it showed one.

What follows in this section was written after those measurements. It is in the steps and in the job of release 2.3.0 and was run on the same system later that day: Measured with the runtime of release 2.3.0, at the end of this section, says what was seen and what was not run. The test suite of rag_core holds the text of the macros and runs the Python of the job.

Who hands a lock back. A step that fails hands the run lock back by rewriting the ledger without that row — copy, drop, promote, save — and then writes a NOTE that begins with its name and says the run lock was released so the run can be retried. The steps measured above did that whether the run held a lock or not. Seen in those runs: a purge that had gone through, a preview of a purge and a RAG - Register Setup that failed after RAG - Load Vector Store had already written the ledger each rewrote the ledger once more and wrote the NOTE. A run that the lock of another run had refused did the same by the code, and saved the ledger with the lock row of the other run in it. Now only a failing run whose own lock row stands in the ledger rewrites it and writes the NOTE. A run that another run's lock refused and a step that fails after the ledger was written leave the ledger alone, a purge that went through has written the ledger without its lock row and does not write it a second time, and none of them says that a lock was released. A preview of RAG - Purge Documents takes no lock at all (retention and erasure).

The job hands its lock back. Up to this change the job appended its lock row before its Python program looked for the lock of another run, and only a run that went through took the row out again, by storing the ledger. A run that failed left a fresh lock row behind, and a run that another lock had refused left a second one. The next run of the job or of the flow was then refused for 30 minutes with nothing running: another ingestion run appears active for this ledger (run lock held) - retry later. The row carried no run id, so nothing could tell it from the lock of another run. The job now makes its run id in SAS, as RAG - List Documents does, and writes it into the lock row. It looks for a fresh lock of another run before it appends; a run that is refused appends nothing, exports the ledger once and leaves the table and its saved file as they are. SAS refuses such a run before the Python program looks, so the message ends the run as it stands above, without RuntimeError: in front of it. A run that failed after it took the lock copies the ledger without the row that carries its own id, drops the table, promotes and saves the copy, and writes NOTE: RAG ingestion: the run lock was released so the run can be retried. The ledger keeps its column types. A lock row with an empty run id — written by a job definition that was not manifested again — is the lock of another run to the job and to the steps: it refuses while it is less than 30 minutes old, is ignored afterwards, and stays in the ledger until a run that goes through writes it.

One limit, read from the code and not measured. A lock row carries the time of the SAS clock, and the Python programs of the job and of the steps compare it with their own clock, which is UTC. In a compute session whose SAS clock is not UTC — the option TIMEZONE — the two differ by the offset. East of UTC the Python program of the job then still takes for fresh a lock row that SAS took for stale: such a run has appended its own lock, hands it back, and its message does carry RuntimeError:. The sessions of the test system run in UTC.

More than one lock row. A run that crashes leaves its lock row behind; 30 minutes later the next run ignores it and appends its own beside it, and the stale row stays until a run that goes through writes the ledger. The job and the steps RAG - List Documents, RAG - Load Vector Store and RAG - Purge Documents take the newest lock row to decide whether another run holds the lock. They took one row, whichever CAS returned first or last, so a stale row could hide the lock of a run that was at work. No such ledger had come about on the test system by itself; the measurement below made one.

The job ends as failed when the run failed. Ingest-Documents.sas never raises a SAS error, so up to release 2.2 SAS Job Execution reported every run of it as completed and the outcome was in the log only. The program now sets SYSCC as its last statement when the run failed, and SAS Job Execution then reports the job as failed. It still runs to its last statement; nothing aborts. That statement was measured for the job RAG - Register Setup generates from a flow, which ended as failed (the job generated from a flow), and later the same day for Ingest-Documents.sas (below). Two ways out of the program used to leave no milestone for the Prompt Builder either: a saved ledger that cannot be loaded, and a compute context without the requests package. Both now write the milestone Ingestion failed: … that every other failure writes, so Launch ingestion shows The ingestion run did not succeed where it showed Run finished. The ingestion ledger is below.

The job stores a ledger only after a run that went through. The job stored rag_ledger_out.json whenever that file existed in WORK. In a SAS session that had run the job before, a later run that stopped early found the file of the earlier run and stored that ledger again, over the saved file. A job started by SAS Job Execution has a WORK of its own and was not affected. The two files the job reads the ledger and its lock from, rag_ledger_in.json and rag_ledger_lock.json, stayed in WORK as well: in a SAS session that had run the job before, a run that found no ledger in memory exported none and read the two files of the earlier run — that ledger as its own, and its lock as the lock that was written. The job now deletes both before it exports anything and says so (NOTE: RAG ingestion: rag_ledger_in.json of an earlier run of this SAS session was deleted from WORK); a file that is there and cannot be deleted stops the run. The line is written for each of the two files that is there: for both after a run that took a lock, for rag_ledger_in.json alone after a run that was refused, and for none after a run that had no ledger.

The run id. A run is named run-<epoch>-<ten digits>, and rag_runs is keyed on that name and shared by every project in the database. The digits were &sysjobid in the steps and the process id in the job, and neither told two sessions apart: twelve flow runs of the measurements above, each in a compute server of its own, ended in -344, the four other runs with an id a step had made in -343 or -345, and the job runs in -400 to -408. Two runs that started in the same second could therefore get the same id; no such collision was seen. The steps and the job now take the ten digits from a UUID, in SAS (&sysjobid only where UUIDGEN returns nothing); the lock row of the job carries the id. The Python program of the job makes an id with ten random digits only where SAS hands it none. Ids written before keep their form and are read as before. The epoch in the id is the time of the SAS clock — in the steps as before, and now in the job, whose Python program made the id from its own clock up to release 2.2. What that means for started_at is said under run history.

Measured with the runtime of release 2.3.0, on 2026-10-11 on SAS Viya 2026.09 with pgvector, in the SAS Studio compute context. The job ran in SAS Job Execution and, where one SAS session had to hold several runs, as a program in a compute session. The flows ran as the code SAS Studio generates for them and were not clicked in SAS Studio. The lock of another run was that of a flow that really ran; the old and the stale lock rows were appended by hand.

  • A job run that fails after it took the lock, on a CHAR and on a VARCHAR ledger, with one parameter of the configuration changed. The log held, in this order: NOTE: the ledger … holds its text columns as char - the run lock is written the same way (or as varchar); the append of one row; NOTE: Python-Subprocess - RAGINGEST Ingestion failed: RuntimeError: configuration drift: …; a table <ledger>_R with the 4 rows the ledger had before the run, its promote and its save; NOTE: RAG ingestion: the run lock was released so the run can be retried; and ERROR: RAG ingestion failed: RuntimeError: configuration drift: …. The ledger then held the same 4 document rows, no lock row and the column type it had. The job run again five seconds later was not refused and completed.
  • A job launched while the flow of the same ledger runs. No append and one PROC JSON step; the milestone Ingestion failed: another ingestion run appears active for this ledger (run lock held) - retry later and the same text behind ERROR: RAG ingestion failed:, without RuntimeError:; no <ledger>_R and no line about a released lock. Where a setup embeds​

The documents of a collection and the question asked of it have to be embedded by the same container: a question embedded somewhere else searches the collection with the wrong vectors, and nothing reports it. The Builder therefore resolves the embedding endpoint of a setup once — the SCR endpoint option of the Prompt Builder object, and <SAS Viya host>/llm where that option is blank, the host being the SAS Viya host option or the address the page is opened at — and gives the same value to everything it generates and starts. (A stored setup that names an endpoint of its own, embedding.scrEndpoint, keeps it ahead of the option; the Builder itself never writes one.)

Receives it as
The ingestion job, at Manifest setup and at Launch ingestionthe parameter scrEndpoint
The Embed step of the generated SAS Studio flowthe step option _rgem_scrEndpoint
Test retrievalthe parameter scrEndpoint
The retrieval modelthe constant EMBED_ENDPOINT in its MANIFEST block

With a blank option, that address has to be reachable from the compute session of the ingestion and from the destination the retrieval model is published to. Where the page is opened under a name that is not — a port-forward, an alias of a reverse proxy — set the SCR endpoint option.

The value is written at Manifest setup. A job definition, a flow and a retrieval model generated earlier keep what they were generated with until the setup is manifested again; a launch from the page always passes the current value, a scheduled run of the job and a run of the flow in SAS Studio do not.

The retrieval model looks for the endpoint in this order and takes the first that is not blank:

  1. scr_endpoint in the options input of the call,
  2. the environment variable RAGEMBED_ENDPOINT on the destination,
  3. the manifested EMBED_ENDPOINT,
  4. SAS_SERVICES_URL + /llm, where the variable is set — a compute session sets it.

Up to release 2.2 the fourth came before the third, so in a compute session the question was embedded at <SAS Viya host>/llm whatever the setup had been manifested for. The order is part of retrieve_context.py: a model has it once deploy-rag-content has published the current template and the setup has been manifested again.

TLS verification in the retrieval model​

The retrieval model — registered by Manifest setup of the Builder, or by the custom step RAG - Register Setup in SAS Studio — makes two HTTPS calls itself: to the embedding container, to embed the question, and — only in a compute session, where a session token exists — to the credentials service. It verifies both against the CA bundle of the deployment, and two environment variables per call decide how:

CallCA bundleVerification on or off
Embedding containerRAGEMBED_CABUNDLERAGEMBED_SSLVERIFY
Credentials serviceRAGSTORE_CABUNDLERAGSTORE_SSLVERIFY
  • <prefix>_CABUNDLE names the bundle and defaults to /security/trustedcerts.pem. When that file does not exist where the model runs, the model verifies against the certificates Python trusts by default, and a certificate signed by the deployment's own CA is refused.
  • <prefix>_SSLVERIFY set to false, no or 0 switches verification off on that destination; set to true, yes or 1 it switches verification on. The variable wins in both directions.
  • When the variable is not set, or holds any other word, the constant SSL_VERIFY in the MANIFEST block of the model decides. The Builder writes it from the option Verify TLS certificates in manifested models (sslVerify) of the Prompt Builder object: True while the option is ticked, which is the default, and False while it is not. The custom step RAG - Register Setup writes it from a checkbox of its own, in the same way — see the checkbox of the custom step.

So the option is a default written when the setup is manifested. A retrieval model that is already registered keeps its constant until Manifest setup runs again, and RAGEMBED_SSLVERIFY=true and RAGSTORE_SSLVERIFY=true on a destination turn verification back on for a model manifested without it. While the option is not ticked, the step shows a warning at Manifest setup before the click, and the model it registers carries the tag TLS-Verification-Off in SAS Model Manager — Deployment of Decisions shows how to list such models. Manifesting the setup again with the option ticked writes SSL_VERIFY = True and removes the tag. The tag follows the score code the model holds: when SAS Model Manager refuses retrieve_context.py, the manifest stops at that stage with the HTTP status and leaves the score code and the tags as they were, and a tag that could not be written or removed is named in the outcome beside the button. When the upload of retrieve_context.py gets no usable answer — the connection drops, or an ingress answers with its error page — the page reads the file back: when the setup holds it, the manifest goes on; when it does not, the manifest stops at that stage and says so. Only when it cannot be read back either does the manifest stop with it is not known whether SAS Model Manager stored retrieve_context.py, leaving the tag as it was; until Manifest setup has run through again, the tag may then not match the SSL_VERIFY line the model holds. This was driven against a stand-in for SAS Viya, not against SAS Viya.

What the option does not touch:

  • The ingestion job, the generated flow and Test retrieval. They run in a compute session, where the bundle is mounted, and verify as before.
  • The connection to the vector store. Its TLS is the option RAG: vector store TLS (storeSslmode) and the sslmode of the store.
  • A model registered with the custom step RAG - Register Setup. The step does not read the options of the Prompt Builder object. It has a checkbox of its own for the same setting — see the checkbox of the custom step.
  • A template deployed before release 2.3.0. The retrieve_context.py under <content root>/models then has no SSL_VERIFY constant. Manifest setup succeeds with it, and the model verifies whatever the option says. With the option not ticked, the outcome beside the button says that verification is still ON and that the template has to be deployed again, and the model is not tagged. Run deploy-rag-content to publish the current retrieve_context.py: the next Manifest setup writes SSL_VERIFY = False and tags the model.

Switching verification off is for a destination that runs Python where the bundle is not mounted — the case found with SAS Micro Analytic Service, which Deployment of Decisions describes together with the mount that keeps verification on. That mount is the fix for production; verification off is for a test system on a closed cluster network. The mount was measured there with a decision template, and with a prompt template with the included LLM call. A retrieval model was published there after the mount as well. Without the credentials of the vector store it answered no vector-store credentials resolved; with them passed in options it returned chunks, with SSL_VERIFY = True in its score code — see the retrieval model in a decision. The call to the credentials service is not made when the credentials come with the call or from the environment — the two cases that were run — so the verification of that one call in SAS Micro Analytic Service is not measured.

Both Launch ingestion and Test retrieval need the ingestion compute context option (ragComputeContext) to be set — SAS Job Execution rejects a job that does not name one, and the rejection carries no log. The Builder checks first and names the missing setting. The optimization compute context of the same Options pane does not count: it is a different option, for a different job.

Enrichment: an LLM call per chunk​

Off by default. A chunk that reads perfectly in place is often meaningless on its own — "revenue grew 12%" says nothing about whose revenue, or when — and the published remedy is to prepend a short LLM-written statement situating it in its document, then embed the two together. The Builder's Enrichment section is that slot, and it is general: the same call can classify a chunk, pull out an effective date, or flag personal data. Which of those it does is decided by the prompt, not by the pipeline.

The prompt is a Prompt Builder artifact, not a setting here. Build and evaluate it in the Prompt Builder, manifest it, and point the RAG setup at that Model Manager model. The prompt then has its own documentation, versions and permissions, and improving it does not mean editing a RAG setup.

It must be manifested with the integrated LLM call. That option makes the score code perform the call and return the answer, which is what the ingestion reads. The other form returns llmBody/llmURL for the Call LLM node of SAS Intelligent Decisioning — the request to make rather than its result — and the Builder and the ingestion both refuse it by name.

Only prompts manifested with output parsing are offered. Those are the ones whose answer is a set of named variables, which is exactly what this stage stores — the Prompt Builder tags them Output-Parsing when you manifest them that way. The project list is built from those prompts, so a prompt project holding none of them never appears rather than appearing and then being empty. If a prompt you expect is missing, re-manifest it with output parsing.

Several prompts, one after the other​

The stage is a list. Situating a chunk and extracting fields from it are different jobs, and one prompt asked to do both is worse at each — so Add another prompt runs a second, a third, over the same chunks, in the order shown. Each sees the chunk as the chunker produced it, not as the previous prompt left it.

Two rules hold across the chain, and both are refused rather than resolved silently, in the Builder and again in the ingestion:

  • Only one prompt may write the context header. A chunk has one, so a second would overwrite the first — after you had already paid for it, one LLM call per chunk.
  • Two prompts may not store the same column, for the same reason and with no way to tell afterwards which prompt wrote what.

enrich_version holds every prompt that contributed to a chunk, comma separated, so a chunk can say that its header came from one prompt and its clause_type from another.

The cost is the obvious one: each prompt is its own LLM call per chunk, so two prompts cost twice as much as one. The run log prices each separately and rag_runs records the total.

Nothing is guessed for a prompt input whose name is unfamiliar: a silently wrong mapping produces a whole corpus of confident nonsense, so the setup will not save until every input is mapped.

What the extracted values become​

A stored output is a real column, named after the output and typed from the prompt's registered output variables — a string becomes text, a decimal becomes a double, so a confidence score can be averaged rather than parsed out of a JSON blob. Retrieval returns them alongside the chunk.

Three rules govern the schema, and all three are reported in the run log rather than applied quietly:

  • A new column is not backfilled. Add an output to the prompt and the column appears on the next run, holding null for every chunk written before it. That is indistinguishable from an LLM that had nothing to say, so the log states it explicitly; only a full re-ingestion (bump the pipeline version) fills it in.
  • A column you stop producing is not dropped. It keeps whatever the prompt that wrote it said. Removing data is never a side effect of editing a prompt.
  • A name the table already uses is refused, by name, in the Builder and in the ingestion. score, content, page and rank are all plausible things to ask an LLM for and all belong to the chunk schema — rename the output in the prompt, or don't store it.
  • The column is the output name in lower case. Both pgvector and SingleStore fold an unquoted identifier, so an output called Department becomes a department column. Nothing else about the name changes — a stored output is never prefixed or abbreviated.

Latest, or pinned​

Latest re-reads the prompt on every run, so improving it in the Prompt Builder changes what the next ingestion writes — without re-processing anything already stored. Pinning freezes a version, which is what you want once a corpus is in production and you want a prompt change to be a deliberate act.

Either way, every enriched chunk records which prompt at which version wrote it in enrich_version, so a collection that legitimately holds work from two prompts can be read that way rather than merely being that way.

Version labels (1.0, 1.1) are not unique — the Builder shows the date beside each and stores the version's id.

A pinned version can lose its files

A version's snapshot does not always keep its score code — an older model on our own environment returned its file listing but no content. Both the Builder and the ingestion refuse an empty prompt rather than running one, naming the version. If a pin stops working, pin a different version or return to Latest.

What it costs, and what that buys​

One LLM call per chunk, repeated on every re-chunk — this is normally the largest line in an ingestion, an order of magnitude above the embedding. It is priced in the run log while the run is happening, and recorded per run in rag_runs (enrich_calls, enrich_input_tokens, enrich_output_tokens, enrich_seconds, enrich_failed) so RAG_RUN_COST reports embedding and enrichment side by side with a total.

A prompt manifested without the prompt_length and output_length outputs returns no token counts, and a token-priced model then has nothing to multiply. That reads as unknown rather than as zero — select those outputs when you manifest the prompt if you want the cost.

On the benefit: the widely cited 35–49% reduction in retrieval failures comes from one vendor on one corpus, with a Claude-class model generating the headers, and the affordable price in that write-up depends on prompt caching over the parent document, which a self-hosted container does not have. Treat it as a technique to measure on your own corpus, not as a number to expect. The cheapest first check is Test retrieval, which shows the stored header beside each chunk once a collection has been enriched.

Consequences worth knowing before you turn it on​

  • Enrichment is deliberately NOT part of the drift fingerprint. Changing the prompt, the mapping or the stored outputs applies from the next run onward and never demands a re-ingest. The trade is explicit: a collection can hold headers written by two different prompt versions, and enrich_version on each chunk is what makes that visible. The drift guard still covers the chunker, the token window and the embedding model — the settings that change the vectors themselves and would make a collection unreadable.
  • A hallucinated header is permanent and invisible at query time. It is baked into the vector and into the stored chunk. Read a few through Test retrieval before building a large corpus on a new prompt.
  • Failure is per chunk. A call that fails, or a response that was not the JSON the prompt asked for, leaves that chunk without a header and it is embedded plain rather than failing the run. A parsed output is never stored from the prompt author's default value — a plausible answer no model generated is worse than none. The count is named in the run log and in the run summary, because a corpus where a tenth of the chunks have no header retrieves differently from one where all of them do.
  • The prompt's score code is executed in the ingestion compute session, exactly as SAS Container Runtime would execute it. That is what scoring a model is; the control is Model Manager permissions on the prompt project. Do not point a setup at a model you would not run.
  • A prompt calling a hosted LLM needs that provider's key in the same credential domain as the store credentials, under the provider's name (OpenAI, Anthropic, …). A prompt whose LLM runs as a local container takes no API key and needs nothing. The mapping from model to provider lives in rag_core/providers.py; a model missing from it fails at load with that said, rather than sending a wrong key on its behalf.

In a SAS Studio flow the stage is the RAG - Enrich Chunks step, wired between Chunk Documents and Embed Chunks. The Builder adds one step per prompt to the generated flow, in order, and adds none at all for a setup that does not enrich. Chaining the step by hand does the same thing: each run adds to what the last one wrote rather than replacing it.

Two prerequisites that are not optional​

Both of these produce confusing failures if missed, so check them first.

1. A compute context that runs as the requesting user​

The steps create a CAS session in SAS and reuse it from Python, because the staged table has to be visible to the promote that follows. CAS only lets an identity reconnect to its own session.

The stock SAS Job Execution compute context runs the server as a service account (sas-be-sa on a default deployment) while the CAS session belongs to the user who launched the job. The two do not match, and the first step fails. The step detects this and says so, but the fix is environmental:

Run RAG flows and jobs in a context that runs as the requesting user. The SAS Studio compute context does; a full five-step ingestion is verified running there as a job.

Submit with that context explicitly:

{ "arguments": { "_contextName": "SAS Studio compute context" } }

For jobs launched from the Builder, that context is the option RAG: ingestion compute context (ragComputeContext) of the Prompt Builder object. It is deliberately not the option Optimization: compute context (computeContext): the prompt optimization job is commonly run in the stock context, which is exactly the one that does not work here.

The same service-account mismatch also prevents credential-domain lookups, so one context change fixes both.

2. A credential domain holding the store credentials​

Vector-store credentials come from a SAS Viya credential domain (default agentic-ai-keys), never from the flow. Entries are backend-prefixed so one domain can serve several stores:

PGVECTOR_RAG_USER      PGVECTOR_RAG_PW
SINGLESTORE_RAG_USER   SINGLESTORE_RAG_PW

The same domain also carries where each store lives. These are not secrets, but the domain is the one place every identity can already read, so the Builder resolves the connection instead of asking users for a hostname they should never have to hold:

PGVECTOR_HOST     PGVECTOR_PORT     PGVECTOR_DB     PGVECTOR_SSLMODE
SINGLESTORE_HOST  SINGLESTORE_PORT  SINGLESTORE_DB  SINGLESTORE_SSLMODE

RAGSTORE_* is the unprefixed fallback for any backend, the same precedence the runtime already applies to a .env. A value passed explicitly — a host typed into a step — still wins over the domain, so the steps are unaffected. Without <BACKEND>_HOST and <BACKEND>_DB the Builder shows the store as unresolved and refuses to save a setup that could not ingest.

Each run is recorded in three tables in the vector store's own database, beside the chunks they describe:

TableContents

The database copy is authoritative; the CAS copy is disposable and rebuildable.

RAG - Load Vector Store, the step of the flow, and Ingest-Documents.sas — Launch ingestion, or the ingestion job of a setup — publish the same two tables: every run the store holds for the collection (the newest 500) and their document events (the newest 5,000), not only the run that publishes, with the 35 and 10 columns, the measures as numbers and everything else as text, promoted and saved in the caslib of the pipeline tables. For the job <project> is its ledger table without the ending _LEDGER, which is the table prefix of a setup. A run that finds nothing to do publishes too, so one more run of a setup brings the runs before it into CAS, as far as the store recorded them.

The job publishes since release 2.3.0; before, only the step did. Measured on 2026-10-11 on SAS Viya 2026.09, with the job as it was: <project>_RUNS still had 3 rows after a job run on pgvector, and on SingleStore the store held four runs of a collection while the CAS copy held three. On 2026-10-11 and on 2026-10-12 the pull of the log chain found the ledger of a setup that the Prompt Builder had ingested in memory and its <project>_RUNS not.

The job as it publishes ran on the test system later on 2026-10-12, in six SAS Job Execution jobs with a content folder, a table prefix and a collection of their own; every job ended as completed:

  • A first run of three documents, with one file excluded: <project>_RUNS with 1 row and 35 columns - 13 VARCHAR and 22 DOUBLE - and <project>_DOC_EVENTS with 4 rows and 10 columns, both promoted and saved, with the NOTE below above the last line of the log. Set against a run table the step had published on 2026-10-11, no column differed in name, type or label; two differed in length, and one of the document events.
  • A run that found nothing to do: 2 rows and 5 events. A run with one changed document: 3 rows and 7 events.
  • With the run history switched off the log had no line about the history, and both tables and their saved files were as the run before had left them.
  • Both tables dropped and their files deleted, then a run: 4 rows and 8 events - every run the store held. The run with the history switched off is not among them: it is not in the store.
  • With the rag_core of before this change in the content folder the job wrote the milestone rag history: not read for CAS (ImportError: …) - the ingestion itself is unaffected and the WARNING, left both tables as they were and ended as completed.

The tables were read back in a compute session, not in jobs. The pull and the link of the log chain then found those runs - see The Third Run. Not provoked: an upload that fails, a row count that differs, a promote or a save that is refused. Changed after those runs and not run in SAS: the reason of a history that could not be read reaches SAS through the function of the logging programs, so in the WARNING and in the milestone a quote shows as a backtick, % as pct, & as + and a semicolon as a comma, a comment mark is split, and the reason ends after 200 characters.

The two differ in three points. With the history switched off, and for a table the store holds no rows for, the step drops the CAS table and deletes its saved file (read from its program); the job leaves the table as it is. The job puts an upload in the place of a table only when it holds every row that was read. And a history the job cannot read or publish is a WARNING in its log — WARNING: RAG ingestion: the run history ... was not published ... — while the run stays one that went through; the next run publishes the history again. A run that published writes this line above its last line:

NOTE: RAG ingestion: the run history was published to CAS, promoted and saved - <caslib>.<project>_RUNS with <n> rows and <caslib>.<project>_DOC_EVENTS with <m> rows.

The job definition RAG Ingest - <setup> holds a copy of Ingest-Documents.sas from the time the setup was manifested. After the RAG content is deployed again, Manifest setup has to run once for a setup before its job publishes. RAG - Purge Documents writes no row to either table (retention and erasure).

started_at of a run is the epoch in its run id, read as UTC, and the steps and the job take that epoch from the SAS clock of the compute session. On the test system, whose sessions run in UTC, started_at was the start of each run (measured on 2026-10-11, for 20 runs of one collection). In a compute session whose SAS clock is not UTC — the option TIMEZONE — it is off by the offset to UTC, while finished_at, which Python writes from its own clock, is not. For a run of the job that is new with release 2.3.0: up to release 2.2 the Python program of the job made the id from its own clock. Read from the code, not measured.

History never fails a load. If the store refuses the write, the ingestion still stands and the log says so.

Skipped is not failed​

A document the pipeline decided not to ingest — no extractor for its format, a source file with code ingestion off, a scanned PDF with no text layer — is recorded as skipped with the reason. failed is reserved for something a person can fix. Collapsing the two made every run look broken and hid the rows that were. Both are counted separately in rag_runs (docs_skipped, docs_failed), and every skipped document is named in the run log, grouped by reason.

The summary of RAG - Extract Text counts such a document as skipped as well. A new document in which the extractor finds no text — an empty file, a PDF that holds only scans — was counted there under documents extracted and under extractors used, although rag_core hands it back as skipped. It is now counted as skipped, with the reason in the line rag skipped: 1 - <extractor> found no text (empty or scanned-only document) above the summary: three unchanged documents and one empty file give 0 documents extracted, 0 failed, 3 skipped as unchanged, 1 skipped and no line extractors used. Measured on 2026-10-11 on SAS Viya 2026.09 with an empty .txt file: the step logged rag extract: 0 extracted, 1 skipped, 0 failed and rag skipped: 1 - plaintext found no text (empty or scanned-only document) with the path of the file, and no line extractors used. The summary of that run read 0 documents extracted, 0 failed, 3 skipped as unchanged, 1 deleted, 1 skipped, because a file had been taken out of the folder before it. With one more new document it read 1 documents extracted, 0 failed, 3 skipped as unchanged, 1 skipped, followed by extractors used: plaintext=1. Measured the same day for an excluded code file beside three unchanged documents: 0 documents extracted, 0 failed, 3 skipped as unchanged, 1 excluded.

docs_skipped is added to an existing rag_runs table by an additive migration on the next run, and so are docs_excluded — the documents the deployment excludes, a source file with code ingestion off — and the six enrichment columns: a collection built before the Enrich stage existed keeps answering, and its runs simply record no LLM cost. A run reads which columns rag_runs has and adds only the missing ones, so an upgraded deployment needs no manual DDL where the store user of the ingestion may alter the table — on PostgreSQL that is its owner. Where it may not, the Load step logs rag history: not recorded (… must be owner of table rag_runs, nothing is written for that run and the ingestion itself is not affected, until the owner runs an ingestion or a DBA runs ALTER TABLE rag_runs ADD COLUMN docs_excluded integer DEFAULT 0 once.

Before release 2.3.0 a run wrote docs_excluded to a table that had no such column, so by the code every write to rag_runs failed and no run was recorded; the runs of that time are not backfilled.

Measured on 2026-10-11 on SAS Viya 2026.09, with pgvector and with SingleStore 9.0.40:

  • Every run wrote its row. The logs said rag history: run … recorded, and rag history: not recorded stood in none of them. On pgvector the CAS copy <project>_RUNS held 35 columns, docs_excluded among them, and grew with the runs of the flow, to 19 rows.
  • The column is added to a table that exists. On SingleStore rag_runs had 34 columns and no docs_excluded before the first run and 35 with it after; the two runs in between added two rows to rag_runs and three events to rag_doc_events. That table is shared by every collection in the database, and the accelerator does not take the column out again: the first run of this release changes rag_runs for good.
  • The count is written. With one source-code file in the documents folder and code ingestion off, the two runs that followed — the job and the flow, on pgvector — had docs_excluded 1, and the 17 runs before them 0.

Not measured: a store whose user may not alter rag_runs, and with it the line must be owner of table rag_runs; a store that does not say which columns a table has; whether an older runtime that is still deployed elsewhere writes its rows to a rag_runs that has the new column; and docs_excluded other than 0 on SingleStore. The tests run the first two against a stand-in for the connection.

The run log also states what the embedding and the enrichment cost while the run is still on screen, and spells out where the chunk token budget came from — it is the setup's chunk window minus the estimator's safety margin, not a limit the model imposed.

Security posture​

Secrets. Store credentials live only in the credential domain, resolved per identity at run time. They are never written to a flow, a CAS table, a WORK file or a log. The .env file is git-ignored and is read only by the admin scripts on your workstation. On SCR and MAS destinations — which have no SAS Viya session — the same names are supplied as environment variables.

The address of the vector store. Host and database are configuration, not a credential, and they stand in the log: the summary of RAG - Load Vector Store names the vector store. One line of it reads NOTE: <backend> collection <collection> on <host>/<database>, with the host as it is set for the step — an IP address on the test system (seen on 2026-10-11 with SingleStore: singlestore collection zz_verify_s2_v1 on <host>/SASModel). The line after it names the credential domain and the name of the entry the user was read from (<BACKEND>_RAG_USER), not its value: user and password come from the credential domain, and the summary holds neither. Seen on 2026-10-11 with pgvector, as two lines that follow each other: NOTE: pgvector collection zz_verify_r12s_v1 on <host>/postgres and NOTE: credentials resolved from domain agentic-ai-keys (PGVECTOR_RAG_USER). A search of that flow log for the words password, user name, credential, secret and API key found that one line outside the echoed program; such a search does not show that the name of the account stands nowhere as a bare value. The summary is part of the log of every run that reaches the step, so the address of the store is in the job log of every run of a flow that is scheduled as a job, for everyone who may read that log.

What crosses which boundary. Document text leaves the source only to reach the extractor, the embedding container and the vector store, all inside your deployment. The embedding model runs as a governed SCR container you publish.

Two settings can change that, and both are explicit choices:

  • an embedding model that forwards to a hosted API (the fact sheet's deployment_type says which) sends the chunk text to that provider;
  • an Enrich stage whose prompt calls a hosted LLM sends the chunk, and whatever else the mapping gives it — including up to 20,000 characters of the surrounding document — to that provider, once per chunk.

Both are visible on the setup, and neither happens by default: the shipped embedding default and every enrichment prompt built on a locally served model stay inside the deployment.

Identity. Everything runs as the identity that launched it, which is why the run-as-requesting-user context matters: it keeps the audit trail truthful as well as making the steps work.

Error text. Database error messages are stored in the ledger's error_text and shown in step summaries. Some stores put internal cluster hostnames in their own error messages, so that column can contain infrastructure detail. Treat the ledger table as internal, or restrict the caslib holding it.

What is not encrypted by the accelerator. Chunk text and embeddings sit in your vector store in the clear. Encryption at rest is the database's responsibility. TLS to the store is configurable per backend (sslmode for PostgreSQL, on/off for SingleStore) and defaults to enabled.
