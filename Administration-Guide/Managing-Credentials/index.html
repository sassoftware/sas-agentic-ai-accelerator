Managing Credentials

The accelerator can resolve every external secret it needs — LLM provider API keys and RAG vector-store passwords — from a SAS Viya credential domain instead of governed tables or report-assigned data. Credentials are then centrally administered, per-user or per-group, and never stored in a CAS table or report definition. The Prompt Builder additionally uses this to show each user only the models they actually hold a key for.

The model: one domain, named entries, per-identity credentials​

One credential domain (for example agentic-ai-keys) serves the whole deployment — its name is the single value configured in the app Options. A credential in the domain belongs to a user or group and carries a map of named secrets:

Entry nameHolds
OpenAI, Anthropic, Google, AzureOpenAI, …LLM provider API keys — named after the KeyName each model definition's API_KEY option references (key_name in definition.yaml), because the Prompt Builder, its RAG Builder part included, looks a model's key up under exactly that name
PGVECTOR_RAG_USER, PGVECTOR_RAG_PWRAG vector-store credentials — the prefix names the vector DB backend
SINGLESTORE_RAG_USER, SINGLESTORE_RAG_PW, …further vector-store backends; one domain serves several stores side by side

Who resolves what:

  • A group credential (for example for LLMConsumers) equips every member at once — and nobody else. The credential has to go to a group the people who open the Prompt Builder are members of. A credential for a group they are not in is written without an error and mdb credentials-report shows the group holding it, and those users still find the models of the provider disabled in the Prompt Builder, with this note:

    No <provider> key available in the <domain> credential domain - ask your administrator for access.

    The examples on this page use LLMConsumers for those people: it is the group for everybody who needs access to the LLM repository, and mdb setup writes the commands that create it into sas-viya-cli-commands.txt (see Setup SAS Model Manager). A site that equips another group names that group instead — what counts is the membership, not the name.

  • A user credential belongs to one person and overrides the group credential entirely — a personal set of keys.

  • A user with neither, or with a map that lacks a specific entry, sees the affected models greyed out in the Prompt Builder with a note naming the missing entry and the domain — access to keys is an identity decision, not an application setting.

Connection configuration — vector-store host, port, database name — is not a secret and stays in the RAG setup, never in the credential.

Creating and updating: the CLI workflow​

Multi-entry credentials are authored with the shipped scripts create-credential-domain.ps1 (Windows) / create-credential-domain.sh (Linux/macOS), which authenticate through your sas-viya CLI session:

  1. Sign in once: ./sas-viya auth login.

  2. Keep your secrets where they already live: the accelerator's git-ignored .env file. The script reads it directly — no second secrets file to author or clean up. Provider key variables map onto their provider entry names, and every <BACKEND>_RAG_USER / <BACKEND>_RAG_PW pair is carried over verbatim (uppercased); everything else in the .env is ignored:

    .env variableDomain entry
    OPENAI_API_KEYOpenAI
    ANTHROPIC_API_KEYAnthropic
    GEMINI_API_KEYGoogle
    OPENROUTER_API_KEYOpenRouter
    AZURE_OPENAI_API_KEYAzureOpenAI
    MISTRAL_API_KEYMistral
    VOYAGE_API_KEYVoyageAI
    HUGGINGFACE_API_KEYHuggingFace
    AWS_BEDROCK_API_KEYAWSBedrock
    PGVECTOR_RAG_USER, PGVECTOR_RAG_PW, SINGLESTORE_RAG_USER, …same names

  3. Run the script per identity you want to equip:

    ./create-credential-domain.ps1 -IdentityType group -IdentityId LLMConsumers
    ./create-credential-domain.sh -t user -i myuser

    By default the repository's own .env is used. Point at a different file to manage multiple environments from separate .env files:

    ./create-credential-domain.ps1 -IdentityType user -IdentityId myuser -EnvFile C:\envs\prod.env
    ./create-credential-domain.sh -t user -i myuser -e /envs/prod.env

    For full control (custom entry names, no mapping), pass a raw NAME=VALUE file instead with -KeysFile my-keys.env / -k my-keys.env — its entries are stored verbatim.

The domain is created if needed and the identity's credential is fully replaced with the recognized entries (the source file must list every entry the identity should keep, not only new ones). Creating the domain and any group credential requires SAS administrator rights; a user can (re)run the script for their own user credential in an existing domain. Secret values are never printed.

Equipping many identities at once​

The scripts above equip one identity per run, which is right for a demo and wrong for a rollout. mdb does a whole deployment from a manifest, and reports what it did:

mdb credentials-init                        # write a starter manifest
mdb credentials-add group LLMConsumers      # add an identity to it
mdb credentials-apply --dry-run             # see the plan
mdb credentials-apply                       # do it
mdb credentials-report                      # who holds one
mdb credentials-remove group FormerTeam     # mark a credential for removal

credentials-init reads your .env and writes a manifest listing the entries it actually carries — names only, never a value — so you can see what is available to hand out before deciding who gets it. All five commands default to credentials.yaml in the working directory, and --manifest (-m) puts it anywhere you keep deployment records; credentials-init still reads --file / -f, the earlier name of the option. The manifest is the one place a rollout is managed from: identities are added to it, narrowed in it and marked for removal in it, and credentials-apply carries out what it says.

The manifest says who gets keys and where those keys come from. It never contains a key, so unlike the .env it is meant to be committed and reviewed in a diff — who may call which provider is a decision worth having a history of. A fuller example is credentials.example.yaml:

domain: agentic-ai-keys
source: ../../.env          # relative to the manifest

identities:
  - {type: group, id: LLMConsumers}
  - {type: group, id: RAGEngineers, only: [PGVECTOR_RAG_USER, PGVECTOR_RAG_PW]}
  - {type: user,  id: sas-be-sa}
  - {type: group, id: FraudAnalytics, source: ../../envs/production.env}
  - {type: group, id: FormerTeam, state: absent}

LLMConsumers stands for the people who open the Prompt Builder. Name the group your users are members of: a credential for another group is written, reported as held, and leaves them with the note No … key available in the … credential domain (see Who resolves what). After a run that plans or writes a group credential, credentials-apply prints one line to that effect, and credentials-report prints it where a group holds a credential: A group credential reaches only the members of that group, and a user's own credential replaces it for that user. Its last line names the report of the same manifest - mdb credentials-report --manifest <file> - or, for a run with --identity, of the same identities and domain. A path with a blank is printed in quotes.

Paths inside a manifest resolve against the manifest's own directory, not your working directory, so a manifest and the .env files it names can be kept together and moved together. credentials-init writes the source path relative when the two are near each other and absolute when they are not — a ../../../../../.. chain is correct and unreadable, and breaks the moment either end moves.

only narrows an identity to some of the entries, named the way the domain spells them (OpenAI, PGVECTOR_RAG_PW) rather than the way the .env does (OPENAI_API_KEY); a name the source does not carry is refused rather than quietly dropped. A single identity needs no manifest at all:

mdb credentials-apply --identity-type group --identity LLMConsumers --dry-run
mdb credentials-report --identity <user id> --identity-type user

--domain, --identity-type, --env-file and --keys-file belong to that mode. With a manifest the run goes to the domain the manifest names and takes the type and the key file of each identity from it. A --domain that names another domain is refused before the sign-in, because an apply also removes what the manifest marks absent; so is any --identity-type, --env-file or --keys-file. Two entries for one identity are refused by credentials-apply and credentials-report as they are by credentials-add, and so is an identity named twice with --identity. An empty value of any option (what a variable of the shell that is not set gives) ends the command with exit code 2 before anything is read or written, as does a --manifest that names a folder. An identity id and a credential domain hold printable ASCII alone (U+0020 to U+007E), with no blank at either end. Any other character - a line break, a control character, a blank such as U+00A0, an invisible one such as U+200B or U+034F, a letter outside ASCII such as ö - is refused with exit code 2 before anything is written or asked of SAS Viya, in a manifest, as an argument and as --domain; a manifest that lists such an id is refused by every credentials command that reads it. Every line names an id and a domain as they are and unquoted, and such a character can show as another one or as none.

A value of the manifest is taken only as YAML reads it. id, domain and source must be text, only a list of texts and verbatim true or false. YAML reads an unquoted 0123 as the number 83 and yes as true, so such a value is refused with exit code 2 before anything is written or asked of SAS Viya: <file>: identity <n>: 'id' must be a text, and YAML read a number there - put it in quotes ('0123', 'yes') to have it read as it is written. Write such a value in quotes (id: '0123'). mdb credentials-init, mdb credentials-add and mdb credentials-remove quote every value they write where YAML would read it otherwise, so --domain 2024 is written domain: '2024'. An id that is missing, empty or ~ is refused as no id; a domain that is missing, empty or ~ is agentic-ai-keys. An empty name in only names an entry no source carries, so the identity is not equipped. This was tested, not run against SAS Viya.

Adding an identity: mdb credentials-add​

mdb credentials-add <type> <id> adds a group or a user to the manifest, so the file need not be edited by hand. The type is group or user:

mdb credentials-add group LLMConsumers
mdb credentials-add group RAGEngineers --only PGVECTOR_RAG_USER,PGVECTOR_RAG_PW
mdb credentials-add group FraudAnalytics --source envs/production.env
mdb credentials-add user sas-be-sa --manifest deployment/credentials.yaml

The command edits the manifest and makes no call to SAS Viya; the credential is written by the next mdb credentials-apply, and the command prints that as its next step (mdb credentials-apply --manifest <file> --dry-run).

OptionMeaning
--onlyThe entries this identity gets, named the way the domain spells them. Repeat the option or separate the names with commas.
--sourceThis identity's own key file. The path is the one you type in the shell, relative to the working directory; it is written into the manifest relative to the manifest.
--manifest, -mThe manifest to edit. Default: credentials.yaml in the working directory.
--env-fileThe .env a new manifest points at. Default: .env in the working directory. Not read when the manifest exists.
--domainThe credential domain a new manifest targets. Default: agentic-ai-keys. Not read when the manifest exists.

What it does with the file:

  • Only that identity changes. Comments, blank lines, the order and the other identities stay byte for byte as they are - but for the two comment lines credentials-init writes above its placeholder, which leave with the placeholder. A new identity is written in block style (- type: group / id: …) after the last one; an identity that is written {type: group, id: …} keeps that style when it is updated.
  • The placeholder is replaced. A manifest from credentials-init names the identity CHANGE-ME-to-a-real-group; the first identity that is added takes its place. The comment about the placeholder above it leaves with it.
  • No manifest yet: it is written the way credentials-init writes it, from the .env, with the identity in place of the placeholder. Without a .env nothing is written.
  • The identity is already listed: no second entry is written, and the command says so and ends with exit code 0. With --only or --source the entry that is there is updated and the change is printed. An identity is the same one when type and id are equal, the id letter for letter.
  • A name the source does not carry is refused. An --only name that is not among the entries of the source, or a --source file that is not there, ends the command with exit code 2 and the message credentials-apply gives for it, and nothing is written.

The edit is made in the text of the file, because the YAML library mdb uses would drop every comment on a rewrite. Before the file is written, the result is read back and has to be the manifest that was there plus the one change. These layouts are refused with a message, and the file is left alone:

  • an identities list that is not written one - line per identity, for example identities: [{…}, {…}], identities: [] or identities: null;
  • an identity that is listed more than once;
  • an only: list that is to be rewritten and holds a comment between its entries, because nothing says which entry of the new list such a comment belongs to;
  • any other layout whose result does not read back as the manifest plus the one change, for example an only: that is an alias or an identity that takes a key through a merge (<<: *o). It ends with the manifest is laid out in a way this edit cannot be made in safely - nothing was written; edit the file by hand.

A file YAML cannot read is refused with the line and the column where the reader stopped, and nothing of its text is shown: a key file handed as the manifest would otherwise be printed with a value.

Removing a credential: state: absent​

A credential is removed through the manifest as well. An identity may carry state: absent:

identities:
  - type: group
    id: FormerTeam
    state: absent

mdb credentials-remove <type> <id> writes that line — on the identity that is listed, or as a new entry when the manifest does not list it — under the same rule as credentials-add: nothing else in the file changes. It does not contact SAS Viya. The credential is deleted by the next mdb credentials-apply:

mdb credentials-remove group FormerTeam
mdb credentials-apply --dry-run         # the plan shows the action "remove"
mdb credentials-apply                   # deletes the credential
mdb credentials-report                  # shows it as absent
  • credentials-apply plans the action remove for such an identity. A dry run shows it and removes nothing. A credential that is already gone is not an error: the run says that there was none to remove.
  • An identity with state: absent needs no source and no entries, so a credential can be removed after its key file is gone. A run that only removes does not create or update the domain.
  • credentials-report shows such an identity as absent (as the manifest says) once its credential is gone, and as STILL THERE (manifest: absent) while it exists. A credential that cannot be read is shown as unreadable with the answer of the service, and the lines below the table count it neither way: the line of the identities the manifest names ends ... hold a credential; <n> could not be read., and the line of those it marks absent ... hold none; <n> could not be read.
  • state: present is the default and may be written. Any other value is refused when the manifest is read, with exit code 2, before anything is written or removed.
  • mdb credentials-add on an identity that is marked absent sets it back to present and says so. The state line is taken out again, or rewritten to state: present where it is the first line of a block entry or where a comment stands on it. The comment stays as it is.

Nothing is removed because a line is missing from the manifest. The service cannot list who holds a credential, so mdb cannot know what a deleted line once said. Leave the entry in the file with state: absent until the report shows the credential as absent.

A refused read, removal or write of a credential names the answer of the service. A write shows the reason only for a 404 - for a group that does not exist, errorCode 12310, measured on 2026-10-14 - and not where the answer holds a value the write carried. The values are compared as the line prints the answer, every run of blanks, tabs and line breaks as one blank, and with the whole answer, also past the 300 characters a line shows of an answer that is no JSON. A request that gets no answer - a connection reset, a timeout - ends with one line, ... failed: no answer (<kind of exception>), that names nothing of the request. No traceback of mdb shows the locals of a frame. The id of an identity is percent-encoded as one segment of the address, so an id with #, ? or / names that identity and no other; . and .. alone are refused. Measured on 2026-10-14 in a second pass: an identity ZZ#X marked absent was asked for as .../groups/ZZ%23X, and SAS Viya answered 404 (errorCode 12302), its answer for a credential that is not there. ? and / were not tried.

credentials-add and credentials-remove were run on files. The removal by state: absent, the plan and the report that show it were measured on 2026-10-14 in a credential domain and a group made for the pass, with the commands as they were before the fix-up of that day: the apply created the domain and the credential of the group with its three entries; after credentials-remove the next apply deleted it - HTTP 204 - without writing the domain, and the report said absent (as the manifest says); an apply once more said that there was none to remove and ended with exit code 0; and a credential the manifest marked absent while it was there was STILL THERE (manifest: absent). The lookup the Prompt Builder makes found the group credential with lookupInGroup=true and answered 404 without it. Of what the fix-up of that day changed, a second pass that day measured three things: a write for a group that does not exist printed the reason of the service - storing the credential for group '<group>' failed: HTTP 404 The credential could not be created because the group identity "<group>" does not exist. (errorCode 12310) - and ended with exit code 1; the report printed the line about a group credential once; and a --domain other than the one of the manifest ended credentials-apply with exit code 2 before any request. The comment on the state: line, the refusal of an identity listed twice and the count of a credential that could not be read ran against a stand-in for the credentials service in the test suite of mdb, not against a SAS Viya server, as did everything changed after that pass.

A dry run cannot show you a diff

Reading a credential returns its metadata — who wrote it, and when — and never its contents, not even the entry names. So a dry run tells you an identity will be created, replaced or removed, but not what it holds today. That is a privacy property rather than a gap: no identity can ever see another's keys.

For the same reason there is no way to list who holds a credential. Both commands report on the identities you name, which is why passing the same manifest you applied gives you the after-picture of that rollout — and why a credential is removed by marking its identity state: absent, never by deleting its line.

Inspecting and deleting: CLI and Environment Manager​

A credential that is managed with a manifest is deleted through the manifest: mdb credentials-remove, then mdb credentials-apply (see Removing a credential). The standard tools delete as well — one credential, or the whole domain, which mdb never deletes — and they show the domain. Authoring the multi-entry map is the job of the scripts and of mdb credentials-apply:

./sas-viya credentials domains list
./sas-viya credentials domains show-info --domain-id "agentic-ai-keys"
# show-info never returns secret values
./sas-viya credentials users delete  --domain-id "agentic-ai-keys" --identity-id thatuser
./sas-viya credentials groups delete --domain-id "agentic-ai-keys" --identity-id LLMConsumers
./sas-viya credentials domains delete --domain-id "agentic-ai-keys"

A credential that is deleted with these tools while a manifest still lists its identity as present is written again by the next mdb credentials-apply: the apply writes every identity the manifest does not mark state: absent.

In SAS Environment Manager (as an administrator), Security → Domains lists the domain and its credentials per identity, and supports deleting them.

How the applications use the domain​

  • The Prompt Builder Options pane gets a Credential domain setting, defaulting to agentic-ai-keys — the same default the admin scripts use, so a deployment that runs a script needs no configuration at all. The Builder fetches the signed-in user's secrets map once at load time and disables models whose provider entry is missing (a note names the entry and domain). The domain is the only key source; enter none to skip the lookup in deployments that use exclusively key-less models - self-hosted ones, and definitions whose container holds the key (--auth env), which are never disabled for a missing entry. The setting is one option for every kind the Prompt Builder offers: prompt templates, decision templates and RAG setups read the same domain. none works for the two template kinds only. A RAG setup has no key-less mode — the vector store's user, password and location come from the domain — so with none the RAG setup card is shown disabled with that reason, and nothing RAG is requested.
  • The prompt-optimization job accepts the same domain name (keyDomain, same default) and resolves keys server-side under the identity its compute session runs as. That is only the launching user when the compute context runs its servers as the requesting user — see the service-account caveat below.
  • RAG ingestion and retrieval read the <BACKEND>_RAG_USER / <BACKEND>_RAG_PW entries the same way — the backend prefix (PGVECTOR_, SINGLESTORE_, …) lets one domain hold credentials for several vector stores at once. Ingestion (SAS Studio / Job Execution) runs under the calling user, so access to the vector store follows the same identity rules end to end.
  • The SAS code of an LLM call that the custom steps LLM - Create LLM Call (1.7) and LLM - Get Options (1.6) and the program Create-LLM-Call.sas write keeps the entry name in %let API_KEY=OpenAI; and reads the key of that entry when it runs, from the domain named in its line %let API_KEY_DOMAIN=agentic-ai-keys; and under the identity of its SAS session; the call sends the key in the place of the name. That line is written as it stands: the steps and the program do not read the Credential domain option of the Prompt Builder (credentialDomain). A site whose keys are in another domain edits that one line of the generated code. The key is not written to the log, and the macro variable options - what LLM-Call-Result-Table.sas puts into the result table - keeps the name. The request goes through the temporary file llmIn, which then holds the key: the code clears that fileref right behind the call, also behind a call that failed, and SAS deletes the file. Code of LLM - Create LLM Call 1.6, LLM - Get Options 1.5 and the program before this release left the file in the WORK folder until the SAS session ended - generate it again, or add filename llmIn clear; behind its PROC HTTP step. The code finds an entry whose name has letters, digits, ., _ and - only: it writes the name with COMPRESS (an entry named Azure OpenAI is looked up as AzureOpenAI and not found) and into a Perl expression that a / ends. The Model Definition Builder refuses any other name in key_name and in the API_KEY default of an options.json. Where the domain holds no such entry for that identity, the code writes WARNING: No key was read for the entry ... and sends an empty API_KEY. Code these programs wrote before sent the entry name as the key, and the provider refused it (401) - generate it again. See the README of SAS-Viya-Integrations/SAS-Code-LLM-Calls.

Where the domain applies — and where it cannot​

Resolving a credential requires a SAS Viya session: the browser (the signed-in user) and compute-session runtimes (SAS Studio steps, Job Execution jobs) have one. A SAS Container Runtime (SCR) container does not, and neither do the MAS and CAS scoring runtimes that published decisions and Intelligent Decisioning tests execute in. For those destinations the secrets are supplied as environment variables at deployment time, using the same names as the .env and the domain (for a vector store: <BACKEND>_RAG_USER / <BACKEND>_RAG_PW, e.g. PGVECTOR_RAG_USER; connection config: the RAGSTORE_* variables; the embedding call: the RAGEMBED_* variables), exactly like the LLM containers receive their configuration today. The manifested retrieval code takes the user and the password of the vector store from the options input of the call first, then from the environment variables, and asks the credential domain only for what is still missing after both, so the same artifact runs on every destination. Where the two variables are set, they are used and the domain is not asked. The LLM containers themselves are unaffected either way: they receive the API key per call via the options payload, resolved by the caller - except a definition built with mdb add --auth env, whose container reads the key from an environment variable filled from a Kubernetes Secret. Its options.json has no API_KEY, so no caller asks the domain for it and no identity needs an entry for it - once the callers built before the switch are rebuilt. RAG ingestion looks the entry of an embedding model or an enrichment LLM up in two static maps of rag_core/providers.py, and a model that is still in them is still asked for (needs the 'OpenAI' entry in the credential domain). After a definition is switched, regenerate the maps from the fact sheets and replace them in the module:

cd SAS-Viya-Integrations/RAG
python -m rag_core.providers --from ../../Embedding-Definitions/embedding_fact_sheet.csv
python -m rag_core.providers --llm-from ../../LLM-Definitions/llm_fact_sheet.csv

A model whose options.json has no API_KEY is left out of the map and needs no entry.

Without the two variables of the vector store the retrieval model does not fail the decision: it answers retrieval failed: RuntimeError: no vector-store credentials resolved: … in retrieval_status and returns no chunk. That is what it answered on 2026-10-11 in a test of SAS Intelligent Decisioning and in the publishing validation on a SAS Micro Analytic Service destination, where neither runtime had them. With the user and the password passed per call instead, in the options input of the model, the retrieval model returned chunks in both places the same day.

The two variables as environment variables were measured for SAS Micro Analytic Service, also on 2026-10-11: PGVECTOR_RAG_USER and PGVECTOR_RAG_PW were put into a Kubernetes secret and set on the containers of the deployment from it,

kubectl -n <namespace> set env deployment/sas-microanalytic-score --containers=* --from=secret/<name>

the pod restarted, and a call with {} as the options of the retrieval model returned retrieval_status ok and three hits. Not measured: the same variables for the test of SAS Intelligent Decisioning, which runs in CAS, and for a SAS Container Runtime container. The retrieval model in a decision lists every variable the model reads and where each destination takes them.

Service-account compute contexts. A compute context can be configured to run its servers under a shared service account instead of the requesting user (the stock SAS Job Execution compute context often is). A job running there resolves the domain as that service account — not as the person who clicked Optimize — so a personal credential is never found. Whether a context does this is its attribute runServerAs, which the answer of GET /compute/contexts/<id> holds as attributes.runServerAs. A context without the attribute runs as the requesting user. On SAS Viya 2026.09 the stock SAS Job Execution compute context has runServerAs set to a service account and SAS Studio compute context has none (read with the REST call on 2026-10-20).

The remedy is a compute context that runs as the requesting user: point the app's compute-context Option at it, and keys follow the per-user/group rules above. The Prompt Builder has two such options, one per job: Optimization: compute context (computeContext) for the prompt-optimization job and RAG: ingestion compute context (ragComputeContext) for the RAG ingestion and the retrieval test.

Granting the credential to the service account's identity or one of its groups with the admin script is no remedy for these two jobs. It makes the keys available to every job that runs under that account, and the jobs still fail: the optimization job writes its result to the prompt in SAS Model Manager, and the service account may not change the prompt of a user - on 2026-10-20 the job, run under it, made all its model calls and was then refused the write with HTTP 403. From release 2.3.0 the optimization job compares the user its session runs as with the user who started it and ends before its first model call when the two differ; its message names the account the session runs as and the option to change. The RAG ingestion cannot reuse the CAS session it needs in such a context (see Deploying the Builder UIs).
