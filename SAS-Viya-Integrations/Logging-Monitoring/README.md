# Parsing the Log

The goal is to create a table that extracts all of the relevant information from the container logs and collect everything as a CAS table.

For this two options are available:
1. The *Log-Parser-Code.sas* is a script that you can point at the logging file and it will parse all of the information into a CAS table.
2. The *LLM - Log Parser* custom step, which is just a nice little UI on top of the same SAS script - this step is located in the Custom-Steps folder.

By default the parser writes the CAS table **`LLM_LOGS`** to the **`Public`** caslib and both promotes it (global scope) and saves it to disk. Set the `_log_target_table_lib` / `_log_target_table_name` macro variables in front of *Log-Parser-Code.sas* (or the custom step's options) to target a different library or table name - see [Settings that stay yours](#settings-that-stay-yours).

The parser reads the log from the file system of the SAS compute server: `_log_path` has to start with `sasserver:`, and a file in SAS Content is not read. The default, `sasserver:/export/pvs/sasdata/data/llm/llms.log`, is an example path. The [Logging & Monitoring administration guide](../../website/docs/Administration-Guide/Logging-&-Monitoring.md) says what that path assumes and how the file reaches the compute server where the host that collects the logs shares no mount with it.

Three programs of this folder work on one set of tables, in this order:

1. collect the log (the script of the guide)
2. *Log-Parser-Code.sas* (or the step *LLM - Log Parser*) - one row per request in `LLM_LOGS`
3. *Get-All-Prompts.sas* (or the step *LLM - Get All Prompts*) - the experiments, the RAG setups and a catalog of models from SAS Model Manager
4. *Link-Logs-To-Models.sas* - fills the columns of `LLM_LOGS` that name the model that answered and the prompt, decision template or RAG setup that sent the request

Steps 2 to 4 ran as one chain on a SAS Viya system on 2026-10-11 and on 2026-10-12, each time with the programs as they were then: in the last run of 2026-10-12 with version 2.4 of the step *LLM - Log Parser* and version 2.2 of the step *LLM - Get All Prompts*. Each run led to changes. The programs of this folder are versions 2.11 and 2.6 of the two steps, with the code files and the link program that go with them; the changelog of the release says what they change. The guide says for a run what was measured, with which version of each program, and what was changed afterwards. The Python of the three programs runs in the tests of this folder.

`timestamp` is a SAS datetime; `temperature`, `top_p`, `top_k`, `max_tokens`, `prompt_length`, `output_length`, `runtime`, `status_code`, `failed`, `answer_confidence` and `match_candidates` are numeric; every other column is text (VARCHAR). The first twelve columns are the ones the table had before release 2.3.0 - same names, order, types and meanings, and the *LLM Usage Report* reads those twelve. The last nine are written empty by the parser: *Link-Logs-To-Models.sas* fills them. The labels above are those of a table the parser starts. A table of release 2.2 that is appended to keeps the labels its twelve columns had - `system_prompt`, `user_prompt` and `response` stay `The system prompt used by the request`, `The user prompt used by the request` and `The response of the model to the users request` (measured on 2026-10-13 on a copy of a table of 3,630 rows) -, and the 24 further columns get the labels above.

## What a row holds for each kind of model

Every scoring request becomes one row, whatever kind of model served it. The columns are the same for all three kinds:

| Column | LLM | Decision model | Embedding model |
| --- | --- | --- | --- |
| kind | `llm` | `decision` | `embedding` |
| system_prompt | the system prompt | the questions, as the JSON that was sent | missing |
| user_prompt | the user prompt | the state | missing |
| response | the response, its lines joined with a blank | the answers as JSON - every answer with its confidence and probabilities | missing |
| prompt_length | input tokens | input tokens | the tokens of the embedded text |
| output_length | output tokens | output tokens | missing |
| runtime | seconds | seconds | seconds |
| temperature, top_p, top_k, max_tokens | from the options of the request | from the options of the request | from the options of the request |
| status_code, failed, error_text | of the response; a request that failed has no status, `failed` = 1 and its first error | the same | the same |
| transaction_id, request_id, user_agent | of the request | the same | the same |
| options | as sent, keys replaced by `REDACTED` | the same | the same |
| embedding_mode, project, input_hash | missing | missing | the `Embedding_Mode` option as sent, the `project` input, the SHA-256 of the embedded text |
| answer, answer_confidence | missing | the answer to the first question and its confidence | missing |
| rag_collection, rag_query_hash | the collection and the SHA-256 of the question when the user prompt holds the results of a retrieval - of the last one when it holds several -, otherwise missing | missing | missing |

The text an embedding model receives is **not** copied into the table: an ingestion run embeds every chunk of every document, and the table would end up holding the whole corpus. Its hash is kept instead.

`kind` names the kind of model. It is decided by the names of the inputs of the request (`document`; `questions` / `state`; `systemPrompt` / `userPrompt`) and is missing when the `Request Data:` line can not be read. `max_tokens` is read from the option `max_tokens`, then from `max_completion_tokens`, then from `max_length`.

A hash is the SHA-256, in lower-case hex, of the UTF-8 bytes of the text with every run of white space made one blank; a character that has no UTF-8 bytes counts as a question mark. *Get-All-Prompts.sas* and *Link-Logs-To-Models.sas* hash a text the same way. The question of a retrieval therefore has the hash of the embedding call that embedded it: `rag_query_hash` of the LLM row equals `input_hash` of the embedding row in query mode. The results of a retrieval are the JSON object the RAG runtime writes into a prompt, with all six of its keys (`query`, `hits`, `graph_context`, `retrieval_mode`, `collection`, `ingestion_run_id`); of several such objects in one prompt the last one counts. The search tries 500 opening braces of a prompt and decodes 2,000,000 characters at most.

A request that failed in the container writes no `Response:` line: the container logs the traceback and `Error occurred in the model scoring function`. Such a request ends at that line and has `failed` = 1, no `status_code` and its first ERROR line in `error_text` (cut after 500 characters; for the line the container writes for an exception, with the last line of the traceback added). `failed` is also 1 for a status of 400 and above, and for a request that was still running where its container's part of the file ends - that one has no error text. `failed` is missing, and never 1, for a request that ran at the same time as another one where no line of the log says which of them a response belongs to.

The request headers are read for `X-Request-Id` and for the kind of client only: no address, no Referer, no cookie and no version of a client reaches the table. In `options` the value of `API_KEY` and of every other option that is a secret by its name (key, secret, password, passwd, pwd, passphrase, credential, authorization, bearer, cookie, `pass` or `pw` as a word of the name, a token that is no number) or by its shape (`sk-...`, `Bearer ...`, a JWT, 20 and more letters and digits in a row that hold both) is replaced by `REDACTED` by the parser itself, whether or not the log was redacted when it was collected. A secret inside a value is replaced as well: the user and the password of an address (`scheme://user:password@host`), a header that carries a secret with everything behind its name, and what follows `bearer` or `basic`. So is what has the shape of a key in the error text.

## What happens to the existing table

- **A log without requests** (an hour without traffic, or a file that only holds the start-up lines of the containers) changes nothing: the parser writes a note to the SAS log and leaves the output table as it is.
- **A log that can not be parsed** (the file is missing, Python or one of its packages is not available) leaves the output table as it is as well and ends with an error.
- **A run that is refused** - a `_log_path` that does not start with `sasserver:`, a `_log_target_table_engine` other than `CAS`, a `_log_append_table` that is neither 1 nor 0 nor without a value, and a run without a value of `_log_append_table` at a table that holds rows, whose rows can not be counted, whose saved file can not be loaded or for which CAS refused or did not run an action of the count - ends with its one ERROR line: no log is read, and nothing is written or dropped.
- **`_log_append_table` has three states.** Set to `1` the program appends, set to `0` it replaces, and without a value - the setting has no default - it only starts a table: where there is no table, or one without rows, it writes the requests of the log as with `0`. At a table that holds rows, in memory or only as its saved file, such a run stops in front of the log with `ERROR: The table <caslib>.<table> holds <n> rows and _log_append_table is not set, so nothing was read and nothing was written - not the table and not its saved file. Set it in front of the program: %let _log_append_table = 1; adds the requests of the log to the table, %let _log_append_table = 0; replaces the table with them.` The rows are counted first: of a table in memory by a listing, of a table that is saved and not in memory by loading its file into `CASUSER` as `_TEMP_LLM_LOGS_SAVED`, which is dropped again. Where that file can not be loaded the run stops in front of the log as well: behind the ERROR lines of the action that did not load it, it writes `ERROR: The saved table <caslib>.<table> could not be loaded and _log_append_table is not set, so nothing was read and nothing was written - the saved file was left as it is.` (measured on 2026-10-13 with a copy of the program whose count asked for a file that was not there: the saved file was as before, and `SYSCC` was 1012). Where `table.tableExists` finds the table in memory and the listing of its rows names no table, the run stops in front of the log too, with `ERROR: The rows of the table <caslib>.<table> could not be counted and _log_append_table is not set, so nothing was read and nothing was written - not the table and not its saved file. Set it in front of the program: ...`, with the two `%let` statements of the line above; a run with `0` replaces such a table and writes no NOTE of the rows it held. Where CAS refuses an action the count goes by - `table.tableExists` of the table, or `table.fileInfo`, the listing of the saved files of a table that is not in memory -, or where the PROC CAS step of the count halts before it says what it counted, the run stops in front of the log as well: behind the ERROR lines of CAS it writes `ERROR: CAS refused or did not run an action that the count of the rows of the table <caslib>.<table> needs and _log_append_table is not set, so nothing was read and nothing was written - not the table and not its saved file.` Up to version 2.9 of the step the program took a listing of the saved files that CAS refused for a library without the saved file, started a new table and saved it over the file, in every state of the setting. Up to this change the program replaced without the setting, and a run that had lost its `%let _log_append_table = 1;` replaced the rows of every run before it without a line that said so - measured on 2026-10-13 on a copy of a table of 3,630 rows, which held the 1,024 requests of one log afterwards, in memory and in its saved file, with a completed job. Any other value - `2`, `yes`, `01` - ends with `ERROR: _log_append_table is <value>, which is no value of this setting: ...`. The file of release 2.2 read the setting in `%if &_log_append_table. %then`, where the macro language takes every whole number other than 0 for true: `2`, `01` and `-1` meant append there, and `00` meant replace. Each of them is refused now, so a program of a site that sets such a value has to set `1` or `0`. The custom step sets `1` or `0` from its checkbox *Append new rows to existing table*, so it never runs without a value.
- **A run that wrote an ERROR line and no table** sets the condition code `SYSCC` to 1012 as its last statement in front of the macro variables it deletes - the value and the place *Ingest-Documents.sas* has for a failed run. For the parser these are a run that is refused - the bullet *A run that is refused* above names each of them -, a log that can not be parsed, a saved table that could not be loaded - by a run that appends or by a run that replaces -, an action that a run which appends or replaces goes by and that CAS refused or did not run, a new table that could not be created and a PROC CAS step that halted while it wrote the table. A WARNING, a NOTE and a log without requests leave the condition code as it was. Such a run behaves like any SAS error: the job fails, and later DATA steps of the SAS session do not run until `SYSCC` is reset. Measured on SAS Viya 2026.09 on 2026-10-12, in SAS Job Execution jobs: the job of a run that was refused ended as failed, and the first DATA step behind the program in the same SAS session went into syntax check mode (`OBS=0`) and did not run, while macro statements and PROC CAS behind it ran. With `%let syscc = 0;` behind the program that DATA step ran and the job ended as completed - so a job that runs a second program behind one that was refused has to reset `SYSCC`, and then no longer ends as failed. In the code SAS Studio generates for a flow the first DATA step behind a step is the end action of the flow itself (`%_flw_action_end`): for a refused run of the step *LLM - Get All Prompts* the log held `_FLW_ACTION_START_` and neither `_FLW_ACTION_TABLE_` nor `_FLW_ACTION_END_`. What SAS Studio shows for such a node was not looked at. *Get-All-Prompts.sas* and *Link-Logs-To-Models.sas* end the same way, see below.
- **Replacing** (`_log_append_table = 0`, and a run without the setting that found no rows) builds the new table under the name `<table>_NEW` beside the existing one. Only when that table exists is the old one dropped and the new one renamed, promoted and saved. If the new table can not be built the old one stays loaded. A run with `0` counts the rows of the table before it writes anything - of a table that is saved and not in memory by loading its file into `CASUSER`, as a run without the setting does. Where that file can not be loaded the run writes nothing: behind the ERROR lines of the action that did not load the file it writes `ERROR: The saved table <caslib>.<table> could not be loaded, nothing was replaced and the saved file was left as it is.`, starts no table and does not save over the file. Where CAS refuses an action of that count - `table.tableExists` of the table or `table.fileInfo` - or the step of the count halts, the run writes nothing either: `ERROR: CAS refused or did not run an action that the run needs for the table <caslib>.<table>, nothing was replaced and neither the table nor its saved file was written.` Version 2.8 of the step went on at that point - measured on 2026-10-13 with a copy of the program whose count asked for a file that was not there: the run ended with the ERROR lines of the action and with `SYSCC` 1012, and it had replaced the table and its saved file by the requests of the log all the same. A run with `0` that replaced a table that held rows says so: `NOTE: The table <caslib>.<table> held <n> row(s). They were replaced by the <m> request(s) of the log, as _log_append_table is 0.` A request the log holds more than once is written once, as in every other state of the setting - see *A request is written once* below -, and a run that replaces or starts a table says so where it left one out: `NOTE: <r> request(s) were read from the log. <m> were written to the table <caslib>.<table> and <l> were left out, as another row of the log holds their request.`
- **Appending** writes the rows of the existing table and the parsed rows to one new table (`_TEMP_LLM_LOGS_ALL` in the caslib of the output table, by a DATA step) and puts it in the place of the existing one, the way replacing does; where no table exists the parsed rows become the table. A table that was saved but is not in memory - after a restart of the CAS server, or when the table is not promoted - is loaded from its `.sashdat` file first; if that file can not be loaded, nothing is appended or saved and the run ends with an error. Where CAS refuses an action the append goes by - `table.tableExists` of the table, in front of the load or behind it, `table.fileInfo`, `table.columnInfo` of the table, or the `table.tableInfo` of `CASUSER` that counts what is left of the rows of the log -, or where the PROC CAS step that asks halts, nothing is appended or saved either: the run ends with `ERROR: CAS refused or did not run an action that the run needs for the table <caslib>.<table>, nothing was appended and neither the table nor its saved file was written.`, and a table it loaded from its saved file for the append is dropped again. The 36 columns of the parser stand in front in their order. A column the existing table lacks is added and is missing in its rows - a table of release 2.2 has the first twelve. A column the parser does not know stays behind the others with its type and length and is missing in the new rows. What the link wrote into existing rows stays. A text column the table holds as CHAR is handed over to the VARCHAR column of the parser without its trailing blanks, so new rows are not cut to its length; a column that is a number on one side and text on the other stops the DATA step, and the table is left as it is with the error `The new table could not be created, ...`. A table that was promoted is promoted again whatever `_log_promote_table` says; the saved copy is replaced only when `_log_save_table` is on. The table is read through a libref, so in append mode its name has to be one a libref can address (32 characters at most), and other sessions do not see the table between the drop and the promote. The new table only takes the place of the existing one when its DATA steps ended with a return code of at most 4, when its rows add up - the rows it holds and the rows that were taken out of it are as many as the existing table held and the log added, and at least one row was taken out for every row of the log that took the place of one - and when the two DATA steps that leave out the requests the table holds already ended with 0 or 4; otherwise the run ends with one ERROR line that names the return codes and the row counts, and the existing table stays as it was - one that the run loaded from its saved file for the append is dropped again, so that only its saved file is left, as before the run. The new table gets the label of the existing table, and `Extracted LLM Log Data` where that one had none. The guide has what the append did on a SAS Viya system.
- **A request is written once**, in every state of the setting. A request is known by three columns together: its `transaction_id`, its `model` and its `timestamp`, the time of its request line. The container writes the transaction ID into the lines of the request, so the three are the same in every file and every run that holds the request. The ID alone is not taken for the request: the container gives a request its ID unless the client sends one, and a client can send the same ID with every request - to two models, or to one model a minute later. Of a request the log itself holds more than once - a file that was collected twice - one row is written: the first that is complete, and the first of all where none is. A row is **incomplete** when its `failed` is missing: the lines it was read from hold neither a response nor an error for the request, as for a request that was still running where the lines of its container end, and for a request whose response the log gives to none of the requests that ran at the same time. `status_code` is missing in such a row as well. A row whose `failed` is 0 or 1 is complete. A run that appends leaves out a request of the log that the table holds already (two DATA steps in front of the one that appends: what the rows of the table are known by goes to `_TEMP_LLM_LOGS_SEEN` in `CASUSER`, and the rows of the log are merged with it), with one exception: a complete row of the log takes the place of the rows of the table of its request when each of them is incomplete - a request that was cut off where an earlier log ended and that a later log holds whole. A complete row of the table is never replaced, where the table holds a request complete and incomplete both rows stay, and no row is replaced in a table without a numeric column `failed`. The row that takes the place is the row of the log: what the link wrote into the row it replaces goes with that row, and the link fills the new one at its next run. The rows that give way are taken out of the new table by one more DATA step, which only runs where a row is replaced (the comparison writes what the rows of the log that take a place are known by to `_TEMP_LLM_LOGS_GONE`, and that step writes the transaction IDs of the rows it takes out to `_TEMP_LLM_LOGS_OUT`, both in `CASUSER`). A table that lacks one of the three columns - the two texts, and the time as a number - is compared with nothing: the rows of a table of release 2.2 have no `transaction_id`, and a log whose requests such a table holds already appends them a second time. A request without a `transaction_id` is never taken for another one and is appended every time it is parsed. No rule of the program decides that case: its row is made of the second its request line was written, its model, its inputs and its request headers, and none of them is its own - the `X-Request-Id` is set outside the container and can come twice. In a file without the lines of the collection script, such a request and another request with the same lines are the same file line for line; onto a table that holds the row, the first has to add nothing and the second has to add a row. In a file of the collection script the two differ in the line of the script, which names the pod and the container - but the table does not keep the pod and the container of a row: the row of such a request of one container and the row of the same request of another container are the same row, so the same file onto the same table has to add nothing in the one case and a row in the other. A table with a column for the pod and the container of a row would tell the two apart; `LLM_LOGS` has none. And a request read again and another request of the same container, written in the same second with the same lines, are the same file line for line with the line of the script as well: no column of the table can tell those two apart.
- **The numbers of a run that appends** stand in one line: `NOTE: <r> request(s) were read from the log. <a> were appended to the table <caslib>.<table> and <p> took the place of <x> row(s) of it whose failed was missing: the table held <o> row(s) and holds <n> now. <s> were left out, as another row holds their request: <t> a row of the table, <l> a row of the log.` - `r` is `a` + `p` + `s`, `s` is `t` + `l`, and `n` is `o` + `a` + `p` - `x`; `x` is `p` unless the table held an incomplete request more than once. Where there was no table the line reads `... <m> were written to the table <caslib>.<table>, which was not there before. <l> were left out, as another row of the log holds their request.` A run that appends nothing writes nothing: where every request of the log is in the table already and none takes the place of a row, no table is built, the existing one is not dropped or renamed, and its saved file is not written - also not where the table has no saved file yet. A table that was loaded from its saved file for the run stays loaded, and a table of the session is promoted where `_log_promote_table` is on, as the table that a run which appends rows writes is. The line of such a run reads `NOTE: <r> request(s) were read from the log and none of them was written: the table <caslib>.<table> keeps its rows, and neither the table nor its saved file was written. All were left out, as another row holds their request: <t> a row of the table, <l> a row of the log.` Version 2.8 of the step wrote the table again in such a run, with the rows it had, and saved it again (measured on 2026-10-13).

## What the parser expects from the log

The parser reads the lines the containers write with `SAS_SCR_LOG_LEVEL_SCR_IO=TRACE`. A request starts at its `Request: POST` line and ends at its `Response: Status Code` line or, when it failed, at the `Error occurred in the model scoring function` line of its transaction; the inputs come from the `Request Data:` line and the numbers and the answer from the lines of the score code (`prompt_length:`, `tokens:`, `output_length:`, `run_time:`, `response:`, `answer:`, `answers:`). A line only counts when it starts as a log line (`<timestamp> - <logger> - <level> - `), so a prompt that quotes such a line is kept as text. While a request is the only one that is running, the lines of its response up to the next line of its transaction are kept as text as well, also where they start like log lines; a line there that names another transaction of the part - the `Response Data:` line of a request whose `Response:` line came earlier - ends the response. A request line there, with a `Request Headers:` line directly behind it or with no further line that starts like a log line behind it up to the next line of the transaction, is read as a request first and decided at the end of the file. It is a request where it gets a transaction, an error, a status or a response of its own, or where a transaction of its model starts behind it that is given to no request. A request line that gets none of them while a request that came later in its part got its transaction - which a container gives a request at once - is read as a line of the response: the file is read once more with it as text, no row is written for it, the response is whole, and the request keeps its status whatever time the quoted lines carry. A request whose container wrote nothing but its first lines there is the same line for line, so a NOTE counts the request lines that were read that way. Where nothing came later in its part, the line can also be a request that came in while the response was written and that the end of the file, or of its part, cut off before its transaction began - two such files are the same line for line. It is read as a line of the response, no row is written for it, the response is missing, and a NOTE counts such requests. A request line that scores nothing (`GET`) gets no transaction either way and is read the same way. Up to this release one more row was written for a quoted request line, and the response ended in front of it. With one more line that starts like a log line behind the quoted request line, and that is no `Request Headers:` line, the request line is text of the response. A log whose lines carry something in front of that - the timestamp of `kubectl logs --timestamps`, the pod name of `--prefix`, a JSON wrapper of a log pipeline - yields no rows; when such a log holds `Request: POST` lines the parser says so with a warning instead of reporting a log without requests. A byte that is not valid UTF-8 is replaced, so one damaged line does not cost the rest of the file. A request whose content can not be read - a `Request Data:` line that was cut off, a request body nested deeper than Python reads - keeps its row with what was read, and a NOTE counts such requests. Options nested deeper than Python decodes are read as names and values, the way options that are no JSON are: the row has them as they were sent and no NOTE counts it. A character without UTF-8 bytes in a text column is replaced by a question mark, and a NOTE of its own counts those requests.

The collected file holds one container after the other, and the parser needs it that way: the lines of each container have to stay together, as `kubectl logs` writes them and the collection script appends them. The collection script of the guide writes one line of its own in front of the lines of every container it collects: `#=# llm-log-collection pod=<pod> container=<container> collected=<UTC time> #=#`. A container can write a line of that shape - a model writes what it is asked for -, so the script puts a backslash in front of every line of a container that starts like its own line, at the start of a line and behind a carriage return, with or without backslashes in front: in what the script wrote, a line of that shape is a line of the script. Behind the first line of the script the parser takes that backslash off again, and a response holds the line as the model wrote it. The redaction leaves the line of the script as it is and makes no other line a line of that shape. From the first such line of a file on, a part ends at each of them and nowhere else, whatever time of collection it carries: a request that is running or waiting there ends without a response and without an error - `failed` is missing, and the NOTE of the requests the lines of their container end on counts it -, nothing that was read goes on in the next part, and a part that begins with a later line of a transaction follows it to its end and gives it to no request. The time of the lines decides nothing in such a file: a line that is older is a line of its container that was written late, and a transaction that has not ended is running until it ends or its part does, so a line of the score code is given to no request while another transaction runs beside it. The pod is no column of the table. A file without such lines - collected before this release, or by a process of your own - is read by the time of its lines, and so is what stands in front of the first line of the script in a file that is appended to: it ends at that line. A line of that shape in lines that were collected without the script of this release is not told from a line of the script - a file with such a line in a response and a file in which the script wrote its line in the middle of that response are the same line for line: it ends the response it stands in, its request has no status and `failed` is missing, and the lines behind it are read as one part up to the next line of the shape. A process of your own that writes the line has to put the backslash in front as the script does. Where one part ends and the next begins, the time of the lines goes back, and that is how the parser finds the place: a line that is more than one second older than a request that is running or waiting starts the next part. A request that is still running there, or where the file ends, has no `Response: Status Code` line and no error: the leftover lines of the next part are not added to it, its `failed` is missing, and a NOTE counts such requests - also a request whose first lines broke off at the request line of one of them, and, in a log that holds no line of a transaction, a request that had all its first lines and ended at that request line. Every request whose `failed` is missing is counted once: in that NOTE where the lines of its container end on it, also where another request ran beside it, and in the NOTE of the requests that ran at the same time where a response could not be given to it. A request without a `Response:` line whose container went on with another request is `failed` = 1. Inside a part the time can go back by a second, as a line is stamped when it is made and written a moment later: a line that is older by one second ends no request. It is the line of its transaction when it names one of this part; a line of the score code or a `Response:` line that is older by a second is given to no request, and the requests that are running then are counted in the NOTE of the requests that ran at the same time. A request line for another model does not end a request that is running: a transaction that a later line still names goes on, unless every such line is more than one second older than that request line. The time of the newest request that can not be told apart from another one counts only while such a request is counted; up to this release it was kept past the last of them, so that in a part that began while nothing ran a line could read as older by more than a second, a part began that was none, the requests that were counted were forgotten, and a request that was waiting took the transaction of another one - in 10 of 600 files of a generator of the review that mixes the first lines of three or four requests.

Limits that follow from what the containers log:

- Only the lines of a transaction (the `transaction_<id>` logger) and the `Response Data:` line name the request they belong to. Every other line is given to a request where the lines around it leave one request it can be the line of, and to none otherwise. The first lines of a request (headers, request data, the two `Randomly generated` lines) are the lines of the request whose request line stands in front of them, as long as no other request line stands in between; a first line that no request is waiting for shows that requests wrote their first lines at the same time, and every request since the one whose first lines broke off keeps its request line only. A transaction that starts while no request of its model has all its first lines and none is counted as waiting, behind first lines of a request of that model that broke off, shows the same. Where the first lines of a request broke off and the lines of its container end before a request since has a status or an error, what stands behind the break can be of that request as well as of a request since: the requests since keep their request line only, and all of them are counted in the NOTE. Where a request since has ended, nothing is taken back: the request that broke off is read as failed - a file in which it went on while each request since waited for the next one is the same line for line. The first line of a transaction belongs to the one request of its model that has all its first lines and no transaction yet; where two such requests are waiting it is given to neither, and both rows keep their prompts, `options`, `request_id`, `kind` and `user_agent` without a `transaction_id`, a status, token counts, a run time or a response. The lines of the score code and the `Response:` line are the lines of the one transaction that is running; while a second one is running they are given to neither. The score code writes each of its lines once for a request: a second line of a kind for the one request that is taken as running was written by another request, and the request keeps none of the values of the score code. A `Response:` line without its `Response Data:` line behind it is the line of the one transaction that is running only behind the line of that transaction that follows the score code, or with a status of 400 and above. `failed` stays missing for a request whose response could not be given to it, and the SAS log has a NOTE with the number of such requests. A request whose first lines are complete and that never gets a transaction stays waiting until its container's part of the file ends, and the requests of that model that follow it in the part are left open. In the six collected logs of the test system (1247 requests) no request started before the one in front of it had ended, so these rules are read from the line format and not from a case.
- In a file that mixes the lines of several containers - a time-ordered export of a log store - the score lines of a request that ran while a request of another container was running are given to neither: its token counts, its run time and its response are missing, and the NOTE counts it.
- In a file without the lines of the collection script, `failed` can be wrong in four ways. For each, two files that are the same byte for byte need different rows, so no reading of such a file is right for both; `tests/test_log_parser.py` holds the files, and `tests/test_log_parser_generated.py` puts every such value of its generated files to one of the four and fails on a value of none. `failed` = 1 for a request the lines of its container end on, in front of another request: no line says whether its container was collected while it ran or the request ended without a line, and no NOTE is written for it. `failed` = 1 for a request that was answered, and `failed` = 0 for a request the lines end on, where the lines end between a `Response:` line and its `Response Data:` line: the `Response:` line names no request. And `failed` = 1 with the text of an error for a request that wrote none: the ERROR line of the score code names no request either. With the lines of the script the generated files of that test show none of the four.
- Only `temperature`, `top_p`, `top_k` and `max_tokens` have a column; every other option is in `options`.
- No line of a log names the model in SAS Model Manager or the prompt, decision template or RAG setup that sent a request. The link columns are filled by content, see below.

The collection script in the [Logging & Monitoring administration guide](../../website/docs/Administration-Guide/Logging-&-Monitoring.md) replaces provider keys and cookies in the log with `REDACTED` before the file is written; its `sed` runs in the C locale, so a byte that is no UTF-8 in such a value does not end the redaction. The parser reads a redacted log like an unredacted one, it never copies a request header other than the `X-Request-Id` into the table, and it replaces keys in the options and in the error text itself.

## What the custom step takes from the SAS session

*Log-Parser-Code.sas* starts a CAS session (`mysess`) in its first lines when neither the session the SAS option `SESSREF` names nor a session `mysess` is connected - a connected `mysess` is used, and the option is set to it -, and assigns the librefs `public` and `casuser`; the session and the librefs stay when the program ends. The custom step is the program without those lines:

- It asks the `SESSFOUND` function whether the session that the SAS option `SESSREF` names is connected - that is the session its CAS actions run in. When it is connected, the step runs in it and does not end it. When it is not and a session `llmLogMySess` is connected, the step sets the option to that session, runs in it and does not end it either. Otherwise the step starts a session of its own (`llmLogMySess`) and ends it as its last action, so of such a run only a table that was promoted or saved is left. The option goes on naming a session that was ended, the step's own included, so the name is not taken for a session: `%sysfunc(sessfound(%sysfunc(getoption(sessref)))) NE 1` is the first question, and *Log-Parser-Code.sas* holds the same line behind its own `cas mysess;`.
- It reads the caslib of the output table from its libref. When the libref is not assigned in the session, the name of the libref is handed to CAS as the name of the caslib.
- In append mode the program assigns the librefs `_llmtgt` (the caslib of the output table) and `_llmsrc` (`CASUSER`) and clears them, keeps the column list of the existing table in `work._log_target_columns` while it reads it, and writes three tables to `CASUSER` that it drops at its end: `_TEMP_LLM_LOGS_SEEN` and `_TEMP_LLM_LOGS_GONE` where the existing table has the columns a request is known by, and `_TEMP_LLM_LOGS_OUT` where a row of the log takes the place of a row of the table.

The code file and the step both need the caslib `CASUSER` of the user who runs them for the staging table `_TEMP_LLM_LOGS`, and PROC PYTHON with the pandas and swat packages. The guide lists what the step takes from the session in full, what was run on a SAS Viya system and what was not.

## The experiments: Get-All-Prompts.sas

*Get-All-Prompts.sas* reads what the Prompt Builder keeps in SAS Model Manager and writes five CAS tables. Every row carries `modelID` and `projectID`, the SAS Model Manager ids of the model - the prompt template, the decision template or the RAG setup - and of its project. The *LLM - Get All Prompts* custom step runs the same program.

| Table | One row per | Key |
|---|---|---|
| `PROMPT_EXPERIMENTS` | experiment run and model of a prompt template or decision template; one row for a model without a run | `modelID`, `runID`, `model` |
| `PROMPT_OPTIMIZATIONS` | optimization or comparison of a prompt template | `modelID`, `optimizationId` |
| `RAG_SETUPS` | RAG setup, saved by the Prompt Builder or registered by the step *RAG - Register Setup* | `modelID` |
| `RAG_RUNS` | ingestion run of a setup: the rows of its `<tables_prefix>_RUNS` table when that is in memory, otherwise the runs its `<tables_prefix>_LEDGER` table still names | `modelID`, `run_id` |
| `MODEL_CATALOG` | model and pattern: the template of a model, each of its experiment runs with the prompts as they were sent, the calls of its judges and of its optimizations, a RAG setup with its collection, a model that answers | `modelID`, `role`, `runID`, `optimization_id`, `target_model` |

The settings are macro variables. The program takes the value below for each one that is not set when it starts ([Settings that stay yours](#settings-that-stay-yours)):

| Macro variable | Default | |
|---|---|---|
| `_gap_tag` | `Prompt-Engineering` | Tag of the projects with prompt templates and decision templates |
| `_gap_rag_tag` | `RAG-Engineering` | Tag of the projects with RAG setups |
| `_gap_llm_project`, `_gap_embedding_project`, `_gap_decision_project` | `LLM Model Project`, `Embedding Model Project`, `Decision Model Project` | The projects of the model definitions: a name, a project id or `tag:<tag>`, several separated by `\|`; empty leaves the kind out of the catalog |
| `_gap_out_caslib` | `Public` | CAS library of all five tables |
| `_gap_out_experiments`, `_gap_out_optimizations`, `_gap_out_rag_setups`, `_gap_out_rag_runs`, `_gap_out_catalog` | the table names above | One table name per output: a SAS name of 32 characters at most |

In the custom step the output table names the table of the experiments and the CAS library; the other settings are fields of the step. A table name of more than 32 characters, or one that is no SAS name (letters, digits and underscores, no digit in front), ends the program with one ERROR line before it reads SAS Model Manager: CAS takes such a name, but no CAS libref can address the table. *Get-All-Prompts.sas* runs in the CAS session the option `SESSREF` names when that session is connected, and otherwise in a connected session `mySess`, to which it sets the option; only where neither is connected does it start `mySess`, and it ends only a session it started. A run that wrote an ERROR line and left an output table unwritten sets `SYSCC` to 1012 as its last statement in front of the macro variables it deletes: a table name that is refused, projects that could not be listed or another reason SAS Model Manager could not be read for, a table that was not written, and in the step an output library that is no CAS library. A WARNING - a model that could not be read, a setup that is left out - leaves the condition code as it was. Every message of the Python is made one text before it is handed to SAS, by the function the two other programs carry: in a name from SAS Model Manager a quote shows as a backtick, `%` as `pct`, `&` as `+`, a semicolon as a comma, a comment mark is split by a blank, a tab or a line break is a blank, and parentheses that do not pair up show as brackets.

How it works: one PROC PYTHON step reads SAS Model Manager (it needs the package `requests`), shapes the rows and hands each table to SAS as a JSON file with a map in the WORK folder, with the LENGTH statement of the table in a macro variable. A DATA step reads each file - or, for a table without rows, only declares the columns, so that an empty output still has all of them - and PROC CASUTIL drops, loads, promotes and saves the table. `RAG_RUNS` is stacked in SAS from the run tables that are in memory (`run_source` = `run table`). The step *RAG - Load Vector Store* publishes such a table, and so does the ingestion job of a setup of the Prompt Builder (*Ingest-Documents.sas*), with every run the vector store holds for the collection, once the job definition of the setup holds the program that publishes it and while the run history of the setup is switched on. For a setup whose run table is not in memory, the runs its `<tables_prefix>_LEDGER` table still names are written (`run_source` = `ledger`), each from the second its run id holds to the latest `updated_at` of its rows, with the collection and the embedding model of the setup and without counts. Every run writes its id into the row of every document of the folder, so a ledger names the newest run only. The ledger is read only where the run table is not in memory, so a run that both name is one row. A setup with neither table in memory is left out with a NOTE, and no table of a setup is loaded or changed. A setup whose CAS library is not available in the session is left out with a NOTE, and so is a setup for which CAS refused a question the pull goes by - the question for the run table, the one for the ledger where the run table is not in memory, and for a CAS library other than `CASUSER` the listing of the CAS libraries - or whose PROC CAS step halted before it set what it found: `NOTE: The CAS library <caslib> of the run table <table> is not available in this session, or CAS did not say whether it, the table or its ledger table is there, so its runs are not in <RAG_RUNS>.`

`PROMPT_EXPERIMENTS` keeps the 49 columns it had - the *LLM Usage Report* reads 38 of them - and has twelve more behind them: `modelID`, `projectID`, `projectName`, `kind` (`prompt` or `decision`), `expected`, `options`, `variables`, `resolved_system_prompt`, `resolved_user_prompt`, `resolved_system_hash`, `resolved_user_hash`, `judge_reasoning`. The resolved prompts are the templates of a run with the values of its variables filled in the way the Prompt Builder fills them, and the two hashes are taken of those texts before a text is cut to the length of a SAS column. In `options` the value of an option that is a secret by its name is replaced by `REDACTED`, by the names the log parser goes by. `runID` is a number in this table and text in `MODEL_CATALOG`.

`MODEL_CATALOG` has the columns `modelID`, `projectID`, `projectName`, `name`, `role`, `runID`, `target_model`, `system_template`, `user_template`, `resolved_system_prompt`, `resolved_user_prompt`, `collection`, `template_source`, `resolved_system_hash`, `resolved_user_hash`, `run_time`, `prompt_length`, `output_length`, `window_start`, `window_end`, `optimization_id`. `role` is `prompt`, `decision` or `rag` for what sends requests, `judge` or `optimization` for the calls the Prompt Builder makes for a prompt, and `llm`, `embedding` or `decision_model` for what answers; the `name` of an answering model is the name of its container, which is the `model` of a log row. `template_source` says where a row is from: `score code`, `best run` or `newest run` for the templates of a model, `builder` or `step` for a RAG setup. The row of an experiment run and model holds what the tracker measured of that call - `run_time`, `prompt_length`, `output_length` -, which is what tells the request of the run from another request with the same prompts. A `judge` row - one per run that was judged and model that judged it - holds the run in `runID`, the judge in `target_model` and the prompts of the run as they were sent, which the judge is shown in the user prompt of its call. An `optimization` row - one per entry of the optimization tracker and model it called - holds the id of the entry in `optimization_id`, an empty `runID`, the start and the end of the job in `window_start` and `window_end` (`YYYY-MM-DDTHH:MM:SSZ`, UTC) and the system prompt the optimization started from in `resolved_system_prompt`. The guide lists the columns of all five tables.

Limits: a model whose file can not be read is named in a WARNING and keeps a row without runs; when the projects can not be listed the program ends with an ERROR and leaves the tables as they are; the prompts as sent are what the Prompt Builder sent in an experiment, and the templates of a manifested model are read from its score code without running it. A setup that was saved in the Prompt Builder and registered with the step *RAG - Register Setup* is two models, two rows of `RAG_SETUPS` and two `rag` rows of the catalog with one collection, and its runs are in `RAG_RUNS` once for each. A RAG setup without a collection - its properties or its setup file could not be read - keeps its row of `RAG_SETUPS` and has no row in the catalog, with a WARNING. An `optimizationId` that a tracker holds on more than one entry is counted in the catalog, so that no two rows have the same key: the rows of the second entry carry it as `<id>#2`, of the third as `<id>#3`, and a WARNING names the model. A counter that would make the id of another entry of the tracker is passed over - of the ids `1`, `1` and `1#2` the second entry is `1#3` -, an id that is longer than the 16 bytes of the column is cut to make room for its counter, and entries without an `optimizationId` are counted the same way: the second of them carries `#2`, and the WARNING says how many there are. No entry is left out, as each has a window of its own that its calls are found by. `PROMPT_OPTIMIZATIONS` holds such entries as the tracker has them, so its key is not unique for that model.

## Linking the log to the models and to what called them

*Link-Logs-To-Models.sas* fills the link columns of the log table: for every request the SAS Model Manager model that answered, and the manifested prompt, decision template or RAG setup that made the call. It reads the log table, `MODEL_CATALOG` and, when it is there, `RAG_RUNS`.

The settings are macro variables. The program takes the default below for each one that is not set when it starts ([Settings that stay yours](#settings-that-stay-yours)):

| Macro variable | Default | Meaning |
| --- | --- | --- |
| `_lnk_log_caslib`, `_lnk_log_table` | `Public`, `LLM_LOGS` | The log table. Its link columns are filled in place |
| `_lnk_catalog_caslib`, `_lnk_catalog_table` | `Public`, `MODEL_CATALOG` | The catalog that Get-All-Prompts.sas writes |
| `_lnk_runs_caslib`, `_lnk_runs_table` | `Public`, `RAG_RUNS` | The ingestion runs. Without the table no embedding row is linked to an ingestion run |
| `_lnk_redo_all` | `0` | `0` links the rows without a `match_method`, `1` links all rows again |
| `_lnk_min_literal` | `20` | The characters of fixed text a template needs to take part, whitespace not counted; an experiment run needs as many in its prompts, and a call of an optimization or of a judge in the texts the catalog holds of it |
| `_lnk_utc_offset` | `0` | The hours the clock of the containers is ahead of UTC; the ingestion runs and the windows of the optimizations are recorded in UTC |
| `_lnk_query_window` | `300` | The seconds within which the prompt that carries a retrieval follows the embedding of its query |
| `_lnk_promote_table`, `_lnk_save_table` | `1`, `1` | They decide for a table that is not promoted and for one that has no saved file. A table that is promoted is promoted again and a table that has a saved file is saved again, whatever the two say |

### The link columns

| Column | What the program writes |
| --- | --- |
| model_id | The SAS Model Manager ID of the model that answered: the catalog row of the role `llm`, `embedding` or `decision_model` whose name is the name of the container. Empty when no model or two models have the name; two are named in a NOTE |
| caller_model_id, caller_project_id, caller_kind, caller_name | The prompt, decision template or RAG setup that made the request (`caller_kind`: `prompt`, `decision`, `rag`), and for a call of an optimization or of a judge the prompt it was made for. Empty when `match_method` is `none` or `ambiguous` |
| experiment_run_id | The run, when `match_method` is `experiment run`, and the run that was judged, when it is `judge`. Text; it is the `runID` of `PROMPT_EXPERIMENTS`, which is a number there, and a run id counts inside one model only. It is the place of the run in the tracker: the Prompt Builder numbers the runs again when one is deleted |
| rag_model_id | For an LLM row whose prompt carries a retrieval: the RAG setup of its collection. Filled whatever `match_method` says |
| match_method | The rule that decided: `experiment run`, `questions and state`, `questions`, `template`, `optimization`, `judge`, `retrieval query`, `ingestion run`, `ambiguous`, `none` |
| match_candidates | The number of candidates the rule found: for `experiment run` the runs whose run time is the one of the row - or, where the catalog holds no run time, the runs with its prompts -, callers otherwise, 0 for `none` |

### The rules

No request and no log line names its caller, so every link is made by content. The first rule that fits decides.

| Kind of row | Rule | The row is linked when |
| --- | --- | --- |
| LLM, decision | `experiment run` | its prompts (for a decision its questions and state) are the prompts of an experiment run as they were sent - compared by the hashes the catalog holds of them -, the run went to the model of the row, the request did not come from the score code or a SAS session (`user_agent` is not `python-requests` or `SAS`), and its `runtime` is the `run_time` the catalog holds for the run and model, with three decimals. A run is given to one row, the earliest. A request with the prompts of a run and another run time is linked by the rules below and gets no run. Where the catalog holds no run time for the runs with these prompts, the newest of them is written and a NOTE counts such rows |
| decision | `questions and state` | its questions are the questions of a decision template - compared as JSON, so key order and whitespace do not matter - and its state fits the state template |
| decision | `questions` | its questions are the questions of a decision template whose state template has no fixed text or does not fit |
| LLM | `template` | its system and user prompt fit the templates of a prompt: every `{{variable}}` stands for any text, also none or several lines, the fixed text is there in its order from the first character to the last, whitespace squeezed. The templates of earlier runs of a prompt count as its templates |
| LLM | `optimization`, then `judge` | it is a call the Prompt Builder made for a prompt: it holds every text of a catalog row of that role in its system or its user prompt - at least one of them as a part of the prompt, not as the whole of it -, it went to the model in `target_model`, and, where the row has a window, it was sent inside it. A judge call gets the run that was judged when exactly one run remains |
| embedding, query mode | `retrieval query` | the hash of its text is the hash of the query of a retrieval that an LLM row of the table carries, and that LLM row follows it within `_lnk_query_window` seconds. The nearest such row names the collection. The same question is embedded many times and for more than one collection, so a prompt before the embedding or long after it does not count. A setup of which the catalog names another embedding model than the model of the row is not taken |
| embedding, document mode | `ingestion run` | its `project` is `rag`, as the RAG runtime sends it, or empty, and its time lies inside exactly one run of `RAG_RUNS` with its embedding model |

When several callers fit, the one with the most fixed text wins. A caller of which the catalog only names other target models is taken when no other caller fits. Callers that tie, two collections for one query in the same second and two overlapping ingestion runs are `ambiguous`; a row that fits nothing is `none`. Where two models hold one collection - a setup saved in the Prompt Builder and registered with the step - the model the Builder saved is taken (`template_source` = `builder`) when the other one is its registration: the catalog marks it `step`, the two name no different embedding models, and it is named `RAG Retrieval - <name of the setup>` or holds an ingestion run in common with the setup. Another model with the same collection name, two setups of the Builder, or two models of the step, with one collection are `ambiguous`. Of several retrievals in one prompt the last one names the collection and the ingestion run. Rows of an earlier parser have no `kind`: it is taken from the role of the model that answered. A row or a catalog row whose content can not be read does not stop the link: the row gets `none`, the catalog row takes no part, and a WARNING names both.

### What cannot be linked

- A request names no caller, and a direct call of a model (a script, a health check) has none.
- Two prompts or decision templates with the same text fit the same requests: `ambiguous`.
- A template that is one variable, or has less than 20 characters of fixed text, takes no part - it would fit the requests of other callers. The program counts such callers in a NOTE.
- A test call of the Builder that was not kept as a run and was made with a text that is no longer the template.
- The health check a prompt optimization sends first, and a call whose instructions the optimizer replaced by a proposal of its own: they hold no text of the prompt.
- A further request with the prompts of an experiment run is linked to its prompt, and to no run.
- The query of a retrieval that never reached an LLM prompt or whose prompt does not follow within `_lnk_query_window` seconds, an embedding call outside of an ingestion run, a run without `finished_at`, and the earlier ingestions of a setup whose run table is not in memory: its ledger names the newest run only.
- A published model that sends the prompts of an experiment run again is linked to its prompt, not to the run.
- A template that is longer than a SAS column (32,767 bytes) is cut in the catalog and fits no request; an experiment run with such a prompt is still found, by its hash.

### How the tables join

- `LLM_LOGS.model_id` = `MODEL_CATALOG.modelID` - the model that answered
- `LLM_LOGS.caller_model_id` = `PROMPT_EXPERIMENTS.modelID` - the prompt or decision template; with `experiment_run_id` = `runID` (the first is text, the second a number) and `model` = `model` the row of the run. After a run was deleted in the Prompt Builder and the pull was run again, a row that was linked earlier can name another run: the link program counts such rows in a WARNING, and `_lnk_redo_all = 1` links all rows again
- `LLM_LOGS.caller_model_id` = `PROMPT_OPTIMIZATIONS.modelID` - the optimizations of that prompt; a call of an optimization belongs to the one with `startedAt <= timestamp <= finishedAt`
- `LLM_LOGS.caller_model_id` = `RAG_SETUPS.modelID` - the setup of an embedding row (`caller_kind` = `rag`)
- `LLM_LOGS.rag_model_id` = `RAG_SETUPS.modelID` - the setup whose retrieval an LLM prompt carried
- `RAG_RUNS.modelID` = `RAG_SETUPS.modelID` - the ingestion runs of a setup

`MODEL_CATALOG` has one row per model and pattern; join callers to it through a distinct list of `modelID`.

### What happens to the table

- The twelve columns of every release, the columns of the parser and every column the program does not know stay in CAS and are not rewritten. The program numbers the rows in a copy in `CASUSER`, reads what it compares (the prompts only of the rows it links), uploads the link columns with the row number and merges them back by that number.
- The new table is built as `<table>_NEW` beside the log table, gets the label of the log table and replaces it the way the parser replaces a table. A table that is promoted is promoted again and a table that has a saved file is saved again; for any other table the two settings decide. While the program runs it needs room for two more copies of the table.
- A run that links no row builds no new table: the log table, its promotion and its saved file stay as they are, and one NOTE says so.
- A log table that is a saved file and not in memory - after a restart of the CAS server - is loaded before it is linked. Where such a run then links no row, the loaded table is promoted as `_lnk_promote_table` says, so that it is not gone when the CAS session of the program ends; the saved file is not written again. One more line says what was done: a NOTE for the table that was promoted, a NOTE for the one that stays a table of the session because `_lnk_promote_table` is not 1, a WARNING where the promotion did not take, and a WARNING where CAS did not say whether it took.
- Where CAS refuses to say whether a table the program reads is in memory, or to list the saved files of its CAS library - for the log table, the catalog or the table of the ingestion runs where it is not in memory, or for the saved file of the log table, which is looked for where `_lnk_save_table` is not `1` -, or where the PROC CAS step that asks halts, the run links nothing and writes nothing, behind the ERROR lines of CAS: `ERROR: CAS did not say whether a table the program reads is in memory or did not list the saved files of its CAS library, so it is not known whether that table is there or whether the log table has a saved file. Nothing was linked and the tables were left as they are.` Up to this change such a listing was taken for a library without the file: the log table and the catalog counted as not found, the table of the ingestion runs as not there - and the rows were linked without it -, and the log table as one without a saved file, which was then not written again. The question whether a table is in memory was read without asking whether CAS had refused it. A new table that CAS does not say is there takes the place of nothing, also where CAS refused the question, which has a line of its own: `ERROR: CAS refused to say whether the new table <caslib>.<table>_NEW is there, so it did not take the place of the table <caslib>.<table>, which was left as it is.`
- A row that has a `match_method` is left as it is, also when the catalog has changed since; `_lnk_redo_all = 1` links every row again.
- A log table without the link columns, written by an earlier parser, is refused with one ERROR line. Without `MODEL_CATALOG` there is one ERROR line that names *Get-All-Prompts.sas*. The table is left as it is in both cases.
- A table that grew while it was linked is left as it is with an ERROR line: run the parser and the link program one after the other.
- A run that wrote an ERROR line and no table sets `SYSCC` to 1012 as its last statement in front of the macro variables it deletes: a log table or a catalog that was not found, a question or a listing of saved files that CAS refused or did not answer, a table the program refused, rows that could not be linked and a new table that could not be put in the place of the log table - also where the PROC CAS step that puts it in place halted. A WARNING and a run that had no row to link leave the condition code as it was.

The SAS log ends with one NOTE per kind of row: the rows, how many are linked to a model, the callers by method, `ambiguous` and `none`. Every message is made one text before it is handed to SAS: in a message a quote shows as a backtick, `%` as `pct`, `&` as `+` and a semicolon as a comma, a comment mark is split by a blank, a line break or a tab is a blank, parentheses that do not pair up show as brackets, and a message ends after 900 characters. The parser and the pull carry the same function. The program starts a CAS session (`lnkMySess`) only when the SAS session has none that is connected, and ends only that one.

## Tests

`tests/` runs the Python of the three programs outside of SAS on made-up logs and files and checks that the code files and the custom steps still hold the same programs:

```bash
python -m pytest SAS-Viya-Integrations/Logging-Monitoring/tests
```

`tests/test_log_parser.py` runs the parser on made-up logs. The SAS code around that Python - the CAS actions that replace, append, load, promote and save the table - does not run in these tests: they hold its text and the order of its actions, and the text of the step's About tab and of the guide where those describe the program. They also hold the SAS text of append mode and what its DATA step writes for a table of twelve columns, for a table with some of the new columns, with a column the parser does not know, with CHAR text columns and with a column of the other type, by the rules of LENGTH and SET. They run the parser on requests whose lines interleave at every position, in one container and in a file that mixes several, and check that no row holds a value of another request. The condition of the session check is taken from the program and decided for three states of a SAS session - no CAS session, the step's own session ended with its name left in the option, a session of the user - with the values the two functions returned on SAS Viya 2026.09 on 2026-10-11: the option `SESSREF` named `CASAUTO` without a CAS session and the session's name after one was ended, and `SESSFOUND` returned 0 in both states and 1 for a connected session. What the runs on SAS Viya showed - the step twice and three times in one SAS session, a session of the user used and left alone - is in the guide under *What Was Measured*.

`tests/test_get_all_prompts.py` runs the Python of *Get-All-Prompts.sas* against a made-up SAS Model Manager that pages its listings and can fail a request (`tests/get_all_prompts_harness.py`), on trackers, setups and score code written for the tests in the shape of the real ones. It checks the variables filled into a prompt, a run without a system prompt, a decision template, the optimizations, both kinds of RAG setup, the catalog with the rows of judges and optimizations, the table names it refuses, paging, the failures and an empty output. The DATA steps, the stacking of the run tables and PROC CASUTIL do not run in these tests: they hold their text. For the stacking the harness also has a stand-in that follows the two macros of the program (`stack_rag_runs`). With it the tests hand the pull the run table the ingestion job publishes - the file its Python writes with `rag_core` - and the table the step stages, and check that both give the same rows of `RAG_RUNS`, that a run the run table and the ledger both name is one row, and, in `tests/test_end_to_end.py`, that a document embedding inside a run of such a table is linked to that run.

`tests/test_link_logs.py` runs the Python of *Link-Logs-To-Models.sas*. `tests/link_logs_harness.py` builds log rows and catalog rows with the columns of the two other programs and stands in for the SAS object and for CAS: it keeps tables as frames and does what the program asks CAS for. The tests cover every rule and their order, ambiguity, the minimum of fixed text, a prompt with a retrieval, ingestion windows, a second run and a redo, the columns the program does not know and the two refusals. The stand-in for the SAS object fails a test in which the program hands SAS a message that would not arrive as one text, or a macro variable that is no whole number. They do not show what CAS does with the calls.

Five test files read several programs at once. `tests/test_handed_to_sas.py` collects every place of the Python of the three programs and the two steps that hands a text to SAS - a message, the name and the value of a macro variable, code for CAS - and fails for one that does not send its text through the escaping function, for another way to SAS and for a function that differs between the programs; it also sends names through each program that SAS would not take as text. *Start-Here.sas* of the folder [Setup](../Setup/README.md), the page with the installation check, carries the same function and is held to the same tests. `tests/test_job_state.py` reads every statement of the SAS code that writes an ERROR line and checks that it leads to the statement that sets `SYSCC`, and that nothing else does. `tests/test_cas_sessions.py` reads every statement that starts or ends a CAS session in the programs of this folder and in the two steps: each stands under the check of a connected session. `tests/test_fix_content_23.py` takes every such statement of every program of `SAS-Viya-Integrations` that is not frozen and of every step that is no RAG step, and runs the session check and the clean-up for each state of the sessions a program names, a foreign one and the option `SESSREF`: no program starts a session of a name that is connected, none ends a session it did not start, and the CAS steps between them run in a session that is connected. `tests/test_settings.py` reads the settings of all five programs: the macro that sets a default is the one text it may have, and followed the way that text says a value that is set in front of a program wins, every other setting is the default it was, and each of the two steps gets every setting from a control.

`tests/test_cost_view.py` follows the two macros of *Build-RAG-Cost-View.sas* with `tests/macro_harness.py`, which resolves the part of the macro language they are written in the way the macro processor does: an argument of a macro function ends at a comma that is not masked. For a list of one, two and many run tables, with and without blanks around the commas, it holds the DATA step the macro generates; for the list as it was written before it gives the error that was measured; for a run that did not stack its tables and for a cost table without a column it holds that the macro generates no statement that drops the output table, and that the last line is an ERROR line; for a list without a table and for run tables that were not stacked, that the macro that prices the runs generates no statement and writes one ERROR line at most, and that a step of it that ends with an error is the last one; and for a CAS table with other rows than the run has, that the last line is an ERROR line as well. The steps the macros generate do not run in these tests.

`tests/test_end_to_end.py` runs the three one after the other: log lines of all three kinds become rows, tracker, setup and score code files become the catalog, and the link program is given both. Among its requests are two experiment runs with the same prompts, a further request with those prompts, the call of a judge, the calls of an optimization inside and outside of its window, and a query embedding with and without a prompt behind it. It also reads from the code of the three programs that they hand each other the same columns, kinds, roles, default table names and the same hash.

Each program lives in its code file and in a step (the link program has no step). Change *Log-Parser-Code.sas*, then carry the same code into the `templates.SAS` entry of *LLM - Log Parser.step* (the step is one line of JSON - load it, replace the entry and write it back compactly rather than editing it by hand). For *Get-All-Prompts.sas*, put the lines between the two `gap core` comments of the program between the step's own first and last lines. The tests fail while a step and its program differ.

## Where these tables are used

`Public.LLM_LOGS` is one of the four CAS tables behind the **LLM Usage Report** - the recommended monitoring template, which is part of the transfer package of the content folder. The other three are the fact sheets *LLM_FACT_SHEET* / *EMBEDDING_FACT_SHEET* (loaded with `mdb load-facts` or *Load-Fact-Sheets.sas*) and *PROMPT_EXPERIMENTS* (from *Get-All-Prompts.sas*, which writes four further tables the report does not read). All four are expected in the *Public* caslib by default. The report reads the twelve columns of `LLM_LOGS` and the columns of `PROMPT_EXPERIMENTS` that both tables had before release 2.3.0; the columns this release adds are for reports of your own. *Load-Fact-Sheets.sas* and *Build-RAG-Cost-View.sas* run in the CAS session of the SAS session when one is connected and leave it as it is; they start a session of their own (`mySess`, `_rcvSess`) only when there is none, and end only that one. *Load-Fact-Sheets.sas* reads the three fact sheet files of `_lfs_path` one after the other. Each sheet is first loaded beside its table, as `<table>_NEW` in the CAS session, and its rows are counted; only a sheet that CAS held completely takes the place of the table: the table is dropped, and the upload whose rows were counted is promoted under its name and saved - the sheet is not loaded a second time. A table that has the name `<table>_NEW` before a sheet is loaded is no table of the program: CAS is asked first (`table.tableExists`), and where it does not answer that there is none, the sheet is not loaded and neither table is touched, with a WARNING that says to rename or drop that table. Where CAS refuses that question, or the PROC CAS step that asks it halts, the sheet is not loaded either, with a WARNING that says that CAS did not say whether there is such a table. A file that is not in the folder, a folder that is not there, a file without rows and a sheet that CAS did not take leave the table of that sheet as it is, with a WARNING, and the other sheets are loaded. Where the promote is refused, a table of that name that is in memory - the table could not be dropped - is left as it is, and where none is, the table is loaded again from the file it was saved to before; each of these outcomes is a WARNING of its own. Where CAS refuses the question whether such a table is in memory, nothing is loaded either, with the WARNING of a table that was not loaded again. Where the PROC CAS step of the swap halts before it says which of these outcomes it was, the line is `WARNING: Nothing said what became of the sheet - messages above -, the table <caslib>.<table> may not hold it.` A sheet whose count CAS refused - the question whether the upload is there, or the listing of its rows - is a sheet that CAS did not take. The job definition *Load-Accelerator-Tables* of the content folder includes *Load-Fact-Sheets.sas* from that folder and loads the release table beside the three sheets ([Setup](../Setup/README.md)).

*Build-RAG-Cost-View.sas* stacks the run tables `_rcv_runs_tables` names - one table, or several separated by commas - and prices their runs with the two fact sheets. A list of several tables is set with a `%let` in front of the include, as in [Settings that stay yours](#settings-that-stay-yours). With two run tables the program of before failed, measured on SAS Viya 2026.09 on 2026-10-12: the list stood in `%scan` as a reference with an ampersand, its own comma ended the argument, and the log held `ERROR: Argument 2 to macro function %SCAN is not a number.` and `ERROR: The macro _RCV_STACK_RUNS will stop executing.` - and the run still ended with the NOTE that the table was built, for a table that did not exist. The list is now handed over through `%superq`, as one text; a comma and a blank both end a name. The output table is dropped and loaded only when the run tables were stacked and priced without an error and the run has a cost table to put in its place, so a run that fails on the way leaves the table of an earlier run as it is. A run leaves at the first refusal with one ERROR line: a list without a table, run tables that could not be stacked - a table that is not there, behind SAS's own line for it - and a step that prices the runs and ends with an error run no further step, and no table of WORK is left from an earlier run in the same session. Measured on 2026-10-12, the program of before went on behind its own ERROR line, and SAS wrote ERROR lines for tables of WORK that were not there. The last line of a run is `NOTE: <table> built in <caslib>.` when CAS holds the table with the rows of this run, and otherwise an ERROR line that starts with `ERROR: Build-RAG-Cost-View:`; a run with such a line sets `SYSCC` to 1012 as its last statement in front of the macro variables it deletes, as the three programs above do.

See the [Logging & Monitoring administration guide](../../website/docs/Administration-Guide/Logging-&-Monitoring.md) for how the report reaches a site with the transfer package and how to point it at a different caslib if your tables are not in *Public*.
