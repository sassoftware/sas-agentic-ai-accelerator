# SAS Viya Integrations

This folder holds the integrations that put the deployed LLMs, embedding models and RAG pipelines to work inside SAS Viya - as SAS Studio custom steps, SAS code, SAS Job Execution jobs, SAS Intelligent Decisioning nodes and SAS Visual Analytics content. Most of them work in a low-code or no-code fashion.

The [Administration Guide](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Introduction) explains how to deploy each piece; this page is the map of what is here.

## The transfer package and its manifest

| File | Contents | Guide |
| --- | --- | --- |
| `SAS-Agentic-AI-Accelerator.json` | The content folder `/SAS Agentic AI Accelerator` as one SAS Viya transfer package. `Start Here`: the job definition of the first page - links to the two reports and the guides, and the installation check. `Prompt Builder`: the **LLM Prompt Builder** - which builds prompt templates, decision templates and, as its RAG Builder part, RAG setups - with the SAS Visual Analytics report that hosts it, the SAS Job Execution definition that serves the single-file app and the optimization job. `RAG`: the **RAG runtime** - the nine RAG custom steps, `rag_core`, the ingestion and retrieval-test programs and the retrieval model template. `Logging and Monitoring`: the **LLM Usage Report**, the *LLM - Log Parser* and *LLM - Get All Prompts* steps and the five programs. `Data`: the three fact sheets and the release table as CSV, and the job definition `Load-Accelerator-Tables` that loads the four into CAS. `Custom Steps`: three *LLM* steps and the four *MM* steps. `Decisions`: the decision *Call LLM Node*, which carries the *Call LLM* node of SAS Intelligent Decisioning under one id and is not meant to be published. `release.json`: the release, the commit the folder was deployed from, and every object of the folder - with a content hash for each file, custom step and job definition | [Deploying the Builder UIs](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Setup-Additional-UIs), [RAG Ingestion and Retrieval](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/RAG-Ingestion-and-Retrieval), [Logging & Monitoring](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Logging-&-Monitoring) |
| `package-manifest.yaml` | The list of what ships in that folder: one entry per object with its path below the content root, its kind (folder, file, step, job definition, report, decision) and the repository file it is a copy of. A parameter of a job definition marked `siteSetting` - the compute context `_contextName`, the CAS library and server, the credential domain, the names of the repository and the projects, the release table - holds a value of the site: a new job definition gets the default, and so does one on your site that has no such parameter; a value a job definition on your site holds is left alone by a deploy and an import unless `--compute-context` names one. `contentRoot` is always the content root the content goes to; one job definition named with `--to` keeps the one it has. A report lists the files that are its children, its pictures, with their hashes. An object that is not listed is not deployed, not exported and fails the check when it is found in the package; a path with `Showcases`, `Example`, a folder whose name holds `generated` or a name starting with `ZZ_VERIFY` is refused | - |

`mdb builders-import` brings the package to a site in two ways. The **reports**, with their pictures, go through the SAS Viya transfer service: the command loads the release table - the package's `Data/ACCELERATOR_RELEASES.csv` where the package holds it, so the table says what was imported - binds the Prompt Builder report to it, points the Data-Driven Content URL at your server, and with `--report-caslib` binds the other tables the reports read to a CAS library of yours; the part of the package it uploads is deleted after the import job. The **decision** `Decisions/Call LLM Node` and the *Call LLM* node type it carries go through the transfer service as well, in a job of their own: a node type of the package's id on your site is overwritten in place, and a *Call LLM* node under another id leaves both out, before anything of them is uploaded, with exit code 1 and the command `mdb decision-node-migrate` (`--no-decisions` imports without them). **Every file, custom step and job definition below the package's root folder** - and every empty folder - is brought in place, with the package as the source: the manifest of your checkout does not limit what is brought, the never-ship rule and the rule for a path do (a name with a slash, `.` or `..` is not taken, and each object that is not brought gets a `not imported:` line with the reason). An object that exists at its path is updated under the id it has on your site, whatever id the package carries, and a missing one is created - one line per object says `equal`, `updated` or `created`. A custom step your flows use therefore stays the step they reference, and a file is not deleted and uploaded again. Two objects of one name in a folder, or a reference of that name to an object of that kind elsewhere - alone, or beside the object itself - fail the entry: each is named on its line and none is written. A compute context your site set in a job definition stays: the ingestion compute context of the options the import writes back is given to a job definition the import creates and to one on the site that has no `_contextName`; a `_contextName` a job definition on the site holds is kept. `--content-root` names another folder for the files, custom steps and job definitions (one that is not there is created only with `--create`); a report and the decision are imported only into the folder the package was exported from, at the root of SAS Content, so with another folder the command ends with exit code 1 unless `--no-reports --no-decisions` leaves both out. `--dry-run` says what a run would do and sends GET requests only. The command still needs your clone of this repository: to find the manifest (the default package file and content root), to configure a site without the Prompt Builder report from the model definitions, and for the release table of a package that holds none.

Importing a report **replaces the options** an administrator set on the Prompt Builder object - the switch that enables RAG among them - so the command reads them from the report before the import, keeps them in a file `builder-options-captured-<time>.json` and writes them back afterwards (a run that writes every option back removes the file); `--options` writes back a file saved with `mdb options-save` instead. The report is the one at its place in the content folder, `<content root>/Prompt Builder/Prompt Builder` - a report of that name elsewhere is not read and not written. A report that is there and cannot be read, or holds no option at all, stops the command before anything is imported. See [Preserving builder options across a report import](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Setup-Additional-UIs#preserving-builder-options-across-a-report-import), which also covers a site that still has the retired `RAG Builder` report - an import removes nothing. The package carries no authorization rule: the command writes `sas-viya-cli-content-commands.txt`, the commands that give the *LLM Consumers* group Read on the content folder, for you to review and run.

`mdb content-deploy` brings a content folder to the state of a checkout from the manifest, without a package, by the same requests: it creates folders, uploads a file that is missing and replaces the content of one that differs, registers custom steps and updates an existing step so that it keeps its id, and creates or updates the job definitions. It does not deploy the two reports and it deletes nothing; `--dry-run` lists what would change. The run stops at the first write that fails - also at a folder that cannot be created - and lists what it did not attempt. `release.json` is written last, only by a run that covers every entry of the manifest - a run of a part that names it, `--only release.json`, is refused - and only when every entry in front of it was written, so after a run that did not get there the folder's `release.json` is the one an earlier run wrote, or there is none. A content root other than `/SAS Agentic AI Accelerator` that is not there is created only with `--create`, and a folder that is created for the content gets a line of its own. Two more uses of the same command:

- `mdb content-deploy --only "Logging and Monitoring/LLM - Log Parser.step" --to "/Custom Steps/LLM - Log Parser.step"` updates, in place, a step your site registered in a folder of its own - `--to` takes the SAS Content path, the id or the URI of the step, and never creates one. The line names the step it wrote and its folder; a step whose name is not the entry's is not written without `--force`. The same works for a file and a job definition.
- `mdb content-deploy --only RAG --to "/Team/Retrieval"` deploys the RAG runtime into a RAG content root of any name; a folder that is not there needs `--create`. A folder with a job definition that reads the content root goes to that folder of a content root - `--only Data --to "/Team/Tables/Data"` writes `/Team/Tables` into `contentRoot` - and any other target ends the command before it signs in.

Maintainers build the package with `mdb content-deploy` followed by `mdb package-export`. The export keeps what the manifest lists and drops everything else that sits in the folder, with every authorization rule and share; it resets the option defaults of the Prompt Builder report, removes the report's per-user states, replaces the exporting host and replaces the user ids in `createdBy`, `modifiedBy` and `userName` with the text `sas-agentic-ai-accelerator`. `mdb package-check --release` then compares the package with the checkout, object by object, and fails with one line per difference - also when the commit `release.json` names is not in the history of the checkout. Between releases the package is the content of an earlier commit: `mdb package-check` without `--release`, which the workflow `verify-model-definitions.yml` runs on a branch, prints a difference in content as a line starting with `drift:` and fails only for what a package must never hold - see [CONTRIBUTING](../CONTRIBUTING.md). The four packages of earlier releases - one each for the Prompt Builder, the RAG runtime, the usage report and a starter set - are replaced by this one. Until the package of release 2.3.0 is exported, `SAS-Agentic-AI-Accelerator.json` is not in this folder and the four earlier files still are: the commit that adds the one file removes them.

## Folders

### Custom-Steps

SAS Studio custom steps (a SAS Studio Analyst license is required). They reach a site with the transfer package, or from a checkout with `mdb content-deploy`, which registers each step with SAS Studio - a `.step` uploaded as a plain file renders as an empty editor. `Other/deploy-rag-content.ps1` / `.sh` do that for the RAG steps alone. The package places the RAG steps in `RAG/steps`, the two logging steps in `Logging and Monitoring` and the others in `Custom Steps`. One step of this folder is not in the manifest and so not in the package: *LLM - Get Prompt Experiments*, the step of August 2024 that reads the experiment tracker of one model - *LLM - Get All Prompts* is the step that pulls the experiments. Steps starting with *MM* are general SAS Model Manager helpers built along the way.

| Step | Purpose |
| --- | --- |
| LLM - List Available LLMs | Table of every LLM registered in the LLM project |
| LLM - Get Options | The options an LLM accepts, with their defaults |
| LLM - Create LLM Call | Generates the SAS code that calls one LLM |
| LLM - Get Prompt Experiments | The experiment runs of one prompt-test. Not part of the package |
| LLM - Get All Prompts | Five tables of what the Prompt Builder keeps in SAS Model Manager - experiments, optimizations, RAG setups, their ingestion runs and a catalog of models - for reporting |
| LLM - Log Parser | Parses the collected SCR container logs into the `LLM_LOGS` table: one row per request to an LLM, a decision model or an embedding model |
| RAG - List Documents, Extract Text, Chunk Documents, Enrich Chunks, Embed Chunks, Load Vector Store | The ingestion pipeline, in that order (Enrich is optional) |
| RAG - Retrieve Context | Asks a collection a question - the same retrieval a deployed decision performs |
| RAG - Register Setup | Manifests and registers the retrieval model and writes the governance artifacts |
| RAG - Purge Documents | Erases named documents, including their retired generations |
| MM - Get All Repositories / Get Projects in Repository / Get Models in Project / Get Model Information | SAS Model Manager lookups |

The RAG steps are described in the [RAG user guide](https://sassoftware.github.io/sas-agentic-ai-accelerator/User-Guide/RAG).

### RAG and RAG-Ingestion

`RAG/rag_core/` is the Python runtime the RAG steps, the ingestion job and the jobs the RAG Builder (the RAG part of the Prompt Builder) launches import at run time; `RAG/retrieve_context.py` is the retrieval model template that *RAG - Register Setup* and the RAG Builder's **Manifest setup** manifest per setup - its MANIFEST block holds, among the setup's values, `SSL_VERIFY`, the default for TLS verification that the Builder writes from the option **Verify TLS certificates in manifested models**, that *RAG - Register Setup* writes from its checkbox **Verify TLS certificates in the registered retrieval model**, and that `RAGEMBED_SSLVERIFY` / `RAGSTORE_SSLVERIFY` overrule on a destination; `RAG/tests/` is its test suite (`python -m pytest SAS-Viya-Integrations/RAG/tests`). `RAG-Ingestion/` holds the standalone schedulable `Ingest-Documents.sas` job and `Test-Retrieval.sas`. `rag_core`, the two programs and the model template reach SAS Content with the transfer package, or from a checkout with `mdb content-deploy` (`Other/deploy-rag-content.ps1` / `.sh` run it for the RAG folder alone) - SAS Content is the distribution channel, nothing is fetched from GitHub at run time.

### Logging-Monitoring

Everything for monitoring: `README.md` (the `LLM_LOGS` table and where it is used), `Log-Parser-Code.sas` (the log parser as a code file - the *LLM - Log Parser* step carries the same code), `Get-All-Prompts.sas` (the `PROMPT_EXPERIMENTS`, `PROMPT_OPTIMIZATIONS`, `RAG_SETUPS`, `RAG_RUNS` and `MODEL_CATALOG` tables - the *LLM - Get All Prompts* step carries the same code), `Link-Logs-To-Models.sas` (fills the columns of `LLM_LOGS` that name the SAS Model Manager model that answered a request and the prompt, decision template or RAG setup that sent it), `Load-Fact-Sheets.sas` (or `mdb load-facts`) and `Build-RAG-Cost-View.sas`. The *LLM Usage Report* is part of the transfer package. Each of the five programs takes a setting only where its macro variable is not set when the program starts, so a site keeps its values in a program of its own that sets them and includes the shipped file - see *Settings that stay yours* in the `README.md` there.

A note on prices: the report's *Average Price* / *Total Price* calculated items multiply token counts with the per-token prices from the fact sheets. Providers quote prices per million tokens and distinguish input from output tokens; the report works in individual tokens. Locally served models are priced at $0 by default - the calculated item has a comment at the top that explains how to add a per-second price.

### Setup

The programs of two job definitions of the content folder, with their tests (`python -m pytest SAS-Viya-Integrations/Setup/tests`). `Start-Here.sas` is the job definition `Start Here` at the root of the folder: one HTML page with links to the two reports and to the guides, and an installation check that reads `release.json`, the content folder, the CAS tables of the reports, SAS Model Manager, the credential domain by its name, the Python packages, the publishing destinations and the compute contexts - with GET requests only. `Load-Accelerator-Tables.sas` is the job definition `Data/Load-Accelerator-Tables`: it loads the release table and the three fact sheets from the `Data` folder into CAS, the fact sheets by including `Load-Fact-Sheets.sas` from `Logging and Monitoring`. See the `README.md` there.

### Prompt-Optimization

The server side of the Prompt Builder's **Optimize** feature: `Optimize-Prompt-DSPy.sas` (a SAS Job Execution job that improves a prompt with DSPy), `Create-Optimization-Dataset.sas` (a template for a governed CAS training table) and `requirements.txt` for the compute context. See [Enabling Prompt Optimization](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Enabling-Prompt-Optimization).

### SAS-Code-LLM-Calls

Scripts to run the prompt workflow from SAS code - the `README.md` there walks through them in order:

- `Get-List-of-available-LLMs.sas` - the LLMs you have access to
- `Create-LLM-Call.sas` - the SAS code that calls a specific LLM, with all of its options
- `LLM-Call-Result-Table.sas` / `LLM-Call-Combined-Result-Table.sas` - the call output as a table, for one or several LLMs
- `Track-Prompt-Experiments.sas` / `Manual-Prompt-Experiment-Tracker.sas` / `Get-Prompt-Experiments.sas` - record and read prompt experiments in SAS Model Manager
- `Test-DS2-Scoring-from-SAS-Studio.sas` - one query against an LLM from PROC DS2

### SAS-Code-Model-Manager-Interaction

General SAS Model Manager helpers, not specific to this project: `MM-Get-Repositories.sas`, `MM-Get-Projects-in-Repository.sas`, `MM-Get-Models-in-Project.sas`, `MM-Get-Models-Information.sas`, and `createLLMRepository.sas` - the SAS-code way to create the *LLM Repository*. Prefer `mdb setup`, which creates the repository, both model projects and the authorization commands.

### SAS-Intelligent-Decisioning-Integration

`Create-Custom-SAS-Intelligent-Decisioning-Node.sas` adds the *Call LLM* node to the *Objects* pane of SAS Intelligent Decisioning; `Update-Custom-SAS-Intelligent-Decisioning-Node.sas` updates it in place. A SAS Intelligent Decisioning license is required.

A decision references the node by its id, so the node has one id on every site: `f9efcbb7-f57b-4a62-b56d-1a89595e2039`. From release 2.3.0 the transfer package brings the node under that id, as the dependency of the decision `Decisions/Call LLM Node`, and `mdb builders-import` imports it. The create program creates it under that id too, and creates nothing where the node is there already or where a node named *Call LLM* is there under another id. That site runs `mdb decision-node-migrate` (a dry run, then `--apply`) before `mdb builders-import`. The update program looks for the node under that id first and falls back to the name. See [The Call LLM node and its id](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Deployment-of-Decisions#call-llm-node-uuid).
