# Setup: the first page and the tables of the reports

The page and the program of two job definitions of the content folder `/SAS Agentic AI Accelerator`. Each job definition holds a copy of its file.

| Job definition | File | What it does |
| --- | --- | --- |
| `Start Here` (at the root of the content folder) | *Start-Here.html* | One page, served as the form of the job definition: what the accelerator is, links to the guides, and - once `mdb check` has run - the installation check with links to the two reports |
| `Data/Load-Accelerator-Tables` | *Load-Accelerator-Tables.sas* | Loads the release table and the three fact sheets from the folder `Data` into CAS |

`Data/Load-Accelerator-Tables` runs in a compute context that runs under the identity of the person who starts it: the job definition names that context in its parameter `_contextName`, and a request can name another one. `Start Here` runs nothing.

## Start Here

The job definition serves one page; opening it runs nothing, so it opens on a site whose compute server is not set up as well:

```text
https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Start Here
```

The release ships *Start-Here.html*: what the accelerator is, the guides, and that `mdb check` is to be run. `mdb check` - see [`mdb check`](https://sassoftware.github.io/sas-agentic-ai-accelerator/Administration-Guide/Setup-Additional-UIs#mdb-check) - runs the installation check as the administrator who runs it, prints it by part with what to do, and writes the result into the form of the job definition, in place: the verdicts, every line, the links to the two reports and when it ran. A deploy or an import of the package writes *Start-Here.html* back. The checks are in `Model-Definition-Builder/cli/src/mdb/core/start_here.py`.

The check reads SAS Viya with GET requests: the content folder, the CAS tables, SAS Model Manager, the options of the Prompt Builder report, the credential domain by its name, the publishing destinations and the compute contexts. What only the compute server can say is asked in one short compute session per compute context the parts run in: whether PROC PYTHON runs, which packages its Python has, whether it reaches SAS Viya and trusts its certificate, and whether its sessions run as the person who ran the check. Where SAS Viya refuses every request of the check with 401 or 403, it has one line at its top in place of those lines.

The installation check gives every line one of four states - `ok`, `missing`, `not checked`, `not used` - with what was found and one sentence what to do. Every line belongs to one part of the accelerator: prompt building, logging and the LLM Usage Report, RAG, prompt optimization, decision models. The table *By part* gives each part one verdict - `ready`, the number of lines to do, the number not checked, or `not used here` - and the first thing to do. A part the options of the Prompt Builder report switch off (`enableRag`, `enableOptimization`, `enableDecision`) is `not used here`, and so is the driver of a RAG backend it does not offer (`enable_pgvector`, `enable_singlestore`): their lines that are not ok are `not used`, not `missing`. Where the options cannot be read, every part counts as used.

| Section | What is looked at |
| --- | --- |
| Release | `release.json` in the content root: release, commit and date. The file is asked for at the Files service only |
| Content | Every entry `release.json` lists: present in this content root or not. A custom step is registered - by the import of the package or by `mdb content-deploy` -, so a `.step` file that was uploaded to the folder is not the step: the step is `missing` while only that file is there, and the line of a step that is registered names a file of its name that lies beside it. What a folder holds under the name of an entry is told the way `mdb content-deploy` tells it: a member has the name of the entry to the letter - a step that is registered under the name without `.step` is not the step of the entry -, and is of its kind by what its uri starts with. A member of a folder that is a reference to an object elsewhere is no entry of the folder, whatever it names: it is not followed. A reference that has the name of an entry and names an object of the kind of the entry stands in the way of that entry - `mdb content-deploy` and the import write nothing for it -, so the line of the entry is `missing` with the advice to remove the reference: where the reference is all the folder holds under that name, and where it lies beside the object - the entry is then counted as present, and its line is shown with the lines that are not ok. Two objects of the name and kind of an entry stand in its way as well, because nothing says which one is meant: the line is `missing` with the advice to remove or rename all but one, and the entry is counted as present. Below a name two folders have nothing is read, and the entries there are `not checked`; below a folder that has a reference to a folder beside it the entries are read from that folder, and the line of the folder says that nothing is written below it. A report that is there is `ok` whatever lies beside it: `mdb` writes no report and fails none over a reference. For a report that is missing the advice names the import of the package and `mdb builders-import` - a report comes with the package - and says that `mdb content-deploy` writes none. A decision - `Decisions/Call LLM Node`, which brings the *Call LLM* node - is checked like a report, and its advice names the import of the package and `mdb builders-import` as well, and `mdb decision-node-migrate` first where `mdb builders-import` names it. A reference to an object of another kind is no part of the check, as it fails nothing in `mdb`. The line of `release.json` is judged the same way, and of two files of that name in the content root neither is read |
| CAS tables of the reports | `ACCELERATOR_RELEASES` (Prompt Builder) and `LLM_LOGS`, `PROMPT_EXPERIMENTS`, `LLM_FACT_SHEET`, `EMBEDDING_FACT_SHEET`, `DECISION_FACT_SHEET`, `RAG_SETUPS`, `RAG_RUNS` (LLM Usage Report): there, their rows, when they were loaded |
| CAS tables of the logging chain | The two tables *Get-All-Prompts.sas* writes for *Link-Logs-To-Models.sas* that no report binds - `PROMPT_OPTIMIZATIONS`, `MODEL_CATALOG`: there, their rows, when they were loaded |
| SAS Model Manager | The repository and the projects of the LLM, the embedding model and the decision model definitions, found by name as *Get-All-Prompts.sas* finds them, a project inside the repository as the Prompt Builder asks for the decision models; the number of models of each, and a project without a model is `missing` |
| Options of the Prompt Builder report | `modelRepositoryID`, `llmProjectID` and, with RAG switched on, `embeddingProjectID`: whether each names the object that was found by its name. The Prompt Builder reads the repository and these two projects by the ids the options hold |
| Credentials | The credential domain of the provider keys, by its name. No entry of it is asked for |
| Compute server | Per compute context a part runs its jobs in: a compute session, PROC PYTHON, a request to SAS Viya from the compute server - with the cause where it gets no answer: a certificate it does not trust (set `SAS_VIYA_CABUNDLE`, or `SAS_VIYA_VERIFY_SSL=false` on a test system), a host it cannot reach, a timeout -, and for RAG and prompt optimization whether its sessions run as you |
| Python packages | For each part what the Python of the compute context it runs in needs: `pandas`, `swat`, `requests` for logging; for the RAG runtime also `psycopg2-binary`, `singlestoredb`, `pypdfium2`, `markitdown`; `dspy`, `requests` and `optuna` in the versions of `Prompt-Optimization/requirements.txt` for prompt optimization |
| Publishing destinations | Whether one is defined, and their names |
| Compute contexts | The contexts the options `computeContext` and `ragComputeContext` of the Prompt Builder name, and the ones the parameter `computeContexts` names |

What holds for the check:

- **It changes nothing but the page.** Every request to the services is a GET; the compute sessions it starts are deleted when they have answered, and the form of `Start Here` is the one thing it writes.
- **A site that lacks something gets a line, not a failed check.** A service that does not answer, a right that is lacking and a folder that is not there are lines: `not checked` with the HTTP status, or `missing`.
- **It lists what the person who ran it can read,** and says so under the summary of the page.
- **Every text is escaped.** A name from the system or from a parameter is text on the page, written so that no two braces stand side by side - SAS Job Execution reads a form as a Go template -, and a guide address is a link only where it is an `https` address of the website of the accelerator or of this SAS Viya. The page names no host, no token and no user id.
- **No advice is an upload.** What the check says to do about a custom step that is missing names the import of the package and `mdb content-deploy`, which register it. Measured on 2026-10-12: a `.step` file uploaded in the place of a step is a file of the folder and no step, and `mdb content-deploy` then registers the step and leaves that file beside it.

Parameters of the job definition - the settings of the check, which `mdb check` reads from the job definition on the site:

| Parameter | Value | |
| --- | --- | --- |
| `_action` | `form` | The job definition serves its form, the page |
| `contentRoot` | `/SAS Agentic AI Accelerator` | The content folder that is checked |
| `caslib`, `casServer` | `Public`, `cas-shared-default` | Where the tables of the reports are |
| `credentialDomain` | `agentic-ai-keys` | Used where the option of the Prompt Builder report is empty or says `none` |
| `repositoryName`, `llmProject`, `embeddingProject`, `decisionProject` | `LLM Repository`, `LLM Model Project`, `Embedding Model Project`, `Decision Model Project` | The names `mdb setup` gives them |
| `computeContexts` | `SAS Studio compute context\|SAS Job Execution compute context` | Compute contexts to look for, separated by `\|`; the first is the one the compute server is probed in for prompt building and logging |
| `guideUrl` | `https://sassoftware.github.io/sas-agentic-ai-accelerator` | Where the guides are: linked on the website of the accelerator or on this SAS Viya, text anywhere else |

`contentRoot` and the other parameters but `guideUrl` are settings of a site: a deploy and an import leave them as the site has them.

## Load-Accelerator-Tables

The job gives the two reports their tables after an import of the package, without the command line. Started from SAS Job Execution:

```text
https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Data/Load-Accelerator-Tables&_contextName=<a compute context that runs as you>
```

- **The fact sheets** are loaded by *Load-Fact-Sheets.sas* of the folder `Logging and Monitoring` of the content root, which the job includes: one program loads the sheets, run on its own or from the job. The job hands it its folder (`<contentRoot>/Data`) and its CAS library through the two settings `_lfs_path` and `_lfs_caslib`. Where the program is not in the folder, the job says so with a WARNING and loads the release table; a fact sheet table that is then not in the CAS library at the end of the job is the ERROR line of that check, and the job fails (*The state of the job* below). A folder that is not there is the same WARNING: measured on 2026-10-13 with a content root without `Logging and Monitoring`, the FILENAME statement for a file of that folder wrote two ERROR lines in front of the WARNING, so the job - and *Load-Fact-Sheets.sas* for the folder of the sheets - asks the Folders service for a folder first, with the request *Start Here* asks for the content root with, and assigns no fileref where the answer is 404.
- **The release table** is loaded by the job itself, from `Data/ACCELERATOR_RELEASES.csv`, the file `mdb load-releases --csv` writes. CAS reads the file with the eleven columns of `mdb` in their order, the three numbers (`is_current`, `release_rank`, `item_rank`) as DOUBLE and the eight text columns as VARCHAR - the types the table has that `mdb load-releases` loads. No value passes a SAS variable, so none is cut to 32,767 bytes.
- **Against the table of `mdb`**, measured on SAS Viya 2026.09 on 2026-10-12 with both loaded from the changelog of one commit: 707 rows, the same eleven columns in the same order, the same types and the same lengths. One difference: the formatted length - the width CAS keeps for display beside the length of a column - is 16 where the table of `mdb` has 6, 10, 8 and 8, for the four text columns whose longest value is shorter than 16 bytes (`version`, `release_date`, `change_type`, `builder_part`). It changes nothing: a width of 16 shows every value of these columns whole, and the page of the Prompt Builder reads nothing from the table it is assigned. The job names the name and the type of a column and no length, so CAS decides both for it.
- **A table that exists is replaced only by one that loaded completely.** The file is uploaded beside the table as `<table>_NEW`, a table of the CAS session, and its rows are counted against the lines of the file. Only then is the table dropped, the upload promoted under its name and saved. A table that has the name `<table>_NEW` before the upload is no table of the job - a site can have one -, so CAS is asked first (`table.tableExists`): where it does not answer that there is none, nothing is uploaded and no table of that name is dropped, with a WARNING that says to rename or drop that table. The file a table of the name of `releaseTable` was saved to is looked at the same way: it is loaded as `_LAT_SAVED` only where no table of that name is in the CAS library, and is otherwise left as it is with an ERROR line of its own: it names the table `_LAT_SAVED`, says what `table.tableExists` answered and that the table is to be renamed or dropped before the job is run again. A saved file that could not be loaded or lacks columns of a release table keeps the line that says so. Where CAS refuses to list the files of the CAS library, it is not known whether such a file is there: the upload is dropped again and no table is loaded, with an ERROR line of its own. The other actions of CAS the job goes by there - the question whether a table is there, the count of the rows of the upload and the listing of the columns of a table - are no answer either where CAS refuses one: the upload is dropped again and no table is loaded, with one more ERROR line, and where CAS refuses the question whether `<table>_NEW` is there, or the PROC CAS step that asks it halts, nothing is uploaded, with an ERROR line of that question. A file that is not in the folder, a first line with other columns and an upload that does not hold every row leave the table as it is, with a WARNING. *Load-Fact-Sheets.sas* replaces each fact sheet table the same way: the upload of the sheet whose rows were counted is promoted under the name of the table and saved, and the sheet is not loaded a second time. Where the promote is refused, a table of that name that is in memory - the table could not be dropped - is left as it is, and where none is, the table is loaded again from the file it was saved to before. Each of these outcomes, and a load from the file that fails as well, is a WARNING of its own, and so is a PROC CAS step that halted before it said which of them it was.
- **The session.** In a compute context that runs under a service account the SAS session is that account. The log then holds one NOTE that the session does not run as the user who started the job - the program compares `SYSUSERID` with `SYS_COMPUTE_SESSION_OWNER` as the persons they name, a domain behind `@` or in front of a backslash dropped, and writes neither -, and that the parameter `_contextName` names a compute context that runs as you. What such a session may read depends on how the system configures its context: measured on 2026-10-12 in the `SAS Job Execution compute context` of the test system, the log held the NOTE, and the job read the folder `Data` and loaded the release table as it did in the `SAS Studio compute context`.
- **The state of the job.** The job writes an ERROR line and sets `SYSCC` to 1012 when one of the four tables is not in the CAS library at its end or CAS does not say whether it is, when a parameter is refused, and when the release table is left as it is with an ERROR line of its own. A table that was left as it is and is there is a WARNING.
- **The page.** Started from its address in SAS Job Execution, the job answers with a page: each of the four tables with its rows and what this run did with it - *Loaded by this run*, *Left as it was* or *Not in the CAS library* - under a line that says whether the four are in the CAS library. Whether this run loaded a table is read from CAS: the rows of each table and the time CAS made it are read before the tables are loaded and again at the end, and a table with another time, or one that was not there before, is one this run loaded. The log has every line, and the WARNING lines of a table that was left as it was say why. SAS Job Execution answers a run that fails with its own page *Job Error*, which names the ERROR line of the job. A table the upload could not take the place of - two runs at the same time, where the promote of the second is refused because the first loaded the table - is *Left as it was*, *Loaded again from its saved file* or *Loaded by this run and not saved*, with its WARNING in the log; the job then ends with warnings, not as a failed job, so the page shows (measured on 2026-10-20: two runs started 3 seconds apart, the second refused with `The target table DECISION_FACT_SHEET of the promotion already exists`, ended with *Job Error* before this change). The job definition holds the parameter `_output_type` with the value `html` for the page; for a job definition without it the job writes no page, with a NOTE, and run in SAS Studio, where the session has no `_webout`, the program writes none. Measured on 2026-10-20 in a test folder with test table names: a run that loaded the four tables answered with four rows *Loaded by this run* (934, 35, 16 and 6 rows), and a run from a content root without `decision_fact_sheet.csv` and without `Load-Fact-Sheets.sas` with the release table *Loaded by this run* and the three fact sheets *Left as it was*; a run without the release file answered with *Job Error* and the ERROR line that named the release table. Before, the job definition had no `_output_type`, and the job answered with an empty page *SAS Output*.

| Parameter | Value | |
| --- | --- | --- |
| `_action` | `execute` | |
| `_output_type` | `html` | The job writes its page itself, to `_webout` |
| `_contextName` | `SAS Studio compute context` | The compute context the job runs in: one that runs as the person who starts it |
| `contentRoot` | `/SAS Agentic AI Accelerator` | The content folder whose `Data` folder holds the four files |
| `caslib` | `Public` | The CAS library of the four tables |
| `releaseTable` | `ACCELERATOR_RELEASES` | The name of the release table: a SAS name of 28 characters at most. A table of that name that exists and lacks one of the ten columns every release table has - a fact sheet, the log table - is left as it is, with an ERROR line; the release table of 2.2.0, without `builder_part`, is replaced. Where no table of that name is in memory, the job looks for the file one was saved to (`<name>.sashdat`, which a restart of the CAS server leaves of a saved table), loads it as a table of its session to read its columns, and drops it again: a file that lacks those columns or can not be loaded is left as it is the same way |
| `factSheets` | `1` | `1` loads the three fact sheets as well, `0` leaves the fact sheet tables as they are: the sheets in `Data` are the ones of the release and replace the rows of a site's own definitions. With `0` a fact sheet that is not in the CAS library is a WARNING, and only the release table decides whether the job fails |

`mdb load-releases` and `mdb load-facts` load the same tables from a checkout and stay the way to load them from a workstation. The files in `Data` are the fact sheets of the release, so a table that holds rows of a site's own definitions is replaced by the sheets of the release. A site that keeps definitions of its own loads its sheets with `mdb load-facts` and runs the job with `factSheets=0`.

## Tests

```bash
python -m pytest SAS-Viya-Integrations/Setup/tests
```

The installation check of `Start Here` is tested with `mdb`: `Model-Definition-Builder/cli/tests/test_start_here.py`, `test_start_here_one_rule.py`, `test_start_here_parts.py` and `test_mdb_check.py` run it against a SAS Viya system that is made up - for each of the four kinds `mdb` writes and for `release.json` - a report that is there is held as `ok` - the rule it shares with `mdb content-deploy` for what a folder holds under the name of an entry -, and the program of the probe of the compute server against an address where nothing listens. `tests/test_load_accelerator_tables.py` holds the columns and types of the release table against the columns of `mdb` and against the file `mdb` writes from `CHANGELOG.md`, reads the order of the statements that replace a table, holds what the header of the program says of *Load-Fact-Sheets.sas* against the statements of that program, and checks that the four columns with the other formatted length are the ones whose longest value is shorter than 16 bytes. `tests/test_loader_followed.py` follows the macros of the job with `macro_harness` and runs the CASL of their PROC CAS step against a CAS library that is made up (`casl_harness`, both in the tests of `Logging-Monitoring`): a folder the Folders service answers 404 for is the WARNING and no FILENAME statement, and a table of the name of `releaseTable` that is another table is left as it is - in memory, or only as the file it was saved to -, and a table that has one of the two names the job loads a table of its session under (`<table>_NEW`, `_LAT_SAVED`) is neither loaded over nor dropped, and each of the two has the line that names it - for `_LAT_SAVED` also where the file behind it is a sound release table. A run whose only message is the WARNING of a taken name is followed to the look at the end of the job, which fails the job only for a table that is not in the CAS library. `Logging-Monitoring/tests/test_fact_sheets.py` holds what is said here of `<table>_NEW` for *Load-Fact-Sheets.sas*. The SAS code of the loader does not run in these tests: they hold its text, and say what it does if SAS and CAS behave as their model has it.

`tests/test_readme.py` holds this page: the address of the loader with `_contextName`, the parameters of both tables against the manifest and the program and against the compute context the manifest gives the Prompt Builder job definition, and what the page says of a custom step, of *Load-Fact-Sheets.sas* and of the four widths.

`tests/test_custom_steps.py` reads the custom step *LLM - Create LLM Call* of the folder `Custom Steps`, which has no code file of its own.
