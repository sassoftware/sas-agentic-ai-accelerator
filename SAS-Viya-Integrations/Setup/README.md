# Setup: the first page and the tables of the reports

Two programs for two job definitions of the content folder `/SAS Agentic AI Accelerator`. Each job definition holds a copy of its program.

| Job definition | Program | What it does |
| --- | --- | --- |
| `Start Here` (at the root of the content folder) | *Start-Here.sas* | One HTML page: what the accelerator is, links to its two reports and to the guides, and the installation check |
| `Data/Load-Accelerator-Tables` | *Load-Accelerator-Tables.sas* | Loads the release table and the three fact sheets from the folder `Data` into CAS |

Both run in a compute context that runs under the identity of the person who starts them: each job definition names that context in its parameter `_contextName`, and a request can name another one.

## Start Here

Run from SAS Job Execution, the job writes one page to the browser. The page holds no script and loads no file from another host; its style is inline.

```text
https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Start Here
```

The page shows what its SAS session may read, so it is opened in a compute context that runs as you. The parameter `_contextName` of the job definition names that context; to open the page in another one, name it in the address:

```text
https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Start Here&_contextName=<a compute context that runs as you>
```

What the session of a compute context may read depends on how the system configures that context. Measured on SAS Viya 2026.09 on 2026-10-12, twice, in the `SAS Job Execution compute context` of the test system. On one run, when the job definition did not have the parameter yet and the page was opened without `_contextName`, SAS Viya answered every request of the session with 401, and the page read `13 ok, 0 missing, 15 not checked` - fifteen lines, twelve of them with the advice to ask an administrator; opened with `&_contextName=SAS Studio compute context` the same page had 97 lines that were ok. On a later run the same day the page was built completely in that context - `97 ok, 2 missing, 1 not checked` opened with `&_contextName=SAS Job Execution compute context`, and `96 ok, 3 missing, 1 not checked` opened from a job definition without the parameter, after one file had been taken out of the test folder - by a session whose user (`SYSUSERID`) was not the user it was started for (`SYS_COMPUTE_SESSION_OWNER`); no request was refused, and the note under the summary said that the session does not run as you.

Where SAS Viya refuses every request of the session with 401 or 403, the page has one line at its top in place of those lines: what it is, and what to do. Where the user of the SAS session (`SYSUSERID`) is another one than the user SAS Job Execution started the session for (`SYS_COMPUTE_SESSION_OWNER`), the line says that the session runs as another user than you and how the page is opened with `&_contextName=`; where the two are the same user it says that the session ran as you and to ask for the rights (403) or about the sign-in (401). The program compares the two - a domain written behind `@` or in front of a backslash is no difference - and writes neither to the page. In a session of another user that is refused by some services only, each line that is refused advises to open the page as yourself, and the note under the summary says whose session built the page. In a session of another user the page also links itself in each compute context it found - or, where the contexts could not be listed, in each one the parameter `computeContexts` names -, but the one it ran in.

The installation check gives every line one of three states - `ok`, `missing`, `not checked` - with what was found and one sentence what to do:

| Section | What is looked at |
| --- | --- |
| Release | `release.json` in the content root: release, commit and date. The file is asked for at the Files service only |
| Content | Every entry `release.json` lists: present in this content root or not. A custom step is registered - by the import of the package or by `mdb content-deploy` -, so a `.step` file that was uploaded to the folder is not the step: the step is `missing` while only that file is there, and the line of a step that is registered names a file of its name that lies beside it. What a folder holds under the name of an entry is told the way `mdb content-deploy` tells it: a member has the name of the entry to the letter - a step that is registered under the name without `.step` is not the step of the entry -, and is of its kind by what its uri starts with. A member of a folder that is a reference to an object elsewhere is no entry of the folder, whatever it names: it is not followed. A reference that has the name of an entry and names an object of the kind of the entry stands in the way of that entry - `mdb content-deploy` and the import write nothing for it -, so the line of the entry is `missing` with the advice to remove the reference: where the reference is all the folder holds under that name, and where it lies beside the object - the entry is then counted as present, and its line is shown with the lines that are not ok. Two objects of the name and kind of an entry stand in its way as well, because nothing says which one is meant: the line is `missing` with the advice to remove or rename all but one, and the entry is counted as present. Below a name two folders have nothing is read, and the entries there are `not checked`; below a folder that has a reference to a folder beside it the entries are read from that folder, and the line of the folder says that nothing is written below it. A report that is there is `ok` whatever lies beside it: `mdb` writes no report and fails none over a reference. A reference to an object of another kind is no part of the check, as it fails nothing in `mdb`. The line of `release.json` is judged the same way, and of two files of that name in the content root neither is read |
| CAS tables of the reports | `ACCELERATOR_RELEASES` (Prompt Builder) and `LLM_LOGS`, `PROMPT_EXPERIMENTS`, `LLM_FACT_SHEET`, `EMBEDDING_FACT_SHEET` (LLM Usage Report): there, their rows, when they were loaded |
| CAS tables of the logging chain | `DECISION_FACT_SHEET` and the four tables *Get-All-Prompts.sas* writes beside `PROMPT_EXPERIMENTS` for *Link-Logs-To-Models.sas* - `PROMPT_OPTIMIZATIONS`, `RAG_SETUPS`, `RAG_RUNS`, `MODEL_CATALOG` -, which no report binds: there, their rows, when they were loaded |
| SAS Model Manager | The repository and the projects of the LLM, the embedding model and the decision model definitions, found by name as *Get-All-Prompts.sas* finds them, a project inside the repository as the Prompt Builder asks for the decision models; the number of models of each, and a project without a model is `missing` |
| Options of the Prompt Builder report | `modelRepositoryID`, `llmProjectID` and, with RAG switched on, `embeddingProjectID`: whether each names the object that was found by its name. The Prompt Builder reads the repository and these two projects by the ids the options hold |
| Credentials | The credential domain of the provider keys, by its name. No entry of it is asked for |
| Python packages | For each part what the Python of the compute context needs: `pandas`, `swat`, `requests` for logging; for the RAG runtime also `psycopg2-binary`, `singlestoredb`, `pypdfium2`, `markitdown`; `dspy`, `requests` and `optuna` in the versions of `Prompt-Optimization/requirements.txt` for prompt optimization |
| Publishing destinations | Whether one is defined, and their names |
| Compute contexts | The contexts the options `computeContext` and `ragComputeContext` of the Prompt Builder name, and the ones the parameter `computeContexts` names |

What holds for every page:

- **It changes nothing.** Every request is a GET, and the one file the program writes is the page, in the WORK folder of its session.
- **It does not fail.** A service that does not answer, a right the session lacks and a folder that is not there are lines of the page: `not checked` with the HTTP status, or `missing`. Where PROC PYTHON does not run in the compute context, the page says that and nothing else. The program switches the option `SYNTAXCHECK` off while it runs and sets `SYSCC` back to 0 at its end, because SAS Job Execution shows the page of a job that completed and its own error page for one that failed.
- **It lists what the identity of its SAS session can read.** In a compute context that runs as a service account, that identity is the service account and not the person who opened the page, and what that account can read depends on how the system configures the context. No token and no user id is written to the page, and of an answer that was refused only the status.
- **Every text is escaped.** A name from the system or from a parameter is text on the page, and a guide address is a link only where it is an `https` address of the website of the accelerator or of this SAS Viya: the parameter can come with the request, so any other address is shown as text, with a line that says why.
- **No advice is an upload.** What the page says to do about a custom step that is missing names the import of the package and `mdb content-deploy`, which register it. Measured on 2026-10-12: a `.step` file uploaded in the place of a step is a file of the folder and no step, and `mdb content-deploy` then registers the step and leaves that file beside it.

Parameters of the job definition:

| Parameter | Value | |
| --- | --- | --- |
| `_action` | `execute` | |
| `_output_type` | `html` | The job writes the page itself, to the fileref `_webout` |
| `_contextName` | `SAS Studio compute context` | The compute context the job runs in: one that runs as the person who opens the page |
| `contentRoot` | `/SAS Agentic AI Accelerator` | The content folder that is checked |
| `caslib`, `casServer` | `Public`, `cas-shared-default` | Where the tables of the reports are |
| `credentialDomain` | `agentic-ai-keys` | Used where the option of the Prompt Builder report is empty or says `none` |
| `repositoryName`, `llmProject`, `embeddingProject`, `decisionProject` | `LLM Repository`, `LLM Model Project`, `Embedding Model Project`, `Decision Model Project` | The names `mdb setup` gives them |
| `computeContexts` | `SAS Studio compute context\|SAS Job Execution compute context` | Compute contexts to look for, separated by `\|` |
| `guideUrl` | `https://sassoftware.github.io/sas-agentic-ai-accelerator` | Where the guides are: linked on the website of the accelerator or on this SAS Viya, text anywhere else |

`_contextName` and `contentRoot` are settings of a site: the compute context that runs as its users, and the folder the package was imported into.

A session without `_webout` - the program run in SAS Studio - gets a NOTE that names the file of the page in its WORK folder.

## Load-Accelerator-Tables

The job gives the two reports their tables after an import of the package, without the command line. Started from SAS Job Execution:

```text
https://<your SAS Viya host>/SASJobExecution/?_program=/SAS Agentic AI Accelerator/Data/Load-Accelerator-Tables&_contextName=<a compute context that runs as you>
```

- **The fact sheets** are loaded by *Load-Fact-Sheets.sas* of the folder `Logging and Monitoring` of the content root, which the job includes: one program loads the sheets, run on its own or from the job. The job hands it its folder (`<contentRoot>/Data`) and its CAS library through the two settings `_lfs_path` and `_lfs_caslib`. Where the program is not in the folder, the job says so with a WARNING and loads the release table; a fact sheet table that is then not in the CAS library at the end of the job is the ERROR line of that check, and the job fails (*The state of the job* below). A folder that is not there is the same WARNING: measured on 2026-10-13 with a content root without `Logging and Monitoring`, the FILENAME statement for a file of that folder wrote two ERROR lines in front of the WARNING, so the job - and *Load-Fact-Sheets.sas* for the folder of the sheets - asks the Folders service for a folder first, with the request *Start Here* asks for the content root with, and assigns no fileref where the answer is 404.
- **The release table** is loaded by the job itself, from `Data/ACCELERATOR_RELEASES.csv`, the file `mdb load-releases --csv` writes. CAS reads the file with the eleven columns of `mdb` in their order, the three numbers (`is_current`, `release_rank`, `item_rank`) as DOUBLE and the eight text columns as VARCHAR - the types the table has that `mdb load-releases` loads. No value passes a SAS variable, so none is cut to 32,767 bytes.
- **Against the table of `mdb`**, measured on SAS Viya 2026.09 on 2026-10-12 with both loaded from the changelog of one commit: 707 rows, the same eleven columns in the same order, the same types and the same lengths. One difference: the formatted length - the width CAS keeps for display beside the length of a column - is 16 where the table of `mdb` has 6, 10, 8 and 8, for the four text columns whose longest value is shorter than 16 bytes (`version`, `release_date`, `change_type`, `builder_part`). It changes nothing: a width of 16 shows every value of these columns whole, and the page of the Prompt Builder reads nothing from the table it is assigned. The job names the name and the type of a column and no length, so CAS decides both for it.
- **A table that exists is replaced only by one that loaded completely.** The file is uploaded beside the table as `<table>_NEW`, a table of the CAS session, and its rows are counted against the lines of the file. Only then is the table dropped, the upload promoted under its name and saved. A table that has the name `<table>_NEW` before the upload is no table of the job - a site can have one -, so CAS is asked first (`table.tableExists`): where it does not answer that there is none, nothing is uploaded and no table of that name is dropped, with a WARNING that says to rename or drop that table. The file a table of the name of `releaseTable` was saved to is looked at the same way: it is loaded as `_LAT_SAVED` only where no table of that name is in the CAS library, and is otherwise left as it is with the ERROR line of a file that could not be looked at. A file that is not in the folder, a first line with other columns and an upload that does not hold every row leave the table as it is, with a WARNING. *Load-Fact-Sheets.sas* replaces each fact sheet table the same way: the upload of the sheet whose rows were counted is promoted under the name of the table and saved, and the sheet is not loaded a second time. Where the promote is refused, a table of that name that is in memory - the table could not be dropped - is left as it is, and where none is, the table is loaded again from the file it was saved to before. Each of these outcomes, and a load from the file that fails as well, is a WARNING of its own.
- **The session.** In a compute context that runs under a service account the SAS session is that account. The log then holds one NOTE that the session does not run as the user who started the job - the program compares `SYSUSERID` with `SYS_COMPUTE_SESSION_OWNER` as the persons they name, a domain behind `@` or in front of a backslash dropped, and writes neither -, and that the parameter `_contextName` names a compute context that runs as you. What such a session may read depends on how the system configures its context: measured on 2026-10-12 in the `SAS Job Execution compute context` of the test system, the log held the NOTE, and the job read the folder `Data` and loaded the release table as it did in the `SAS Studio compute context`.
- **The state of the job.** The job writes an ERROR line and sets `SYSCC` to 1012 when one of the four tables is not in the CAS library at its end, and when a parameter is refused. A table that was left as it is and is there is a WARNING.

| Parameter | Value | |
| --- | --- | --- |
| `_action` | `execute` | |
| `_contextName` | `SAS Studio compute context` | The compute context the job runs in: one that runs as the person who starts it |
| `contentRoot` | `/SAS Agentic AI Accelerator` | The content folder whose `Data` folder holds the four files |
| `caslib` | `Public` | The CAS library of the four tables |
| `releaseTable` | `ACCELERATOR_RELEASES` | The name of the release table: a SAS name of 28 characters at most. A table of that name that exists and lacks one of the ten columns every release table has - a fact sheet, the log table - is left as it is, with an ERROR line; the release table of 2.2.0, without `builder_part`, is replaced. Where no table of that name is in memory, the job looks for the file one was saved to (`<name>.sashdat`, which a restart of the CAS server leaves of a saved table), loads it as a table of its session to read its columns, and drops it again: a file that lacks those columns or can not be loaded is left as it is the same way |

`mdb load-releases` and `mdb load-facts` load the same tables from a checkout and stay the way to load them from a workstation.

## Tests

```bash
python -m pytest SAS-Viya-Integrations/Setup/tests
```

`tests/test_start_here.py` runs the Python of *Start-Here.sas* against a SAS Viya system that is made up (`tests/start_here_harness.py`): a complete installation, then one thing taken out at a time, a service that answers 401, 403, 500 or 503, a request without an answer, a `release.json` that is empty and an entry of it that is not in the folder. It reads from the program that it asks with GET and nothing else, that the page holds no token and no user id, and that every text is escaped. For a session that is refused every request it holds the one line at the top - with the counts of the page that was measured, 13 ok and 15 not checked -, for a session of the user and for one of another user; that one request that is answered, a service that is down and a request without an answer keep every line; that a `release.json` whose member names another service is not asked for; and that the advice for a step names the import and `mdb content-deploy`, for a step that is missing, a file that was uploaded in its place and a file that lies beside the registered step. A reference in the place of a file, a step, a job definition, a report, a folder and of `release.json` is held as `missing` and as not followed - the page of 2026-10-13 called a file `present` whose name only a reference had. A reference of the name and kind of an entry beside its object is held as `missing` as well, for each of the five kinds and for `release.json`: for a file with such a reference beside it the page of 2026-10-13 said `ok | present` while `mdb content-deploy` failed the entry. A reference to an object of another kind changes no line. `tests/test_start_here_one_rule.py` holds the rule the page shares with `mdb content-deploy` as one table: the kind of an entry and the number of objects and of references of its name and kind in its folder give what `mdb` says of the entry and the line of the page. Each row is built as a made-up folder that both read - the Python of the page, and `deploy` of `mdb` in a dry run, loaded from the source of this checkout -, with what `mdb` does to an object it found stood in for; a second table holds what the two say of the entries below a folder. The table by which the page tells the kind of a member is held against the one of `mdb`. `tests/test_load_accelerator_tables.py` holds the columns and types of the release table against the columns of `mdb` and against the file `mdb` writes from `CHANGELOG.md`, reads the order of the statements that replace a table, holds what the header of the program says of *Load-Fact-Sheets.sas* against the statements of that program, and checks that the four columns with the other formatted length are the ones whose longest value is shorter than 16 bytes. `tests/test_loader_followed.py` follows the macros of the job with `macro_harness` and runs the CASL of their PROC CAS step against a CAS library that is made up (`casl_harness`, both in the tests of `Logging-Monitoring`): a folder the Folders service answers 404 for is the WARNING and no FILENAME statement, and a table of the name of `releaseTable` that is another table is left as it is - in memory, or only as the file it was saved to -, and a table that has one of the two names the job loads a table of its session under (`<table>_NEW`, `_LAT_SAVED`) is neither loaded over nor dropped; `Logging-Monitoring/tests/test_fact_sheets.py` holds the same for *Load-Fact-Sheets.sas*. The SAS code of both programs does not run in these tests: they hold its text, and say what it does if SAS and CAS behave as their model has it. `Logging-Monitoring/tests/test_handed_to_sas.py` holds *Start-Here.sas* to the escaping function of the logging programs.

`tests/test_readme.py` holds this page: the two addresses with `_contextName`, the parameters of both tables against the programs and against the compute context the manifest gives the Prompt Builder job definition, and what the page says of a custom step, of *Load-Fact-Sheets.sas* and of the four widths.

`tests/test_custom_steps.py` reads the custom step *LLM - Create LLM Call* of the folder `Custom Steps`, which has no code file of its own. For the box *Save the code to a filename?* ticked and no path - the values the step comes with - the program of version 1.0 held an ERROR line and an ABORT statement; the program of version 1.1 writes the code to a temporary file there, as the label of the path says, and keeps the fileref `_slo_LLM`. For a path without an apostrophe its statements are the ones of version 1.0, character for character; an apostrophe of the path is doubled in the statement that assigns the file (version 1.3, and *LLM - Get Options* 1.2), where it ended the text of that statement. A quotation mark of the path is a character of it: measured on 2026-10-13 with the code SAS Studio generates, which writes the value of the path control masked, the DATA step of both steps - it reads the value between quotation marks - held a path with a semicolon, an apostrophe, a quotation mark, an ampersand and a percent sign whole; the tests follow that path and two more with quotation marks from the DATA step on. For *LLM - Get Options* in the state it comes with, the tests follow its closing NOTE: version 1.1 ended there with `ERROR 180-322` and a failed job behind the code file it had written (measured on 2026-10-13), because the NOTE resolved the statement that assigns the temporary file with its semicolon; version 1.2 keeps the statement without the semicolon and the NOTE reads it as text. For the options it follows the reading of version 1.2 - and of *LLM - Get Options* 1.1 and `SAS-Code-LLM-Calls/Create-LLM-Call.sas` - on the table the JSON engine makes of the `options.json` of every LLM definition of the repository: every option is read with its default, also one that lists the values it can take (`values`), where versions 1.0 and 1.1 transposed the table and PROC TRANSPOSE stopped at such an option; and a run that can not read the default of every option writes no code and no file and ends with one ERROR line and `SYSCC` 1012. For the model a run looks up (version 1.4, and *LLM - Get Options* 1.3) the tests follow the open code of both steps with the macro variables SAS Studio wrote on 2026-10-13 for a step that was run as it comes - none for the model table, the model name and the two text fields: the program reads no control that is not there, asks SAS Viya for nothing and ends with one ERROR line that says that no model with an options file was chosen, as it does for every other state of the controls without a model name or without an options file. And the URI of a model table is asked for without the blanks of its column: with a column of 200 characters the versions before asked for `<uri><blanks>/content` and got HTTP 404 (measured on 2026-10-13).

`tests/test_step_macro_statements.py` reads every `%put`, `%let` and macro call of the *LLM* and *MM* steps but *LLM - Log Parser*: none resolves with an ampersand a text the program made while it ran - with `CALL SYMPUT`, `CALL SYMPUTX` or `INTO` -, but for four variables of *LLM - Get All Prompts* that hold a number or a name its Python has looked at. It also holds that a step deletes the macros it defines and no other: *MM - Get Model Information* 1.0 ended with a statement that deleted the macro of *MM - Get Models in Project*. `tests/test_step_sources.py` holds the step files of the folder `Custom-Steps`: `createdBy` and `modifiedBy` of the ten steps that were saved from SAS Studio hold the text `mdb package-export` writes in the place of a user id, and no step has another field that names a user.
